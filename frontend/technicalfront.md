Поведение при дублях не соответствует протоколу
Сейчас при обнаружении активной заявки на объект происходит автоматическая склейка описания в существующую заявку.
Протокол требует другое поведение:
сервер должен вернуть статус duplicate_detected;
клиент показывает модальное окно;
только после подтверждения пользователя команда повторяется с флагом force_create;
при force_create заявка создается.
Автоматическая склейка — это нарушение ожидаемого сценария.
Пользователь может не знать, что его новая заявка не создана, а текст был приклеен к чужой/существующей заявке.
2.4. Поиск дублей слишком узкий
Текущий поиск дубля учитывает:
объект;
группу;
отдел.
Протокол говорит про активную заявку на объект.
Если на объекте уже есть активная заявка с другой группой или другим отделом, текущая логика дубль не увидит.
Нужно искать прежде всего по объекту и статусу активности.

2.5. Для дублей нужен список, а не одна запись
Протокол ожидает, что при duplicate_detected клиенту передаются существующие заявки:
номер;
описание;
дата.
Текущий метод поиска возвращает одну запись и не содержит даты заявки.
Для корректной модальки на фронтенде нужен список подходящих активных заявок.
2.6. force_create читается из данных заявки
Протокол отдельно подчеркивает:
force_create находится только на уровне команды;
force_create не является частью payload.
Сейчас сервис читает его из данных заявки. Это нарушение контракта.
Правильно, когда контроллер синхронизации передает этот флаг отдельно как мета-параметр команды.
