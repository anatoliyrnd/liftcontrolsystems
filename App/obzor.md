# Глубокий анализ архитектуры бэкенда (Lift Control Systems)

Ниже представлен подробный архитектурный анализ предоставленного бэкенда, структурированный в формате документации (Markdown). Анализ охватывает ответственность модулей, протоколы взаимодействия и специфику работы с базой данных.

---

## 1. Краткое описание файлов и ответственности классов

Архитектура бэкенда построена по **слоеному принципу (Layered Architecture)** с элементами Service Locator и строгой изоляцией бизнес-логики от транспорта и работы с БД. Система представляет собой ядро для диспетчерской службы лифтового хозяйства с продвинутой поддержкой **Offline-First** режима для мобильных приложений.

### Точка входа и Инициализация
*   **`api.php` (Front Controller)**: Единая точка входа для всех HTTP-запросов. Отвечает за глобальный перехват исключений, маршрутизацию запросов на публичные (`PublicController`) и защищенные (`ApiController`) эндпоинты, а также формирование финального JSON-ответа.
*   **`bootstrap.php`**: Инициализация ядра. Загружает конфигурации, регистрирует автозагрузчик, настраивает логгер и устанавливает кастомный `error_handler` для конвертации всех PHP-ворнингов и нотисов в `ErrorException` (чтобы ошибки не выводились в JSON-ответ, а корректно падали в лог).
*   **`autoload.php`**: PSR-4 автозагрузчик, маппящий неймспейс `App\` на файловую систему.

### HTTP Слой (`App\Http`)
*   **`Request`**: Абстракция над глобальными массивами PHP. Парсит JSON-тело, извлекает заголовки авторизации, определяет `action` (вызываемый метод) и идентификатор тенанта.
*   **`Response`**: Фабрика для формирования стандартизированных JSON-ответов (успех или ошибка с кодом). Управляет HTTP-статусами и заголовками.
*   **`Cors`**: Middleware для настройки заголовков Cross-Origin Resource Sharing (необходимо для работы современного SPA-фронтенда, например, на Vite/React/Vue).
*   **`ErrorCode`**: Справочник констант с кодами ошибок (например, `Unauthorized`, `ValidationError`, `InternalError`). Обеспечивает единый контракт ошибок с фронтендом.

### Контроллеры (`App\Controller`)
*   **`ApiController`**: Главный коммутатор защищенных действий. Анализирует `action` из запроса, проверяет права доступа и делегирует выполнение соответствующему Сервису.
*   **`PublicController`**: Обрабатывает запросы, не требующие авторизации (например, `get_tenant_info` для получения настроек организации на экране входа).
*   **`AuthController`**: Отвечает за аутентификацию, выпуск Access/Refresh токенов, логаут и сброс сессий.

### Сервисный слой / Бизнес-логика (`App\Service`)
*   **`AuthService`**: Управление сессиями. Проверка паролей, генерация хэшей токенов, валидация "отпечатка устройства" (device fingerprint) для защиты от угона сессий.
*   **`CallService`**: Ядро системы. Управление жизненным циклом заявок (создание, смена статусов, назначение бригад/механиков, закрытие). Содержит валидацию бизнес-правил.
*   **`AddressService` & `AddressCacheService`**: Работа с иерархическим классификатором адресов (Город -> Улица -> Дом -> Лифт). Кэширование деревьев для быстрого отображения в выпадающих списках UI.
*   **`NotificationsService`**: Триггер событий (создание заявки, смена статуса). Формирует уведомления для UI (тосты), Push-уведомлений и интеграции с Telegram-ботом.
*   **`ConfigService`**: Чтение и запись глобальных настроек системы (таблица `lift_options`).
*   **`LegacyProxyService`**: Адаптер (Anti-Corruption Layer) для поддержки старых версий фронтенда или интеграции с внешними legacy-системами (например, SPult).

### Слой доступа к данным (`App\Repository`)
*   **`CallRepository`, `UserRepository`, `AddressRepository`, `HistoryRepository`, `NoteRepository`**: Классы, инкапсулирующие SQL-запросы. Отвечают только за чтение и запись в БД, не содержат бизнес-логики.

### Инфраструктура и Поддержка
*   **`App\Tenant`**: Класс для мультитенантности. Определяет, к какой базе данных или префиксу таблиц обращаться в зависимости от организации.
*   **`App\Registry`**: Простейший DI-контейнер / Service Locator для получения инстансов сервисов и репозиториев.
*   **`App\Exceptions\ApiException`**: Исключение бизнес-логики. Если оно выброшено, `api.php` вернет клиенту понятное сообщение и специфичный `ErrorCode`.
*   **`App\Support\Logger`**: Обертка над PSR-3 логгером для записи событий и фатальных ошибок в файлы.

## 2. Анализ API и Протокола взаимодействия

API системы спроектирован не как классический REST, а как **RPC over HTTP (Action-based API)**, что является оптимальным выбором для сложных корпоративных SPA-приложений и мобильных клиентов с offline-режимом.

### Архитектурный стиль и Маршрутизация
*   **Единый Эндпоинт**: Все запросы идут на `api.php`.
*   **Параметр `action`**: Маршрутизация осуществляется не по HTTP-методам и URL (как в REST `POST /tickets`), а по полю `action` в теле JSON-запроса (например, `{"action": "create_ticket", "payload": {...}}`).
*   **Преимущества**: Упрощает пакетную отправку данных, облегчает реализацию очереди оффлайн-действий на клиенте и упрощает проксирование через `LegacyProxyService`.

### Протокол Аутентификации и Безопасности
Система использует продвинутую двухфакторную сессионную модель:
1.  **Access Tokens** (`lift_access_tokens`): Короткоживущие токены для каждого запроса. В БД хранятся **только их SHA-256 хэши** (`token_hash`), что исключает компрометацию сессий при утечке базы.
2.  **Refresh Tokens** (`lift_refresh_tokens`): Долгоживущие токены для обновления Access-токенов.
3.  **Device Fingerprinting**: Refresh-токены жестко привязаны к `device_fingerprint` и `user_agent`. При попытке использовать украденный refresh-токен с другого устройства, сервис `AuthService` это обнаружит и аннулирует сессию.
4.  **RBAC (Role-Based Access Control)**: Права проверяются на уровне `ApiController` на основе ролей (`administrator`, `dispatcher`, `engineer`, `guest`) и гранулярных флагов в таблице `lift_users` (например, `user_edit_obj`, `user_read_all_calls`).

### 🌟 Протокол Offline-Sync (Идемпотентность и Батчинг)
Это самая сильная и сложная часть архитектуры, спроектированная для работы монтажников в подвалах и шахтах лифтов без связи. Протокол работает на уровне "пачек" (batches):

1.  **Формирование очереди на клиенте**: Клиент генерирует `command_uuid` (v4) для каждого действия (создание заявки, добавление комментария) и группирует их в `batch_id`.
2.  **Идемпотентность пачки (`offline_sync_log`)**: При появлении сети клиент отправляет весь пакет. Сервер сначала проверяет `batch_id` в `offline_sync_log`. Если такой пакет уже обрабатывался (например, сеть оборвалась после сохранения в БД, но до отправки ответа), сервер **не выполняет действия заново**, а мгновенно возвращает сохраненный `response_payload`.
3.  **Идемпотентность команд (`offline_command_log`)**: Внутри пачки каждое действие проверяется по `command_uuid`. Это защищает от дублирования заявок.
4.  **Изоляция ошибок (`offline_actions_archive`)**: Если в пачке из 10 команд одна падает с ошибкой валидации или нехватки прав, **весь пакет не откатывается**. Успешные команды применяются, а ошибочная переносится в "Архив отброшенных действий" с сохранением `payload_snapshot` и кода причины (`reason`). Фронтенд получает ответ и может точечно подсветить пользователю, какая именно оффлайн-заявка не синхронизировалась и почему.

### Синхронизация справочников (Delta-Sync)
Для минимизации трафика используется таблица `lift_dict_versions`. Клиент при старте запрашивает версии словарей (адреса, типы заявок, причины). Если версия на сервере выше, клиент скачивает только измененные данные (или полный срез, если структура изменилась).

### Обработка Ошибок и Контракт ответов
*   Все ответы имеют строгую структуру.
*   **Business Errors**: Выбрасываются через `ApiException`. Клиент получает специфичный код из `ErrorCode` и может показать локализованное сообщение.
*   **Fatal Errors**: Любая необработанная ошибка PHP (благодаря `bootstrap.php`) перехватывается, логируется с трейсом в `app.log`, а клиенту уходит обезличенный `ErrorCode::InternalError` (HTTP 500), чтобы не светить стектрейсы и структуру БД.

## 3. Резюме по структуре Базы Данных (`l3.sql`)

База данных нормализована и отражает предметную область "Диспетчерская лифтового хозяйства":
*   **`lift_calls`**: Центральная таблица (Заявки). Содержит денормализованные поля для быстрого поиска (адрес, статусы, даты, назначенные сотрудники `call_staff` 1-3). Поддерживает оффлайн-заявки через `offline_uuid`.
*   **Адресный классификатор**: Строгая иерархия `lift_city` -> `lift_street` -> `lift_home` -> `lift_object` (сам лифт).
*   **История и Аудит**: `lift_history` (лог изменений заявки), `lift_notes` (комментарии, включая фото/файлы с поддержкой оффлайн-флага `is_offline`), `lift_upload` (вложения).
*   **Мультитенантность и Конфигурация**: Таблица `lift_options` хранит настройки (Telegram-токены, таймауты, сроки ремонта), которые могут переопределяться для разных тенантов.
*   **Отчетность**: Таблица `reports` позволяет диспетчерам и прорабам сохранять сложные JSON-фильтры для быстрого доступа к аналитике.

**Вердикт**: Бэкенд представляет собой зрелое, отказоустойчивое Enterprise-решение. Использование RPC-стиля API в связке с трехуровневой защитой от дублей (Batch -> Command -> Archive) и device fingerprinting делает систему готовой к работе в "полевых" условиях с нестабильным интернетом.
