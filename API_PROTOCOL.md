## 🌐 Глобальные параметры сетевого шлюза

Соглашение о ключе запроса:

- Чтение данных (`config`, `open`, `close`, `loadAddress`, `notifications`) — отправляются с ключом `"data"`.
- Команды и отправка данных (`callnew`, `calledit`, `callClose`, `callnote`, `callNewOffline`) — отправляются с ключом `"action"`.

Это разделение закреплено на стороне сервера.

| Параметр            | Значение                                                                                     |
| :------------------ | :------------------------------------------------------------------------------------------- |
| Рабочий шлюз        | https://e-rcs.ru                                                                             |
| Тестовая заглушка   | https://e-rcs.ru                                                                             |
| Метод запроса       | POST                                                                                         |
| Content-Type        | application/json; charset=utf-8                                                              |
| Accept              | application/json                                                                             |
| Архитектурный стиль | RPC-over-POST (все команды инкапсулируются в тело POST-запроса)                              |
| Таймаут фронтенда   | 15 секунд (AbortController)                                                                  |
| CORS                | Разрешены предварительные OPTIONS-запросы, сервер возвращает 200 OK с заголовками разрешения |

## 📅 Форматы данных

⚠️ **Важно:** Начиная с версии 4.0, все даты и время в запросах и ответах передаются исключительно как Unix timestamp (целое число секунд).
Фронтенд-приложение самостоятельно конвертирует timestamp в человекочитаемый формат `dd.mm.yyyy@hh:mm` (без пробелов) для отображения в UI.

| Тип поля                        | Формат                                    | Пример                                      |
| :------------------------------ | :---------------------------------------- | :------------------------------------------ |
| Дата + время события            | Unix timestamp (секунды)                  | 1761214500 (соответствует 23.10.2026@12:15) |
| Числовые идентификаторы         | Integer (числа)                           | 35732                                       |
| Уровень тревоги (`alert_level`) | Integer 1–3                               | 3                                           |
| Флаг присутствия заметок        | String "Есть заметки (N)" или отсутствует | "Есть заметки (3)"                          |

| Код | Канал (Отображение в UI) | Текстовый суффикс сервера |
| :-- | :----------------------- | :------------------------ |
| 0   | — (не уведомлён)         | "Не уведомлен" (без даты) |

| 2   | 🖥 Принял через WEB      | " - онлайн"               |
| 3   | ✈️ Уведомлён в Telegram  | " - в телеграм"           |
| 4   | 💬 Уведомлён в Max       | " - в макс"               |
| 5   | 🔵 Уведомлён в VK        | " - в вк"                 |
| 6   | 📱 Уведомлён по SMS      | " - по смс"               |
| 7   | ✉️ Уведомлён по Email    | " - по email"             |

## 🛠️ Перечень доступных Экшенов (Actions)

```json
{
  "data": "config"
}
```

Пояснение: `user_permissions.user_id` — ID текущего пользователя в таблице `lift_users`. Совпадает с `staff_id` в заявках. Фронт использует его для проверки «мой ли это сотрудник» через `userStore.isAssignedTo()` и передачи в `callClose`.

#### 🔖 Поле role — роль пользователя

| Роль          | Описание                                                                                                              |
| :------------ | :-------------------------------------------------------------------------------------------------------------------- |
| administrator | Полные права. Может редактировать любое поле любой заявки                                                             |
| dispatcher    | Создаёт заявки, редактирует большинство полей (кроме уже заполненных group/department/level), закрывает, комментирует |
| engineer      | Электромеханик. Видит то, что отдаёт сервер. В своих заявках — комментирует, закрывает, ставит статус уведомления     |
| guest         | Только чтение                                                                                                         |
| reserved      | Резерв. Права гостя, заведена под будущее расширение                                                                  |

#### 🔖 Флаги прав can\_\*

Флаги `can_add_ticket`, `can_view_reports`, `can_view_settings` используются фронтендом для сборки меню и показа соответствующих кнопок.  
**Правило:** если сервер не вернул флаг, фронт считает его `false` и соответствующий пункт меню скрывается.

#### 👷 Поле staff_list — справочник электромехаников

Используется в формах создания и редактирования заявки. Если поля нет или оно пустое — фронт показывает пустой выпадающий список. Значение `id` из `staff_list` — это тот самый `staff_id`, который уходит на сервер в `callnew` и `calledit`.

#### 📚 Справочники отдел / запрос / группа

Приходят как ассоциативный объект `{"id": "name"}`. Ключ совпадает с полями заявки `department_id` / `request_id` / `group_id`. Фронт нормализует его в массив и наполняет `<select>`.

Запрашивает из базы данных полный стек активных, не устранённых неисправностей, находящихся на мониторинге диспетчера и в работе у аварийных бригад.

#### 📥 Тело запроса (Request Payload)

```json
{
  "data": "open"
}
```

Возвращает массив объектов инцидентов. Поля закрытия (`solution`, `close_date`, `close_name`) в этом режиме содержат прочерки или заглушки.

| Уровень | Значение | Рекомендуемые случаи                                                                  |

⚠️ **Deprecated:** Поле `staff_date` (`"DD.MM.YYYY@HH:MM - канал"`) упразднено. Фронтенд собирает сводную строку для UI самостоятельно на основе `notify_date` и `notify_status`.

### 3. Получение списка закрытых заявок (close)

Запрашивает архив устранённых неисправностей за выбранный временной интервал.

#### 📥 Тело запроса (Request Payload)

```json
{
  "data": "close",
  "period": "1"
}
```

#### 🔖 Параметр period

| Значение | Период            |
| :------- | :---------------- |
| "1"      | Последние 24 часа |
| "2"      | 2 дня             |
| "3"      | 3 дня             |
| "7"      | 7 дней            |

### 4. Получение справочника адресов (loadAddress)

Вызывается при инициализации SPA для загрузки и кэширования базы городов, улиц, домов и лифтов.

#### 📥 Тело запроса (Request Payload)

```json
{
  "data": "loadAddress"
}
```

#### 📤 Тело успешного ответа (Response 200 OK)

Возвращает объект с иерархическими массивами. Фронтенд «сплющивает» их в плоскую таблицу для быстрого поиска.

```json
{
  "status": "ok",
  "action": "loadAddress",
  "message": {
    "city": [{ "id": 1, "city_name": "г. Ростов-на-Дону" }],
    "street": [{ "id": 2, "street_name": "ул. Ленина", "city_id": 1 }],
    "home": [{ "id": 5, "home_name": "5", "street_id": 2 }],
    "object": [{ "id": 209, "object_name": "п.1 пасс.", "home_id": 5 }]
  }
}
```

### 5. Регистрация новой заявки (callnew)

Создает новую заявку в системе. На этапе создания назначается только основной ответственный (`staff_id`). Остальные слоты (`staff_id2`, `staff_id3`) добавляются позже через `calledit`.

#### 📥 Тело запроса (Request Payload)

```json
{
  "action": "callnew",
  "city_id": "1",
  "street_id": "2",
  "home_id": "3",
  "object_id": "11",
  "fullAddress": "г. Ростов-на-Дону - Красноармейская ул. дом № 2 корп.2 - п. 1 прав.",
  "group_id": "8",
  "request_id": "2",
  "department_id": "22",
  "repair_time": 1761220800,
  "details": "Описание проблемы оператором диспетчерской службы",
  "staff_id": 3
}
```

#### 🔖 Описание полей

| Поле            | Тип               | Обязательность | Описание                                                                                                                                |
| :-------------- | :---------------- | :------------- | :-------------------------------------------------------------------------------------------------------------------------------------- |
| `city_id`       | string \| integer | Обязательное   | ID города                                                                                                                               |
| `street_id`     | string \| integer | Обязательное   | ID улицы                                                                                                                                |
| `home_id`       | string \| integer | Обязательное   | ID здания                                                                                                                               |
| `object_id`     | string \| integer | Обязательное   | ID объекта/лифта                                                                                                                        |
| `group_id`      | string            | Обязательное   | ID группы лифтов                                                                                                                        |
| `request_id`    | string            | Обязательное   | ID типа неисправности                                                                                                                   |
| `department_id` | string            | Обязательное   | ID отдела/цеха                                                                                                                          |
| `fullAddress`   | string            | Обязательное   | Полная собранная строка адреса для текстового вывода в табличной сетке. Сервер использует её для отображения, но хранит связи по `_id`. |
| `details`       | string            | Обязательное   | Текстовое описание неисправности, введённое оператором                                                                                  |
| `repair_time`   | integer           | Обязательное   | Плановая дата и время окончания ремонта в формате Unix timestamp (секунды)                                                              |
| `staff_id`      | integer           | Опциональное   | ID ответственного. Берётся из `staff_list`, полученного в `config`                                                                      |

⚠️ **Примечание по безопасности:** Фронтенд не отправляет `notify_status`, `alert_level` и `staff_date`. Сервер самостоятельно инициализирует эти поля (для `alert_level` — на основе правил, для `notify_status` — на основе выбора механика).

#### 📤 Тело успешного ответа (Response 200 OK)

```json
{
  "status": "ok",
  "message": "Заявка успешно зарегистрирована.",
  "generated_id": 35733
}
```

### 6. Частичное редактирование заявки (calledit)

Применяется диспетчером для переназначения ответственных, смены цеха, характера неисправности или дополнения описания. В теле POST-пакета передаются только обязательный идентификатор инцидента (`call_id`) и те поля, значения которых были изменены в интерфейсе (dirty tracking).

⚠️ **Важно:** Адрес объекта менять нельзя. Закрытие заявки через `calledit` запрещено — для этого используется отдельный экшен `callClose`.

#### 📥 Тело запроса (Request Payload)

```json
{
  "action": "calledit",
  "call_id": 35732,
  "staff_id": 3,
  "notify_status": 1,
  "staff_id2": 1,
  "notify_status2": 2,
  "group_id": "9",
  "repair_time": 1761230000
}
```

#### 🔖 Описание полей

| Поле                                                  | Тип             | Обязательность | Описание                                                    |
| :---------------------------------------------------- | :-------------- | :------------- | :---------------------------------------------------------- |
| `call_id`                                             | integer         | Обязательное   | Уникальный номер редактируемой заявки в БД                  |
| `staff_id` / `staff_id2` / `staff_id3`                | integer \| null | Опциональное   | ID ответственного. Если передан null — слот освобождается.  |
| `notify_status` / `notify_status2` / `notify_status3` | integer \| null | Опциональное   | Канал уведомления                                           |
| `group_id`                                            | string          | Опциональное   | ID группы                                                   |
| `department_id`                                       | string          | Опциональное   | ID отдела                                                   |
| `request_id`                                          | string          | Опциональное   | ID типа заявки                                              |
| `details`                                             | string          | Опциональное   | Описание неисправности (с добавленными деталями)            |
| `repair_time`                                         | integer         | Опциональное   | Планируемая дата ремонта в формате Unix timestamp (секунды) |

Все опциональные поля передаются исключительно при наличии правок. Фронтенд не отправляет неизменившиеся поля.

#### 🚦 Ограничение состава ответственных

За один запрос `calledit` допускается:

- либо одно новое назначение (слот был пуст, стал заполнен),
- либо одно снятие (слот был заполнен, стал пуст),
- любое количество замен (значение меняется, но слот остаётся заполненным).

Если клиент прислал больше одного назначения или снятия в одном запросе — сервер возвращает ошибку:

```json
{
  "status": "error",
```

### 9. Синхронизация офлайн-пачки (callNewOffline)

Новый экшен для пакетной отправки заявок, созданных в режиме отсутствия сети (из очереди outbox в IndexedDB).

Особенности работы:

- Фронтенд отправляет заявки пачками по 10 штук (`SYNC_BATCH_SIZE`).
- Сервер всегда ожидает массив `tickets` и прогоняет его через `foreach`.
- **Атомарность:** либо принимается и сохраняется вся пачка, либо отклоняется целиком (с указанием ошибки). Частичное сохранение не допускается.
- **Идемпотентность:** каждый тикет содержит поле `offline_uuid`. Сервер хранит его в таблице `lift_calls` (`UNIQUE`). При повторной отправке пачки (например, если связь оборвалась после сохранения на сервере, но до ответа клиенту) сервер молча игнорирует дубликаты и возвращает `{status: "ok"}`.

#### 📥 Тело запроса (Request Payload)

```json
{
  "action": "callNewOffline",
  "tickets": [
    {
      "offline_uuid": "offline_1714567890123_x7k2p",
      "offline_author_id": 3,
      "offline_author_name": "Сергеенко Сергей",
      "city_id": "1",
      "street_id": "2",
      "home_id": "3",
      "object_id": "11",
      "fullAddress": "г. Ростов-на-Дону - Красноармейская ул. дом № 2 корп.2 - п. 1 прав.",
      "group_id": "8",
      "request_id": "2",
      "department_id": "22",
      "repair_time": 1761220800,
      "details": "Описание проблемы...",
      "staff_id": 3
    }
  ]
}
```

#### 🔖 Описание полей

| Поле                  | Тип             | Описание                                                                                                      |
| :-------------------- | :-------------- | :------------------------------------------------------------------------------------------------------------ |
| `tickets`             | array\<object\> | Массив объектов заявок. Каждый элемент полностью соответствует payload'у экшена `callnew` (без ключа action). |
| `offline_uuid`        | string          | Уникальный идентификатор заявки на клиенте (генерируется при сохранении в outbox).                            |
| `offline_author_id`   | integer         | ID пользователя, создавшего заявку.                                                                           |
| `offline_author_name` | string          | ФИО пользователя, создавшего заявку.                                                                          |

#### 📤 Тело успешного ответа (Response 200 OK)

```json
{
  "status": "ok",
  "message": "Пачка из 10 заявок успешно синхронизирована."
}
```

#### 🔄 Логика фронтенда после успеха

1. Получив `{status: "ok"}`, фронтенд удаляет отправленные заявки из очереди outbox (по списку `offline_uuid`).
2. Сразу после этого фронтенд отдельно запрашивает актуальный список открытых заявок: `{ "data": "open" }`.
3. Полученный массив заменяет `tickets_cache` в IndexedDB и обновляет таблицу в памяти.
4. Если запрос `{ "data": "open" }` упадет с ошибкой сети — это не считается сбоем синхронизации. Данные уже на сервере, а таблица обновится при следующем автоматическом опросе.

### 10. Получение событий-уведомлений (notifications)

Лёгкий polling-эндпоинт для получения свежих событий системы. Показывает тосты о действиях других пользователей и дублирует их в блок «История».

- **Окно свежести:** события старше 30 минут не отдаются.
- **Лимит выборки:** не более 10 последних событий за запрос.
- **Частота опроса фронта:** раз в 120 секунд.

#### 📥 Тело запроса (Request Payload)

```json
{
  "data": "notifications",
  "since_id": 142857,
  "versions": {
    "staff": 0,
    "dicts": 0
  }
}
```

- `since_id` (integer, опционально): ID последнего известного клиенту события. 0 или отсутствие — первый запрос после старта сессии.
- `versions` (object, опционально): версии справочников, которые есть у клиента. Если сервер видит, что они устарели, он вернет массив `outdated`.

#### 📤 Тело успешного ответа (Response 200 OK)

```json
{
  "notifications": [
    {
      "id": 142859,
      "event_type": "emergency",
      "ticket_id": 35732,
      "actor_id": 5,
      "text": "Аварийная заявка №35732 (застрял пассажир)",
      "sound": true,
      "timeout": 15000,
      "created_at": 1761215710
    }
  ],
  "last_id": 142859,
  "versions": {
    "staff": 15,
    "dicts": 8
  },
  "outdated": []
}
```

#### 🔖 Поля события

| Поле         | Тип             | Описание                                                                 |
| :----------- | :-------------- | :----------------------------------------------------------------------- |
| `id`         | integer         | Уникальный ID события (AUTO_INCREMENT)                                   |
| `event_type` | string          | Тип события (см. таблицу ниже)                                           |
| `ticket_id`  | integer \| null | ID заявки — если есть, в тосте появится ссылка «Открыть →»               |
| `actor_id`   | integer         | ID пользователя, вызвавшего событие                                      |
| `text`       | string          | Готовый к показу текст                                                   |
| `sound`      | boolean         | Играть ли звук при появлении тоста (по умолчанию false)                  |
| `timeout`    | integer \| null | Время показа в мс. 0 — не закрывать автоматически. null — дефолт по типу |
| `created_at` | integer         | Unix timestamp создания                                                  |

#### 📋 Типы событий (event_type)

| Значение            | Когда пишется                       | Тип тоста | Рекомендуется звук? |
| :------------------ | :---------------------------------- | :-------- | :------------------ |
| `ticket_closed`     | Заявка закрыта (callClose)          | success   | нет                 |
| `note_added`        | Добавлен комментарий (callnote)     | info      | нет                 |
| `ticket_created`    | Новая заявка (callnew)              | info      | нет                 |
| `ticket_reassigned` | Сменили ответственного              | info      | нет                 |
| `staff_accepted`    | Механик принял в работу             | success   | нет                 |
| `ticket_overdue`    | Ремонт просрочен (alert_level: 3)   | warning   | да                  |
| `emergency`         | Аварийная заявка (застрял пассажир) | error     | да                  |
| `staff_unassigned`  | Сняли ответственного                | warning   | нет                 |

## 🚫 Обработка ошибок сетевого шлюза (Error Handling)

⚠️ **Важно:** Из-за настроек веб-сервера (Nginx перехватывает 4xx/5xx статусы) все ответы сервера приходят с HTTP-статусом 200 OK.
Ошибки определяются исключительно по полям `status: "error"` и `code`/`message` в теле ответа.

При сбоях шлюз обязан вернуть строго структурированный JSON-пакет:

```json
{
  "status": "error",
  "code": "error_code",
  "message": "Текст ошибки для пользователя."
}
```

### 💡 Что это дает архитектуре системы?

1. **Разделение ФИО:** Теперь сервер хранит `surname`, `name`, `patronymic` в отдельных полях. Это позволит в будущем легко собирать из них компактные инициалы для узких сеток таблиц (например, _Иванов И.И._).
2. **Безопасная смена пароля:** Передача старого пароля (`old`) обязательна для верификации личности на бэкенде перед записью нового хэша.
3. **Гибкая настройка колонок:** Передача JSON-структур порядка (`order`) и скрытия (`hidden`) позволяет фронтенду динамически перестраивать компоненты таблиц на основе сохраненного состояния пользователя.

# Новый action:

```
json
{ "data": "ticket", "call_id": 35732 }
```

Ответ:
{ "status": "ok", "data": { ...полный объект заявки, как в open/close... } }

Или { "status": "ok", "data": null } если не найдена. Реши, что чище: null или { status: 'error', code: 'not_found' }. Предлагаю { status: 'ok', data: null } — клиенту проще различать «сеть упала» (status: 'error') и «заявки нет» (data: null).

В EditTicket payload — уточнить, что сервер принимает оба имени:

text
