# ТЗ бэкенд — модуль управления адресным пространством

Контракт API и алгоритмы: `md/ADDRESS_ADMIN.md`. ТЗ фронта: `md/техзадания/adressfront.md`.
Документ описывает **требования и паттерны**, а не реализацию. Код выдаётся по одному файлу на сообщение, только по явной команде.

## 0. Область

Волна 1: дерево, перенос трёх уровней, каскад `vis`, поиск, детали узла, лог + cron.
Вне волны: инфо-поля оборудования, группы, XML-импорт, редактирование в SPA, матрица прав, ручные create/rename/delete узлов.

Всё, что не требуется маршрутами из контракта §6, **не реализуется**. Спекулятивные методы интерфейсов запрещены (прецедент: удаление `fillRequired` и лишних методов контракта пользователей).

## 2. Паттерны и SOLID — конкретно

### 2.1 Слои и направление зависимостей

```
Controllers  →  Services  →  Contracts  ←  Repositories\Db
      ↓             ↓
Support\AddressTree (порядок/подписи/пути, чистые функции над строками)
                    ↓
              App\Support\Address (владелец ключей и формата)
              App\Service\AddressCacheService (версия слоя)
```

Правило: контроллер не знает SQL, репозиторий не знает HTTP, сервис не знает `$_GET`/`$_POST`. Зависимости направлены на интерфейсы; `Db`-реализация — единственное место, где живёт `App\Database\DB`.

### 2.2 SOLID по пунктам

| Принцип | Как соблюдается                                                                                                       | Что считается нарушением                                             |
| ------- | --------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- | --- |
| **S**RP | чтение дерева / запись узла / каскад / конфликты / лог — разные контракты; сортировка и display — в сервисе, не в SQL | репозиторий, который одновременно форматирует display и пишет лог    |
| **O**CP | новый уровень добавляется своим репозиторием, контроллером и записями в карте маршрутов                               | диспетчеризация по строке типа, раскопированная по контроллерам      |     |
| **L**SP | контракт описывает поведение (что возвращает, что бросает), а не детали SQL                                           | реализация, возвращающая `false` вместо `null` при отсутствии записи |
| **I**SP | клиент видит только нужные методы: `TreeController` не зависит от записи, `VisController` — от поиска                 | один «AddressRepository» на 30 методов, как в треке А                |
| **D**IP | контроллеры и сервисы зависят от `Contracts`; биндинг интерфейса — одна строка в `Bootstrap`                          | `new Db…()` внутри сервиса                                           |

### 2.3 Шов Db→Api

Как в разделе пользователей: конкретный класс биндится отдельно, интерфейс ссылается на него через `$c->get(класс)`. Трек Б меняет только строку биндинга, потребители не правятся.

### 2.4 Тип узла несёт маршрут — enum и белый список типов не вводятся

Router работает ключом `page.action` и **не выводит** имя метода из строки. Тип узла уже закодирован в маршруте: `city.*`, `street.*`, `home.*`, `object.*`. Поэтому:

- параметра `type` в запросах нет, читать его из ввода запрещено;
- enum-диспетчер и белый список типов не создаются — они дублировали бы карту маршрутов;
- имя таблицы, колонки родителя, колонки имени, колонки ключа и лимиты длины знает **репозиторий сущности** (константы класса), одна таблица — один репозиторий;
- целевой родитель закреплён за маршрутом: `object.move` → дом, `home.move` → улица, `street.move` → город. Проверка «тот ли тип цели» не нужна, тип цели не приходит извне.

Поле `type` в ответах остаётся как данные для фронта и для лога, селектором SQL не является.

Запрещено: собирать имя таблицы/колонки из ввода, ветвиться по строке типа в контроллере или сервисе, вводить «универсальный адресный репозиторий» поверх четырёх сущностных.

### 2.5 Актёр — value object

`Support\Actor` (readonly: id, login, ip, user_agent) собирается контроллером из сессии и передаётся в сервис. Сервис **не зависит** от `SessionAuth` — это делает его проверяемым без сессии и не тянет HTTP-слой в домен.

### 2.6 Домен в PHP, SQL — тупой

Репозиторий возвращает сырые строки. Display-подпись, ключ сортировки, порядок, разбор типов — в сервисе через `App\Support\Address`. Причина: сортировка обязана совпадать с клиентским ключом пикера, а `ORDER BY` в SQL этого не даёт.

### 3.3 Сессия — требует решения (блокер B4)

Варианты:

- **(а)** извлечь старт сессии в общий `Company\Admin\Support\Session::start()` и звать из обоих Bootstrap — **рекомендуется**, один владелец, патч панели на одну строку;
- **(б)** скопировать 25 строк ini в адресный Bootstrap — нарушение DRY, риск расхождения параметров.

До решения файл `Bootstrap.php` модуля не выдаётся.

## 4. Контракты репозиториев

Один контракт на таблицу. Общие требования:

- отсутствие записи → `null`, не `false` и не «пустой массив как повезёт»;
- пишущий метод возвращает **изменённые** строки (`rowCount`), это отражено в докблоке;
- `findById` — сырая строка своей таблицы, без JOIN; `findWithPath` — своя строка плюс id/имена/типы предков **одним** запросом (защита от N+1);
- `search` возвращает строки уже с именами предков через JOIN, чтобы сборка `path` не делала запрос на каждый результат;
- `listIdsBy*` и `occupiedKeys` читают **без фильтра `vis`**: скрытые узлы участвуют в каскаде и в проверке конфликтов, UNIQUE их не различает;
- пишущие методы предполагают активную транзакцию и **сами её не открывают**;
- display-строки и сортировка в репозитории запрещены — это `Support\AddressTree`.

### 4.6 Почему `relocate`, а не `move` + `rename`

Родитель, имя и ключ пишутся **одним** UPDATE. Между двумя запросами читатель увидел бы новое имя со старым ключом (или новый адрес со старым именем), и СПульт по ключу создал бы дубль — тот же дефект, что исправлен в `UserRepository::updateProfile`.

Отдельный `rename` в волне 1 не вводится: ручное переименование вне области, а автонумерация выполняется внутри переноса. Метод без маршрута-потребителя считается спекулятивным и не добавляется.

## 5. Сервисы и распределение оркестрации

Правило: **транзакция живёт только в сервисе**. Чтение без транзакции координирует контроллер — это не доменная операция. Никакого `TreeService` не вводится: его работу делят `Support\AddressTree` (чистая логика) и контроллеры (вызовы репозиториев).

### 5.1 `Support\AddressTree` — чистые функции над строками

Зависимостей от БД нет. Обязан:

1. сортировать уровень через `Address::sortKey` с **обязательной** передачей `street_type` из справочника (без него «23-я линия» теряет «линию» и порядок расходится с клиентским ключом пикера);
2. собирать `display` через `Address::formatCity/formatStreet/formatHome/plain`;
3. собирать `path_display` через `Address::formatDisplay`;
4. нормализовать поисковую строку через `Address::plainKey`;
5. считать ключ уровня только вызовом владельца: `plainKey` для города и объекта, `homeKey` для дома, `streetKey` для улицы (ограничение — блокер B3).

Запрещено: SQL, обращения к сессии/HTTP, свой форматтер, своя нормализация, `ORDER BY` как источник итогового порядка.

### 5.2 `MoveService`

Зависимости: `CityRepositoryInterface`, `StreetRepositoryInterface`, `HomeRepositoryInterface`, `ObjectRepositoryInterface`, `AddressLogRepositoryInterface`, `AddressCacheService`, `DB`.

Три явных метода вместо диспетчеризации по типу:

| Метод                                                                       | Что переносит | Репозиторий цели            |
| --------------------------------------------------------------------------- | ------------- | --------------------------- |
| `objects(array $ids, int $targetHomeId, string $onDuplicate, Actor $actor)` | объекты в дом | `HomeRepositoryInterface`   |
| `homes(array $ids, int $targetStreetId, string $onDuplicate, Actor $actor)` | дома в улицу  | `StreetRepositoryInterface` |
| `streets(array $ids, int $targetCityId, string $onDuplicate, Actor $actor)` | улицы в город | `CityRepositoryInterface`   |

Общий приватный хелпер разрешения конфликта принимает исходное имя, **callable ключа уровня**, карту занятых ключей и лимиты длины — алгоритм автонумерации существует в одном экземпляре, различается только функция ключа.

Каждый метод обязан:

1. валидировать `ids` (непустой, целые > 0, дедупликация, верхний предел пачки) и `on_duplicate` из белого списка; тип из ввода не читается;
2. проверить существование цели через `lockForUpdate` репозитория цели и существование каждого переносимого узла через `findById` **до** записи;
3. выполнить всё в одной транзакции, начав с блокировки цели;
4. читать `occupiedKeys` цели и **дополнять карту** ключами уже обработанных узлов пачки;
5. при `on_duplicate=abort` и любом конфликте — откат и 409 без частичного применения;
6. при `rename` — автонумерация по контракту §8.3, проверка длин §8.4 для каждого кандидата, ограничение попыток;
7. писать `relocate` одним UPDATE (родитель + имя + ключ);
8. пропускать узлы, у которых родитель уже целевой (`same_parent`), не считая это ошибкой;
9. писать лог на каждый перемещённый узел;
10. звать `invalidateCache()` **внутри той же транзакции**;
11. возвращать `version` и `log_id`.

Запрещено: проверять цикл (иерархия строго 4-уровневая, цикл структурно невозможен), трогать `guid`/`spult_id`, менять `vis` без явного решения по скрытой цели (B6), дублировать проверку конфликта в контроллере.

### 5.3 `VisibilityService`

Зависимости: те же четыре репозитория, `AddressLogRepositoryInterface`, `AddressCacheService`, `DB`.

| Метод                                     | Каскад                         |
| ----------------------------------------- | ------------------------------ |
| `city(int $id, int $vis, Actor $actor)`   | город → улицы → дома → объекты |
| `street(int $id, int $vis, Actor $actor)` | улица → дома → объекты         |
| `home(int $id, int $vis, Actor $actor)`   | дом → объекты                  |

Порядок внутри транзакции: `lockForUpdate` узла → `listIdsBy*` по каждому нижнему уровню (без фильтра `vis`) → `setVis` узла → `setVisBy*` по уровням → лог с полным списком id → `invalidateCache()`.

Требования:

- `matched` = количество собранных id, `changed` = `rowCount`; ноль в `changed` не означает отказ;
- `preview` выполняет только чтение и ничего не пишет;
- симметричный каскад вниз, каскад вверх запрещён;
- один UPDATE на уровень, без батчей (объёмы подтверждены: максимум 7151 объект в тенанте);
- сбор id вместо отдельных `COUNT(*)` оправдан тем, что полный лог всё равно требует список id.

## 6. Транзакции и конкурентность

1. Транзакция открывается **в сервисе**, не в контроллере и не в репозитории.
2. `DB::transaction(callable)` передаёт `$this` в замыкание. Замыкание **не `static`**, если нужен `$this`: статическое не привязывает `$this` → `Error` в рантайме, `php -l` это не ловит.
3. Порядок внутри транзакции переноса: `lockParent` → чтение занятых ключей → запись узлов → лог → инкремент версии → коммит.
4. Инкремент версии — **в той же транзакции**: откат операции откатит и версию; после коммита версия гарантированно соответствует данным.
5. Optimistic locking по `timestamp` **не применяется**: у `lift_city` этой колонки нет, единого механизма не получится. Сериализация — `FOR UPDATE` по целевому родителю.
6. Конкурент-писатель `sp.php` активен (`XML_add = 1`) и в транзакцию модуля не входит. Единственная защита от его гонки — UNIQUE-индексы (блокер B2).
7. Дедлок/таймап ожидания лока — не «повторить молча», а разборный ответ и лог; автоматический ретрай в волне 1 не вводится.

## 7. Ключи: правила и блокирующая проблема

### 7.1 Правила вызова владельца

| Уровень | Вызов                                            | Что важно                                                                            |
| ------- | ------------------------------------------------ | ------------------------------------------------------------------------------------ |
| город   | `Address::parseCity` → `Address::plainKey(name)` | `plainKey` от строки с маркером даёт `гростов-на-дону` — не совпадёт со справочником |
| улица   | `Address::streetKey(raw)`                        | тип входит в ключ; при неразобранном типе ключ начинается с `\|`                     |
| дом     | `Address::homeKey(raw)`                          | маркер снимается только ведущий; корпус/дробь/литера сохраняются                     |
| объект  | `Address::plainKey(raw)`                         | `token()` снимает пробелы и точки: `п.1 пасс.` → `п1пасс`                            |

Ключ **не включает** id родителя → при переносе без переименования ключ не меняется, меняется область уникальности. Отсюда: **перенос без конфликта не требует пересчёта ключа вообще**.

### 7.2 Блокер B3 — пересчёт `street_key` из хранимых `(name, type)`

`Address::streetKey()` принимает **сырую строку** и разбирает её. Публичного метода «ключ из имени и типа» нет; `TYPES` и `aliasMap` — `private`.

Следствия, проверенные по исходнику `Address`:

- `streetKey($street_name)` для чистого имени даёт ключ **без типа** (`|ленина`), тогда как `sp.php` для «Ленина ул.» пишет `ул|ленина` → несовпадение;
- имя, заканчивающееся типовым словом («23-я линия»), при пустом `street_type` будет разобрано как тип + остаток — ключ уйдёт не туда;
- реконструкция `name . ' ' . type` корректна для канонических кодов (все 14 входят в собственные алиасы), но **не** для легаси-кодов вне словаря алиасов (например `пр` — сознательно исключён как неоднозначный).

Варианты решения:

- **(а)** добавить в `App\Support\Address` публичный `streetKeyFromParts(string $name, ?string $type): string`, переиспользующий `aliasMap`/`token` — **рекомендуется**: один владелец, никаких вторых словарей. Это правка трека А, отдельное решение;
- **(б)** реконструировать сырую строку в модуле — допустимо **только если** преflight докажет, что все `street_type` канонические, а строк с пустым типом и типовым словом в имени нет.

Решающие запросы:

```sql
SELECT street_type, COUNT(*) c FROM lift_street GROUP BY street_type ORDER BY c DESC;

SELECT COUNT(*) FROM lift_street WHERE street_type IS NULL OR TRIM(street_type) = '';

SELECT id, street_name, street_type, street_key FROM lift_street
 WHERE (street_type IS NULL OR TRIM(street_type) = '')
   AND street_name REGEXP '(линия|лин|шоссе|ш|проспект|переулок|площадь|бульвар|набережная|проезд|тупик|аллея|квартал|микрорайон|территория)$'
 LIMIT 50;

SELECT city_type, COUNT(*) c FROM lift_city GROUP BY city_type;
```

**До решения B3 перенос улицы с автонумерацией не реализуется.** Перенос улицы без конфликта — реализуется (ключ не меняется).

### 7.3 Согласованность хранимых ключей

Преflight из контракта §3.2 обязателен. Дополнительно — сверка ключа с именем для уровней, где пересчёт однозначен:

```sql
SELECT id, city_name, city_key FROM lift_city
 WHERE city_key <> LOWER(REPLACE(REPLACE(city_name, ' ', ''), '.', '')) LIMIT 50;

SELECT id, home_name, home_key FROM lift_home
 WHERE home_key <> LOWER(REPLACE(REPLACE(home_name, ' ', ''), '.', '')) LIMIT 50;

SELECT id, object_name, object_key FROM lift_object
 WHERE object_key <> LOWER(REPLACE(REPLACE(object_name, ' ', ''), '.', '')) LIMIT 50;
```

Оговорка: `LOWER()` в SQL и `mb_strtolower` в PHP могут расходиться на кириллице в зависимости от collation, а `parseHome` снимает ведущий маркер. Расхождения — повод для разбора, **не** для автоматического UPDATE.

## 8. Валидация

`sql_mode` без STRICT: MySQL молча режет строки и прижимает числа. PHP-проверка — единственная защита.

| Что                        | Правило                                      | Ошибка              |
| -------------------------- | -------------------------------------------- | ------------------- |
| `type`                     | `NodeType::tryFrom`, иначе отказ             | `validation_failed` |
| `id`, `target_id`, `ids[]` | приведение к `int`, `> 0`, дедупликация      | `validation_failed` |
| `ids` размер               | 上限 на пачку (например 500) с явным отказом | `validation_failed` |
| `on_duplicate`             | `abort\|rename`                              | `validation_failed` |
| `vis`                      | `0\|1`                                       | `validation_failed` |
| `city_name`                | ≤ 256 символов                               | `too_long`          |
| `street_name`              | ≤ 255                                        | `too_long`          |
| **`home_name`**            | **≤ 64**                                     | `too_long`          |
| `object_name`              | ≤ 255                                        | `too_long`          |
| любой `*_key`              | **≤ 190**                                    | `too_long`          |
| `street_type`              | ≤ 20                                         | `too_long`          |
| `city_type`                | ≤ 10                                         | `too_long`          |
| `q`                        | ≥ 2 символа после нормализации               | `validation_failed` |
| `limit`, `per_page`        | верхние границы (200 / 100)                  | `validation_failed` |
| `user_agent` в логе        | обрезка `mb_substr` до 255                   | —                   |

Проверка длины выполняется **для каждого кандидата автонумерации**, а не только для исходного имени: « (2)» добавляет 4 символа и на `home_name` это критично.

## 9. Ошибки

### 9.1 Транспорт

JSON-маршруты обязаны отвечать конвертом контракта §5.2 при **любом** исходе, включая отказ тенанта, отказ CSRF и непойманный `Throwable`. Текстовые `Tenant not resolved` / `Сервис временно недоступен` для AJAX недопустимы: фронт покажет «сбой сети» вместо причины.

Признак JSON-ожидания: заголовок `Accept: application/json` либо признак JSON-маршрута. Диагностика в лог сохраняется полностью: класс, message, файл:строка, page/action. Канал: `CompanyAddress: request failed`.

### 9.2 Маппинг ошибок БД

Возможен **только после закрытия долга №1** (`DbException` без `previous` → `getCode()=0`, `getPrevious()=null`).

| `errorInfo[1]` | Доменный ответ                    | Примечание                                       |
| -------------- | --------------------------------- | ------------------------------------------------ |
| 1062           | `duplicate_conflict` (409)        | конфликт UNIQUE; после B2 это штатный путь гонки |
| 1452           | `not_found` / `validation_failed` | нарушение FK: родитель не существует             |
| 1213 / 1205    | `internal_error` (500) + лог      | дедлок/таймап лока; авторетрай не вводим         |
| прочее         | `internal_error` (500) + лог      | наружу текст SQL не отдаём                       |

Коды 1062 подтверждены как достижимые (`uq_object_guid` уже ловится в `sp.php`). Остальные — **ожидание, подтвердить прогоном**, не выдавать за проверенный факт.

### 9.3 Запреты

Не глотать исключение ради «красивого ответа»; не подменять конфликт на успех; не отдавать наружу SQL, параметры, стек; не логировать секреты (адресных секретов нет, но `Logger::db` пишет все параметры — долг A4 остаётся открытым).

## 10. Лог и cron

Схема и полнота — контракт §10. Требования к реализации:

1. запись лога — **в той же транзакции**, что и изменение данных;
2. `actor_login` — снимок на момент действия, не JOIN при чтении;
3. перенос — запись на каждый узел; каскад — одна запись с полным списком id в `affected`;
4. `affected` — `LONGTEXT` + `json_encode` (`JSON_UNESCAPED_UNICODE`), **не** JSON-тип: в MariaDB его нет;
5. время — `CURRENT_TIMESTAMP`/`NOW()` в зоне MySQL, PHP-время в DATETIME не пишем;
6. чистка — cron-строкой в `md/cron`, 3 месяца; журнал СПульт (30 дней) не трогаем.

## 11. Требования к SQL

1. Никакой интерполяции ввода. Имена таблиц/колонок знает репозиторий сущности (константы класса), значения — только плейсхолдеры.
2. Каскадные UPDATE — многотабличные с JOIN по цепочке FK, один запрос на уровень.
3. Счётчики `matched` — отдельным `SELECT COUNT(*)` до записи; `changed` — из `rowCount`. Ноль в `changed` не означает failure.
4. Существование узла проверяется `findById` до UPDATE (иначе ноль строк не отличить от отсутствия записи).
5. `occupiedKeys` читает **всех** детей цели без фильтра `vis`.
6. Поиск — `LIKE` по `*_key` с нормализованной иглой, `LIMIT` на уровень.
7. Никаких `SELECT *` в ответах наружу: только поля контракта.
8. Индексы: после B2 сверить `SHOW INDEX` и удалить только полностью покрытые неуникальные (прецедент миграции 1.7). Остальные не трогать.
