Запреты не произвольны: . и - — части имён («Ростов-на-Дону», «пр-кт»), / — номер дома («20/1»), , и ; — разделители display-подписи, причём запятая встречается внутри имени лифта («п.1, пасс.»), № — маркер дома в Address::parseHome.
Два барьера проверки:
Панель при сохранении — значение вне словаря отвергается с подсказкой, список показывается селектом, не свободным вводом.
sp.php при чтении — OptionGuard::separator(): пусто, пробел, многосимвольное значение, массив или символ вне словаря → #. Молча, но панель обязана показывать фактическое значение, а не сохранённое.
Смена разделителя не исправляет уже созданные строки справочника и требует перепроверки city_default: значение, которое раньше делилось корректно, после смены может перестать.

Почему не одна строка с разделителем (пос.|Верхнетемерницкий): кода пос в словаре нет — есть п. formatCity не выведет тип из «пос.», CITY_TYPES['пос'] отсутствует → подпись станет «н.п. Верхнетемерницкий». Селект из словаря исключает такие значения физически.
Правила:
Маркер типа в city_default не хранится никогда. Address::plain() его не снимает — он нормализует только пробелы, поэтому грязное значение уедет в city_name и в city_key.
city_default не должен содержать символ city_separator — кросс-проверка при сохранении.
Код типа вне словаря панель отвергает.
Миграция существующего значения: разово разделить "г. Ростов-на-Дону" → city_default = "Ростов-на-Дону", city_default_type = "г". Выполнять только после проверки guid-пути: Address::format() считает «г.» частью значения города, и изменение представления может дать guid_mismatch на каждом сигнале.
1.3. Известная ловушка данных
lift_city.city_type имеет DEFAULT 'г'. Ветка города в sp.php колонку не пишет — для посёлка, села, хутора тип окажется неверным. Ветка улиц street_type пишет. Асимметрия подлежит устранению вместе с передачей city_default_type в INSERT.

## 1. Настройки тенанта — таблица `lift_options`

Значения задаются вручную через БД или будущую админ-панель. Ключи:

| Ключ                      | Обяз. | Назначение                                                                 | Пример                             |
| ------------------------- | ----- | -------------------------------------------------------------------------- | ---------------------------------- |
| `spult_organization_name` | ✅    | Сверка с `PULT@Name`. Несовпадение → сигнал в карантин                     | `lifter3`                          |
| `city_default`            | ✅    | Город, если в `STREET@Name` нет разделителя                                | `г. Ростов-на-Дону`                |
| `city_separator`          | ✅    | Разделитель «улица#город»                                                  | `#`                                |
| `XML_add`                 | ✅    | `1` = автосоздание города/улицы/дома/лифта, `0` = запрет                   | `0`                                |
| `spult_pult_guid`         | ❌    | Ожидаемый `PULT@GUID`. Используется только при включённом флаге проверки   | `5A988C5A74DE41B39CBB5DBB1B836BDE` |
| `admin_email`             | ❌    | Email админа организации для оповещений о сбоях. Несколько — через запятую | `admin@org.ru`                     |
| `org_key`                 | ❌    | Ключ организации для быстрого входа (волна B4). Пустой = функция выключена | `XXXX-XXXX-XXXX`                   |

**Правило `XML_add = 0`:** никаких автосозданных адресов. Нераспознанный сигнал
уходит в карантин, справочник не засоряется. Решение согласовано.

## 3. Каталоги на диске

Все вне web-root. Права `0750`, владелец — пользователь PHP.

| Путь                         | Назначение                                                |
| ---------------------------- | --------------------------------------------------------- |
| `domains/_spult/incoming/`   | Сырой XML создаётся здесь **до любого разбора**           |
| `domains/_spult/processed/`  | Обработан: заявка создана или заметка добавлена           |
| `domains/_spult/failed/`     | Вина сервера (БД, фатал). Ручной разбор, автоповторов нет |
| `domains/_spult/quarantine/` | Вина данных (адрес, организация, XML). Нужен человек      |
| `domains/_alerts/`           | Метки троттлинга email                                    |
| `domains/_cron/`             | Скрипт чистки                                             |

Рядом с файлом в `failed`/`quarantine` лежит `<имя>.xml.meta.json` с причиной,
распознанными id и адресом — чтобы разбор не был слепым.

**Имя файла уникальное** (`Ymd_His` + uniqid + случайный суффикс). Прежний
`date('Y-m-d_H-i-s')` давал коллизию: два сигнала в одну секунду затирали друг друга.

**Фолбэк:** если `_spult` недоступен для записи, используется
`uploads/spult-xml/` внутри web-root. Обязательно закрыть от HTTP:

```apache
# uploads/spult-xml/.htaccess
Require all denied
```

В XML ФИО операторов и адреса — публичного доступа быть не должно.

## 4. Cron

Вызов **явно через php8.4**: в CLI хостинга по умолчанию 8.1, а код использует
конструкции 8.3+ (типизированные константы класса, readonly-классы). Под 8.1
`bootstrap.php` упадёт на этапе парсинга.

```
15 3 * * * /usr/bin/php8.4 /home/users/z/zamotaev/domains/_cron/cron_cleanup.php
```

Защита: `if (PHP_SAPI !== 'cli') exit;` — секретный токен не нужен, файл вне web-root.

Чистка пакетно `LIMIT 1000` в цикле, по каждому тенанту отдельно,
ошибка одного тенанта не прерывает обход:

| Таблица                   | Условие удаления                       |
| ------------------------- | -------------------------------------- |
| `offline_command_log`     | `created_at < NOW() - INTERVAL 7 DAY`  |
| `offline_sync_log`        | `created_at < NOW() - INTERVAL 30 DAY` |
| `offline_actions_archive` | `created_at < NOW() - INTERVAL 30 DAY` |
| `spult_events`            | `created_at < NOW() - INTERVAL 30 DAY` |
| `lift_access_tokens`      | `expires_at < NOW()`                   |
| `lift_refresh_tokens`     | `expires_at < NOW()`                   |

**Повторов `failed/` нет** — решение согласовано. Папки `failed` и `quarantine`
разбираются вручную через админ-панель.

EVENT `cleanup_offline_tables` в БД оставлен, но неактивен (`event_scheduler` выключен).

## 5. Схема БД — что добавлено

### `lift_object`

| Колонка            | Тип                         | Индекс     | Назначение                                                                      |
| ------------------ | --------------------------- | ---------- | ------------------------------------------------------------------------------- |
| `guid`             | `char(32)` ascii, NULL      | **UNIQUE** | `LIFT@GUID`. Первичный ключ поиска объекта                                      |
| `spult_id`         | `varchar(32)` NULL          | KEY        | `LIFT@ID`. Для сверки и будущего импорта                                        |
| `abbreviated_name` | `varchar(255)` DEFAULT `''` | —          | Было `mediumint(6)`. Освобождено под будущее текстовое описание лифта из СПульт |

Для непривязанных объектов — строго `NULL`, не пустая строка.

### `spult_events`

Журнал событий интеграции. Append-only, TTL 30 дней.
Поля: `kind`, `lift_id`, `ticket_id`, `guid`, `spult_id`, `xml_address`,
`db_address`, `message`, `spool_file`, `meta` (JSON).

## 6. Словарь событий и префиксы истории

### `spult_events.kind`

| kind                    | Смысл                                                                | Заявка создана | Severity     |
| ----------------------- | -------------------------------------------------------------------- | -------------- | ------------ |
| `guid_mismatch`         | GUID найден, адрес в XML отличается. Заявка на объект по GUID        | ✅             | warning      |
| `guid_conflict`         | Адрес совпал, но у объекта уже **другой** GUID. Привязка не изменена | ✅             | **critical** |
| `spult_id_conflict`     | `LIFT@ID` отличается от сохранённого. Не перезаписан                 | ✅             | info         |
| `address_unresolved`    | Адрес не собран, `XML_add = 0`                                       | ❌             | **critical** |
| `org_mismatch`          | `PULT@Name` не совпал с настройкой                                   | ❌             | **critical** |
| `pult_guid_mismatch`    | `PULT@GUID` не совпал (проверка включена)                            | ❌             | **critical** |
| `bad_xml`               | XML не распарсился                                                   | ❌             | warning      |
| `duplicate_note_failed` | Дубликат найден, заметка не легла (сбой БД)                          | ❌             | **critical** |
| `fatal`                 | Системный сбой: БД, тенант, исключение                               | ❌             | **critical** |

### Префиксы в `lift_history`

Машинночитаемые маркеры для фильтрации панелью. Пишутся только когда заявка
существует — у карантина заявки нет, там только запись в `spult_events`.

| Префикс                 | Когда                                                   |
| ----------------------- | ------------------------------------------------------- |
| `[SPult:guid_mismatch]` | Адрес в сигнале отличается от адреса объекта в БД       |
| `[SPult:guid_conflict]` | У объекта другой GUID, привязка не изменена             |
| `[SPult:info_status]`   | Информационные статусы пульта, не включённые в описание |

### Префикс описания заявки

В описание **всегда** добавляется `Создана из SPult. <остаток>`.
При пустом остатке — просто `Создана из SPult`. Это гарантирует непустое
описание и снимает отдельную проверку длины.

Словарь исключений — `config/spult.php`. Стартовый состав:
`Кабина стоит`, `Нет связи`, `Кабина в движении`. Сравнение точное после
нормализации (trim, нижний регистр, схлопывание пробелов), не по подстроке.
Отфильтрованные статусы сохраняются в историю с префиксом `[SPult:info_status]`.

## 7. Email-оповещения

Канал: `App/Support/AdminAlert.php`. **Не зависит от БД** — падение БД является
поводом для письма, поэтому адрес берётся из константы, троттлинг файловый.

| Событие               | Когда                                     |
| --------------------- | ----------------------------------------- |
| `spult_signal_lost`   | Сигнал ушёл в `quarantine/` или `failed/` |
| `spult_guid_conflict` | Конфликт привязки GUID                    |
| `spult_guid_mismatch` | Расхождение адреса при найденном GUID     |
| `api_fatal`           | Любой `internal_error` в `api.php`        |
| `auth_fatal`          | То же в `auth.php`                        |
| `cron_tenant_failed`  | Тенант не обработан cron'ом               |

Троттлинг: одно письмо на одинаковую причину раз в **15 минут**, потолок
**20 писем/час**. Подпись включает тенант и причину — сбой одного тенанта
не подавляет такой же сбой другого. Проверка и установка метки под `flock`.

Расхождение адреса троттлится **по тенанту, не по лифту**: при переименовании
улицы в пульте иначе придёт письмо на каждый лифт. Детали по каждой заявке —
в истории и в `spult_events`.

Бизнес-ошибки (валидация, дубликаты, права) **не почтуются** — это нормальная работа.

## 8. Уведомления в SPA

Событие `spult_error` в ленте `notifications` — чтобы открытая вкладка
диспетчера увидела необработанный сигнал. Параметры: `actor_id: 0` (система,
никогда не отфильтруется как «своё действие»), `sound: true`, `timeout: 0`.

Каналы дополняют друг друга: вкладка открыта → событие в ленте; закрыта → письмо админу.

**Требование к фронтенду:** внести `spult_error` в словарь `notifications-poller.js`.
Неизвестные типы клиент отбрасывает — без правки событие дойдёт до браузера
и будет проигнорировано. Там же висит расхождение `ticket_note` / `note_added`.

## 9. Инварианты приёма СПульт

1. **Непустое тело запроса → всегда HTTP 200.** Пульт не разбирает ответ
   и не ретраит: любой другой код = безвозвратно потерянный сигнал.
   Исключения: не-POST (405) и пустое тело (400) — сигнала нет, терять нечего.
2. Сырой XML сохраняется **до** разбора, имя уникальное.
   3ate. GUID первичен: найден объект по GUID → заявка на него **вне зависимости от адреса**.
3. Привязка GUID только если поле пустое либо в INSERT нового объекта.
   Чужая привязка не перезаписывается никогда.
4. `XML_add = 0` → никаких автосозданных адресов.
5. Короткое описание не отклоняется — дополняется префиксом.
6. Дубликат → заметка в существующую заявку, не отказ.

| Экран                | Источник данных                                   | Действия                                           |
| -------------------- | ------------------------------------------------- | -------------------------------------------------- |

## 12. Приёмка

- [ ] Обычный сигнал → 200, заявка создана, файл в `processed/`
- [ ] Повтор по тому же объекту+отделу → 200, заметка в существующей заявке
- [ ] Пустой `ListStatus` и `Note` → 200, описание `Создана из SPult`, не отказ
- [ ] Незнакомый лифт при `XML_add = 0` → 200, `quarantine/`, запись в `spult_events`
- [ ] Первый сигнал привязанного лифта → `guid` заполнен, `spult_id` заполнен
- [ ] GUID найден, адрес в XML другой → заявка на объект по GUID, префикс в истории, письмо
- [ ] Адрес совпал, у объекта другой GUID → привязка не изменена, событие `guid_conflict`, письмо
- [ ] Опечатка в организации → 200, `quarantine/org_mismatch`, письмо
- [ ] Битый XML → 200, `quarantine/bad_xml`, байты сохранены
- [ ] Остановить MySQL, отправить сигнал → 200, `failed/fatal`, письмо на адрес из константы
- [ ] Два сигнала в одну секунду → два разных файла
- [ ] `curl -I` на файл спула → 403
- [ ] Cron обходит все тенанты, логирует объёмы, продолжает при ошибке одного

## Раздел: Быстрый вход диспетчера по ключу организации

### Назначение

Диспетчер на общем рабочем месте выбирает себя из списка и вводит только пароль — без набора логина. Список открывается по **ключу организации**, который админ сообщает сотрудникам голосом или на бумаге.

Обычный вход по логину и паролю **сохраняется полностью**. Быстрый вход — дополнительный путь, не замена.

### Название организации

Читается из тенанта по поддомену и **не требует ключа**. Экран входа показывает название до всякого ввода. Домен и так идентифицирует организацию — гейтить название проверкой нечего.

### Два публичных действия

Оба работают **без bearer-токена**: экран входа токена не имеет.

| Действие        | Вход                            | Ответ (под `data`)               |
| --------------- | ------------------------------- | -------------------------------- |
| `check_org_key` | `org_key` (можно не передавать) | `{enabled, valid, org_name}`     |
| `get_org_users` | `org_key` обязателен            | `{org_name, users:[{id, name}]}` |

**Порядок на фронте:**

1. Открытие экрана → `check_org_key` **без ключа** → рисует название, по `enabled` решает, показывать ли поле ключа.
2. Ввод ключа → повторный `check_org_key` → `valid`.
3. Подтверждение → `get_org_users` → список.
4. Выбор сотрудника → `loginById(user_id, password)`.

Информационный вызов без ключа **не считается попыткой подбора**: ни лимит, ни счётчик отказов не трогаются. Иначе открытие экрана входа копило бы блокировку на добросовестного диспетчера.

### Исходы

| Ситуация                              | Ответ                                                                                                 |
| ------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| Ключ в настройках пуст                | `check_org_key` → `enabled:false`; `get_org_users` → `forbidden`, `reason: org_key_disabled`          |
| Ключ не передан, функция включена     | `enabled:true, valid:false`                                                                           |
| Ключ неверный                         | `check_org_key` → `valid:false` (не ошибка); `get_org_users` → `forbidden`, `reason: invalid_org_key` |
| Превышен лимит попыток                | `rate_limited`, `details.retry_after` в секундах                                                      |
| Ключ верный, сотрудников с флагом нет | `users: []` — не ошибка                                                                               |

### Что отдаётся в списке

Только `id` и `name`. Эндпоинт публичный, список ФИО — персональные данные за секретом, расширять утечку нечем.

| Поле                       | Отдаётся | Почему                                      |
| -------------------------- | -------- | ------------------------------------------- |
| `id`                       | ✅       | нужен для `loginById`                       |
| `name`                     | ✅       | собранное ФИО (`user_name`)                 |
| `user_login`               | ❌       | половина учётных данных                     |
| `user_phone`, `user_email` | ❌       | ПД, для входа не нужны                      |
| `role`, `position`         | ❌       | показывает, кто админ — мишень для перебора |

Пустое `user_name` собирается из `user_surname` + `user_firstname`, при полностью пустых полях — `Сотрудник №N`. Пустая кнопка невыбираема, а молча выкинуть человека из списка значит закрыть ему вход без объяснений.

### Ключ организации

| Параметр        | Значение                                                           |
| --------------- | ------------------------------------------------------------------ |
| Хранение        | `lift_options`, строка `org_key`, колонка `option_value`           |
| Формат          | `XXXX-XXXX-XXXX`                                                   |
| Алфавит         | `ABCDEFGHJKLMNPQRSTUVWXYZ23456789` — 32 символа, без `0/O` и `1/I` |
| Энтропия        | ≈ 10¹⁸ комбинаций                                                  |
| Пустое значение | функция выключена                                                  |
| Сравнение       | `hash_equals`, timing-safe                                         |

**Нормализация с обеих сторон:** верхний регистр, удаление разделителей и пробелов, подмена кириллических двойников (`А→A`, `В→B`, `С→C`, `Е→E`, `Н→H`, `К→K`, `М→M`, `Р→P`, `Т→T`, `У→Y`, `Х→X`).

Диспетчер на русской раскладке набирает визуально тот же ключ. Без подмены `hash_equals` вернёт `false` на правильном ключе, и разобрать обращение невозможно — строки выглядят идентично.

**Хранится открыто, не хэшем:** админ должен иметь возможность прочитать ключ и продиктовать его. Хэш сделал бы это невозможным.

### Ограничение перебора

Публичный эндпоинт без лимита = перебор ключа. Здесь лимит — часть функциональности, а не отложенное улучшение.

| Параметр                   | Значение                                    |
| -------------------------- | ------------------------------------------- |
| Порог                      | 5 неудачных попыток                         |
| Окно                       | 15 минут (от первой неудачи, не скользящее) |
| Ключ счётчика              | тенант + `REMOTE_ADDR`                      |
| Состояние                  | файловое, `domains/_orgkey/`, вне web-root  |
| Успех                      | счётчик сбрасывается                        |
| Пустой / сверхдлинный ввод | попыткой не считается                       |

`X-Forwarded-For` не используется: заголовок подделывается, и лимит обходился бы одной строкой в запросе.

Окно от первой неудачи, а не скользящее: скользящее атакующий обходит растяжением попыток.

**При недоступном каталоге состояния** — фолбэк во временную папку, при её отказе лимит отключается с уведомлением админу, но вход **не блокируется**. Компромисс осознанный: энтропия ключа делает перебор непрактичным и без лимита, а fail-closed обесточил бы вход всем диспетчерам из-за прав на папку.

### Каталог состояния

```
/home/users/z/zamotaev/domains/_orgkey/
```

Создать вручную, права `0750`, владелец — пользователь PHP (как `_alerts` и `_spult`). Файлы накапливаются, чистятся cron'ом.

## Раздел: Правило для админки тенанта — `allow_dispatcher_quick_login`

### Критерий включения в список

**Единственный критерий — флаг `allow_dispatcher_quick_login = 1`.** Роль и должность на выборку **не влияют**: флаг выставляет админ, он же решает, кто в списке. Дублирующий фильтр по роли обесценил бы флаг для нестандартных должностей и для прораба, нормализованного в `dispatcher`.

### Значение по умолчанию при создании пользователя

| Позиция (`user_position`)                                                               | Флаг по умолчанию |
| --------------------------------------------------------------------------------------- | ----------------- |
| `dispatcher`                                                                            | **1**             |
| `admin`, `foreman`, `mechanic`, `signalman`, `electronic-engineer`, `director`, `guest` | 0                 |
| не задана / пустая                                                                      | 0                 |

В БД `DEFAULT 0` — новый пользователь не попадает в список молча, каким бы путём его ни создали (новый UI, легаси-админка, SQL).

**Следствие:** диспетчер, добавленный через легаси-админку без указания флага, в список не попадёт, пока флаг не выставят вручную. Это соответствует правилу, но об этом надо знать при разборе обращений.

### Поведение при редактировании

**Флаг автоматически не меняется при смене должности.** Правило «dispatcher → 1» относится к **созданию**. При редактировании:

- флаг остаётся таким, каким его выставил админ;
- UI показывает чекбокс и подсказку, если должность диспетчерская, а флаг снят.

Причина: автопереключение при каждом сохранении затирало бы осознанное решение админа — например, временно исключить сотрудника из списка, не меняя должность.

### Исключения из списка (независимо от флага)

| Условие                                | Почему                       |
| -------------------------------------- | ---------------------------- |
| `user_block <> 1`                      | заблокированный не войдёт    |
| `user_password <> ''`                  | без пароля вход невозможен   |
| `user_hiden IS NULL OR user_hiden = 0` | скрытые записи не показываем |

`user_hiden` — nullable. Условие `user_hiden = 0` без проверки `IS NULL` отсекло бы все записи, созданные без явного значения, и список оказался бы пустым при корректных флагах.

Порядок: `ORDER BY user_name, user_id`. Второй ключ — против «прыгающего» списка при одинаковых ФИО.

### Выравнивание существующих записей

До смены `DEFAULT` все пользователи получили флаг `1`. Разовое выравнивание обязательно, иначе список покажет весь штат. SQL — в миграции org-key; снимок флагов сохраняется в `_bak_quick_login_flags`, потому что отличить ручную установку от наследия `DEFAULT 1` в данных невозможно.

## Раздел: Управление ключом (пока через SQL)

Админ-UI для ключа и флага **не реализован**. До его появления — прямые запросы в БД тенанта.

### Строка настройки

| Колонка          | Значение                                   |
| ---------------- | ------------------------------------------ |
| `option_name`    | `org_key`                                  |
| `option_value`   | ключ или пусто                             |
| `name`           | `Ключ организации`                         |
| `type`           | `text`                                     |
| `change_allowed` | `1` — админ тенанта сможет менять через UI |

### Генерация

```bash
/usr/bin/php8.4 -r 'define("APP_ENTRY_POINT", true); require "/home/users/z/zamotaev/domains/liftcs.ru/bootstrap.php"; echo App\Support\OrgKeyGuard::generate(), PHP_EOL;'
```

### Ротация

Обновляется **новейшая** строка по `id`. В `lift_options` индекс по `option_name` — обычный `KEY`, не `UNIQUE`, поэтому дубли возможны: `OrgLoginService` читает новейшую, и обновление произвольной строки дало бы «ключ работает через раз».

Ротация **не рвёт активные сессии**: ключ используется только для входа, выданные токены от него не зависят.

### Выключение

Очистить `option_value` новейшей строки. Поиск «первого непустого среди дублей» включил бы функцию обратно против воли админа — поэтому значение берётся строго из новейшей строки.

## Раздел: Диагностика отказов быстрого входа

| Симптом                              | Причина                                              | Проверка                                                                             |
| ------------------------------------ | ---------------------------------------------------- | ------------------------------------------------------------------------------------ |
| Поле ключа не показывается           | `org_key` пуст или строки нет                        | `SELECT option_value FROM lift_options WHERE option_name='org_key' ORDER BY id DESC` |
| Ключ верный, но `valid:false`        | дубль строки, читается новейшая                      | тот же запрос — сколько строк                                                        |
| Список пуст при верном ключе         | ни у кого флаг не выставлен                          | `SELECT ... WHERE allow_dispatcher_quick_login=1`                                    |
| В списке весь штат                   | выравнивание не выполнено                            | миграция org-key, шаг 1                                                              |
| Диспетчера нет в списке              | `user_block`, `user_hiden`, пустой пароль или флаг 0 | проверить все четыре поля                                                            |
| `rate_limited` на верном ключе       | 5 неудач с этого IP за 15 минут                      | удалить файл состояния в `_orgkey`                                                   |
| `internal_error` вместо отказа ключа | `org_key` пришёл массивом                            | клиент должен слать строку                                                           |
| Ключ не подходит у одного сотрудника | кириллическая раскладка                              | нормализация покрывает; проверить, что `OrgKeyGuard` применён                        |
