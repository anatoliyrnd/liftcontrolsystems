## Блок A. Версии справочников

### A-1 (P1). Разделить счётчик заявок на два ключа

**Сейчас.** `lift_dict_versions` содержит строку `tickets` (сид в `md/sqlupdate.txt`). `AddressCacheService::getVersions()` возвращает ключи `staff`, `dicts`, `addresses`, `tickets`. Единственный метод `invalidateTickets()` вызывается из `callnew`, `calledit`, `callClose`, `callnote`.

Фронтенд отправляет в `versions` ключ `open_tickets`. Сервер в `getOutdated()` сравнивает свой `tickets` с `$clientVersions['tickets'] ?? 0`, то есть всегда с нулём. Результат: `outdated` содержит `tickets` в **каждом** ответе, независимо от того, менялись ли данные.

**Следствие.** Клиент вынужден перезапрашивать полный список открытых заявок каждые 120 секунд при любом состоянии данных. Дельта-синхронизация не работает.

Дополнительно: комментарий в `getOutdated()` утверждает «Здесь уже лежит 'open_tickets'» — это не соответствует коду, переименования нигде нет.

**Требуется.**

1. Добавить в `lift_dict_versions` две строки:
   - `('open_tickets', <текущее значение tickets>, UNIX_TIMESTAMP())`
   - `('closed_tickets', 1, UNIX_TIMESTAMP())`
2. В `getVersions()` инициализировать массив обоими ключами со значением 0, чтобы они присутствовали в ответе даже до первого инкремента.
3. Добавить методы `invalidateOpenTickets()` и `invalidateClosedTickets()` по образцу существующих.
4. Строку `tickets` **оставить** в таблице неиспользуемой. Не удалять — это позволит откатиться без восстановления данных. Удаление отдельной миграцией позже.
5. Исправить комментарий в `getOutdated()`.

**Критерий приёмки.** Ответ `data: "notifications"` содержит `versions` с ключами `staff`, `dicts`, `addresses`, `open_tickets`, `closed_tickets`. При повторном запросе с актуальными версиями клиента массив `outdated` **пуст**.

### A-2 (P1). Расставить инкременты по матрице

**Требуется.** Заменить все вызовы `invalidateTickets()` в `CallService` согласно таблице:

| Метод       | Условие                                            | Инкремент                                  |
| ----------- | -------------------------------------------------- | ------------------------------------------ |
| `callnew`   | `$callStatus === 0`                                | `open_tickets`                             |
| `callnew`   | `$callStatus === 1` (офлайн-заявка сразу закрытая) | `closed_tickets`                           |
| `calledit`  | есть фактические изменения (`!empty($fields)`)     | `open_tickets`                             |
| `callnote`  | всегда                                             | `open_tickets`                             |
| `callClose` | всегда                                             | **оба**: `open_tickets` + `closed_tickets` |

Обоснование для `callClose`: заявка одновременно уходит из открытых и появляется в закрытых, оба слоя устаревают.

В `ApiController::handleSyncCommands` инкремент уже стоит строго после `$this->db->commit()` — это свойство сохранить. При наличии в пачке закрытий инкрементить оба ключа.

**Критерий приёмки.** После закрытия заявки обе версии увеличились на 1. После добавления комментария — только `open_tickets`. Инкремент не происходит, если транзакция откатилась.

## Блок B. Контракт syncCommands

### B-1 (P1). Зафиксировать и защитить полноту `results`

**Сейчас.** Код уже обеспечивает полноту: `processSingleSyncCommand` вызывается в цикле по всем командам, и каждая ветка (успех, `archived`, `failed`, `duplicate_detected`, `missing_ticket_id`, идемпотентный `ignored`) добавляет ровно один элемент в `context['results']`. Исключение наверх уходит только при системном сбое всей пачки — тогда транзакция откатывается и возвращается `status: error`.

**Проблема не в коде, а в отсутствии гарантии.** Фронтенд вынужден был ввести эвристику «если очередь не уменьшилась — принудительно удалить проблемные команды», которая уничтожает пользовательские данные в штатной ситуации (например, когда вся пачка получила `failed` из-за временной проблемы БД). Эвристика убирается, но для этого нужна зафиксированная гарантия.

**Требуется.**

1. Внести в `API_syncCommands.md` явный контракт: «На каждую отправленную команду возвращается ровно один элемент `results` с тем же `command_uuid`. Единственное исключение — `status: "error"` верхнего уровня, когда пачка отклонена целиком; в этом случае `results` отсутствует и ни одна команда не выполнена».
2. Добавить проверку перед формированием ответа: количество `results` равно количеству входных `commands`, множества `command_uuid` совпадают. При расхождении — логировать с `batch_id` и составом обеих множеств. Это защита от будущих регрессий, не исправление текущего бага.
3. Проверить, что кэш идемпотентности `offline_sync_log.response_payload` тоже содержит полный набор при повторном запросе того же `batch_id`. Он сохраняется из того же `$context`, поэтому должен быть корректен — нужна проверка тестом.

**Критерий приёмки.** Тест: пачка из 20 команд, где часть успешна, часть архивирована, часть `failed`, часть `duplicate_detected` — сумма элементов `results` равна 20, uuid совпадают с отправленными. Повторный запрос с тем же `batch_id` возвращает идентичный набор.

### B-2 (P2). Привести два кода `reason` к протоколу

**Сейчас.** `ApiController::mapErrorCodeToReason()` возвращает:

| Код                       | Возвращает         | Протокол ожидает        | Статус         |
| ------------------------- | ------------------ | ----------------------- | -------------- |
| `ErrorCode::Forbidden`    | `no_rights`        | `no_rights`             | ✅ совпадает   |
| `ErrorCode::InvalidInput` | `validation_error` | `validation_error`      | ✅ совпадает   |
| `ErrorCode::NotFound`     | `not_found`        | `ticket_not_found`      | ❌ расхождение |
| `ErrorCode::Closed`       | `ticket_closed`    | `ticket_already_closed` | ❌ расхождение |
| `ErrorCode::MissingToken` | `auth_error`       | нет в протоколе         | ⚠️ определить  |
| default                   | `unknown_error`    | нет в протоколе         | ⚠️ определить  |

**Следствие.** Фронтенд в `_buildArchivedMessage()` ищет перевод по ключу из протокола. Для `not_found` и `ticket_closed` перевод не находится, и диспетчер видит сырой код вместо понятного текста: «Действие отброшено: ticket_closed» вместо «заявка уже закрыта».

**Требуется.** Переименовать два возвращаемых значения: `not_found` → `ticket_not_found`, `ticket_closed` → `ticket_already_closed`. Для `auth_error` и `unknown_error` — либо добавить в протокол, либо маппить в существующие коды.

Объём: ~5 строк.

**Критерий приёмки.** Закрытие уже закрытой заявки через `syncCommands` возвращает `reason: "ticket_already_closed"`.

## Блок C. Проверка прав в online-пути

### C-1 (P2, безопасность). Отсутствует серверная проверка прав для online-действий

**Сейчас.** Проверка ролей реализована только в `ApiController::checkCommandPermissions()` и вызывается **исключительно** из `processSingleSyncCommand`, то есть только для офлайн-пачки.

Методы `CallService::callnew`, `calledit`, `callClose`, `callnote` при вызове из online-пути (`ApiController::handle()` → напрямую `$this->callService->...`) проверяют только:

- наличие и формат `call_id`,
- длину `solution` / `details` / `note`,
- существование заявки,
- не закрыта ли она.

**Проверки роли и назначенности нет.** Пользователь с ролью `guest` или `engineer`, не назначенный на заявку, может закрыть её, отправив POST-запрос напрямую, минуя UI.

Фронтенд гейтит кнопки через `userStore.can()` и поля `can_edit` / `can_close` / `can_comment`, но это клиентская проверка — она не является защитой.

**Требуется.** Вынести проверку прав в общий слой, применяемый одинаково к online и offline путям. Варианты:

- приватный метод `assertPermission(array $user, string $action, array $call)` в `CallService`, вызываемый в начале каждого из четырёх методов;
- либо отдельный `CallPolicy`, как упоминается в `API_syncCommands.md` §2.2 («`CallPolicy::can{Action}($user, $payload)`» — судя по документу, планировался, но в коде не обнаружен).

Матрица прав — из `API_syncCommands.md` §2.2:

| Роль          | CreateTicket | EditTicket | CloseTicket | AddComment  |
| ------------- | :----------: | :--------: | :---------: | :---------: |
| administrator |      ✅      |     ✅     |     ✅      |     ✅      |
| dispatcher    |      ✅      |     ✅     |     ✅      |     ✅      |
| engineer      |      ❌      |     ❌     | только свои | только свои |
| guest         |      ❌      |     ❌     |     ❌      |     ❌      |

При отказе — `ApiException(ErrorCode::Forbidden)`. В online-пути это даст клиенту `status: error` с кодом, в offline — `archived` с `reason: no_rights` (уже работает).

**Критерий приёмки.** Прямой POST `action: "callClose"` от пользователя `guest` возвращает ошибку прав, заявка не закрыта. То же для `engineer` на чужой заявке. Поведение offline-пути не изменилось.

### C-2 (P2). Расхождение вычисляемых `can_*` с матрицей прав

**Сейчас.** `CallRepository::findByIdDetailed()` вычисляет:

```
$canEdit  = $isOpen && ($readAll || $isAssigned);
$canClose = $isOpen && (role admin || dispatcher || engineer || $isAssigned);
```

Два несоответствия:

1. `$canClose` разрешает закрытие **любому** `engineer`, независимо от назначенности. Матрица.protocol и `userStore.can('close_ticket')` на фронте требуют `isAssigned` для engineer.
2. `$canEdit` разрешает редактирование назначенному `engineer`, тогда как матрица запрещает `EditTicket` для engineer полностью. `checkCommandPermissions` в offline-пути его отклонит.

Итог: карточка показывает кнопку, действие отклоняется. Для online — наоборот, действие пройдёт (см. C-1), хотя не должно.

Также: `closureallowed` в `findByIdDetailed` захардкожен в `0`, тогда как в списках `formatList` это поле вообще не отдаётся. Фронтенд использует его как fallback — сейчас fallback всегда ложен.

**Требуется.** Привести вычисление `can_*` в соответствие с матрицей C-1, использовать ту же логику, что и в проверке прав (один источник истины). Определить судьбу `closureallowed`: либо отдавать осмысленно, либо удалить из протокола и с фронта.

**Критерий приёмки.** Для engineer, не назначенного на заявку, `can_close: false` и `can_edit: false`. Кнопки в карточке не отображаются, прямой запрос отклоняется.

## Блок D. Уведомления

### D-1 (P2). Отсутствует `actor_id` — клиенты получают тосты о своих же действиях

**Сейчас.** `NotificationsService::getSince()` выполняет:

```sql
SELECT id, event_type, ticket_id, text, sound, timeout
FROM lift_notifications WHERE id > :since_id ...
```

Колонка `user_id` **не выбирается**. Протокол `API_PROTOCOL.md` §10 документирует поле `actor_id` как обязательное.

Фронтенд фильтрует собственные события:

```
events.filter(ev => ev.actor_id !== myId)
```

Поскольку `actor_id` всегда `undefined`, условие всегда истинно — фильтрация не работает.

**Следствие.** Диспетчер, закрывший заявку, через до 120 секунд получает тост «Заявка №… закрыта» о собственном действии. При активной работе это поток ложных уведомлений, включая звуковые (`sound: 1` у `ticketCreated`).

**Требуется.** Добавить в SELECT алиас `user_id AS actor_id`. Также добавить `created_at` — он документирован в протоколе, но не отдаётся.

**Критерий приёмки.** Ответ содержит `actor_id` с ID автора события. Пользователь не получает тостов о своих действиях.

### D-2 (P3). Расхождение `event_type` с протоколом

**Сейчас.** `NotificationsService` генерирует типы:

| Метод           | `event_type`     | Есть в протоколе?     | Есть в маппинге фронта? |
| --------------- | ---------------- | --------------------- | ----------------------- |
| `ticketCreated` | `ticket_created` | ✅                    | ✅                      |
| `ticketClosed`  | `ticket_closed`  | ✅                    | ✅                      |
| `ticketEdited`  | `ticket_edited`  | ❌                    | ❌                      |
| `ticketNote`    | `ticket_note`    | ❌ (там `note_added`) | ❌                      |

Фронтенд в `BUSINESS.EVENT_TOAST_TYPE` не находит `ticket_edited` и `ticket_note`, падает в fallback `"info"`. Не критично, но тип тоста не соответствует смыслу события, и звуковые/цветовые акценты не работают.

**Требуется.** Либо переименовать `ticket_note` → `note_added` и добавить `ticket_edited` в протокол, либо синхронизировать документ с кодом. Решение за бэкендом — фронт подстроит маппинг.

Дополнительно: протокол документирует типы `ticket_reassigned`, `staff_accepted`, `ticket_overdue`, `emergency`, `staff_unassigned` — они нигде не генерируются. Определить: планируются или удалить из документа.

### D-3 (P3). Лимит выборки расходится с протоколом

`getSince()` по умолчанию `limit = 50`, протокол §10 говорит «не более 10 последних событий за запрос». При массовых операциях клиент получит 50 тостов за тик. Согласовать значение (рекомендуем 10–20) и привести документ в соответствие.

## Блок E. Списки и карточка

### E-1 (P1). Список закрытых заявок не содержит счётчика заметок

**Сейчас.** `CallRepository::formatList()` (общий для `open` и `close`) берёт заметки только из `lift_notes`. При закрытии `CallService::callClose()` сериализует их в `call_full_note_history` и удаляет из `lift_notes` через `deleteByCall()`.

Следствие: в ответе `data: "close"` у закрытой заявки всегда `note: {}`, `note_num: 0`, `other: "—"`, даже если заметок было десять.

При этом `findByIdDetailed()` для закрытых корректно декодирует слепок и отдаёт `note` массивом.

**Наблюдаемый эффект на клиенте:** карточка, открытая из списка закрытых, показывает пустой блок комментариев; та же карточка по прямой ссылке (F5) — комментарии на месте. Воспроизведено.

**Требуется (согласованное решение — «тонкий список»).** В `formatList()` для `type === 'close'`:

- не выбирать тело заметок;
- вычислять `note_num` декодированием `call_full_note_history` и подсчётом элементов;
- заполнять `other` как `"Есть заметки (N)"` при N > 0, иначе `"—"`;
- `note` оставить пустым объектом.

Тело заметок клиент получает точечным запросом `data: "ticket"` при открытии карточки — это принятое поведение, отдельный запрос на открытие закрытой заявки согласован.

Объём: ~10–15 строк.

**Критерий приёмки.** В списке закрытых у заявки с 3 заметками `note_num: 3`, `other: "Есть заметки (3)"`, `note: {}`. Трафик списка не вырос.

### E-2 (P1). Зафиксировать контракт в протоколе

Внести в `API_PROTOCOL.md`: список закрытых заявок не содержит тела заметок, только `note_num` и `other`. Полные заметки — через `data: "ticket"`. Для открытых список остаётся полным.

## Блок F. Техдолг — не блокирует

### F-1 (P3). `created_tickets` не заполняется при идемпотентном повторе

**Сейчас.** При статусе `ignored` (команда уже обработана ранее) `processSingleSyncCommand` возвращает `ticket_id` из `offline_command_log` в элементе `results`, но **не добавляет** его в `createdTicketsMap`.

**Следствие.** Сценарий: связь оборвалась после коммита на сервере, но до обработки ответа клиентом. Клиент повторяет пачку с тем же `batch_id`, получает `ignored`, но не может связать локальный `offline_uuid` с серверным ID. Заявка остаётся в очереди как несинхронизированная, хотя на сервере создана.

**Требуется.** При `ignored` для `CreateTicket` брать `ticket_id` из `offline_command_log` и добавлять в `created_tickets`. Если запись в логе отсутствует (TTL 7 дней истёк) — искать по `offline_uuid` через `findByOfflineUuid()`.

### F-2 (P3). `AcceptTicket` документирован, но не реализован

`API_syncCommands.md` §4.6 описывает команду, матрица §2.2 разрешает её всем ролям кроме guest. В `checkCommandPermissions()` она попадает в `else` → `InvalidArgumentException('unknown_command_type')` → `failed` навсегда.

Фронтенд её сейчас не отправляет, поэтому не блокирует. Требуется решение: реализовать или удалить из протокола. По бизнес-логике («механик принял в работу») команда нужна.

### F-3 (P3). Фото в комментариях принимаются, но игнорируются

`API_syncCommands.md` §4.5 документирует `photo_base64` с лимитом 500 КБ и 2 фото на заявку. Фронтенд сжимает фото (`utils/photo-compressor.js`) и отправляет в online-пути `action: "callnote"` с `photo_base64`.

`CallService::callnote()` читает только `text` / `note`, фото выбрасывается молча. Пользователь видит «Комментарий добавлен», фото нет.

Требуется решение: реализовать приём и хранение (в БД есть `lift_notes.img_name` и таблица `lift_upload`), либо явно отклонять. Если решено не реализовывать — фронт уберёт прикрепление из UI, чтобы не вводить в заблуждение.

### F-4 (P3). Intra-batch mapping отсутствует

`API_syncCommands.md` §10 описывает связывание команд внутри пачки: `AddComment` с `ticket_id: null` и `offline_uuid: X` должен резолвиться в ID заявки, созданной командой `CreateTicket` с тем же `offline_uuid` в этой же пачке. Приведён алгоритм с локальным словарём `$uuidToIdMap`.

**Сейчас.** В `processSingleSyncCommand`:

```
$ticketId = (int) ($cmd['ticket_id'] ?? 0);
$payload['call_id'] = $ticketId;
...
if ($type !== 'CreateTicket' && $ticketId === 0) → failed: missing_ticket_id
```

Словаря нет, fallback на `findByOfflineUuid()` нет. Любая команда с `ticket_id: null` отклоняется.

**Как фронт это обходит.** `outbox-queue.mergeIntoOfflineCreate()` сворачивает правки, комментарии и закрытие офлайн-заявки прямо в `CreateTicket.payload` (поля `details`, `comments`, `solution`, `closed_at`). Работает, но:

- теряется авторство и дата каждого отдельного действия — всё уходит как одно создание;
- операция read-modify-write не атомарна, два быстрых комментария к одной офлайн-заявке могут перезаписать друг друга (исправляем на клиенте транзакцией, но это компенсация).

**Требуется решение.** Реализовать маппинг по протоколу — тогда обход убирается, каждое действие сохраняет автора и дату. Либо принять сворачивание как окончательное решение и убрать §10 из протокола.

От ответа зависит только судьба клиентского обхода. Атомарность транзакции исправляется на клиенте в любом случае.

### F-5 (P3). Rate-limiting не реализован

`API_syncCommands.md` §11 документирует 60 req/min на пользователя, 10 пачек/min, заголовки `X-RateLimit-*`, код `rate_limited` с `retry_after`. В коде не обнаружено (отмечено как техдолг в истории коммитов).

Клиентский cooldown реализован и обрабатывает `rate_limited`, если он придёт. Не блокирует.

**Отдельно обращаю внимание на C-1** — это не косметика: сейчас любой авторизованный пользователь может закрыть или отредактировать любую заявку своей организации прямым запросом, независимо от роли и назначенности. Клиентские проверки `can_*` защитой не являются.

## Что НЕ требуется

- Менять структуру таблиц `outbox` / `offline_*` — все изменения касаются значений полей или новых строк в `lift_dict_versions`.
- Удалять строку `tickets` из `lift_dict_versions` — оставить для возможности откатa.
- Реализовывать новый статус команды для отказов по правам — `archived` + `reason: no_rights` полностью покрывает сценарий, клиент обработает на своей стороне.
- Менять формат `column_settings` в рамках этого ТЗ — разрез по scope (`open` / `close` / `report`) идёт отдельной задачей вместе с фронтом.
