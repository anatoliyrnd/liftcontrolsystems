

## Зафиксировано

| Вопрос | Решение |
|---|---|
| Интервал | **без задержек**, только последовательный `await`. Ожидание ~50 команд ≈ 15–30 с |
| Блокировка при отказе | **только команды той же заявки**, остальные идут |
| Отклонённые в очереди | **остаются видимыми с кнопкой «Удалить»** ⇒ храним в outbox со статусом `rejected`, в отбор на отправку не попадают |
| Автозапуск | **отложен на несколько секунд** после появления связи |
| Три попытки | **переход в ручной режим** |
| Кнопка «Удалить» | на каждой записи, любого статуса — как сейчас |
| «Удалить всю очередь» | с подтверждением, **в бэклог** |

**Достройка 1 — «три попытки» это два разных счётчика.** Смешивать их нельзя: команда не должна становиться «навсегда失败的» из-за того, что сеть лежала.

| Класс | Что считаем | Порог | Результат |
|---|---|---|---|
| Сеть недоступна, таймаут, `rate_limited` | подряд неудачные **запуски** | 3 | ручной режим, команды остаются `pending` |
| Сервер ответил `failed` | `retry_count` **команды** | 3 | `failed` навсегда, блокирует свою заявку |

Любой успех сбрасывает оба счётчика.

**Достройка 2 — при обрыве сети посреди очереди запуск прерывается сразу.** Иначе 50 команд × 15 с таймаута = 12 минут бесполезных ожиданий. Первая сетевая ошибка → выход из цикла, инкремент счётчика запусков.

## 3. Request

### 3.1. Структура

```json
{
  "action": "syncCommands",
  "batch_id": "batch_1761234567890_a1b2c3d4",
  "commands": [
    {
      "command_uuid": "cmd_1761234567890_e5f6a7b8",
      "command_type": "CloseTicket",
      "ticket_id": 35732,
      "offline_uuid": null,
      "payload": { "solution": "Заменён контактор", "closed_at": 1761234567 }
    }
  ]
}
```

### 3.2. Поля

| Поле | Обязательно | Примечание |
|---|---|---|
| `action` | ✅ | `"syncCommands"` |
| `batch_id` | ⚠️ | deprecated, см. §11.2 |
| `commands` | ✅ | **ровно 1 элемент**. Сервер принимает 1–20 для совместимости |
| `commands[0].command_uuid` | ✅ | `cmd_<ts_ms>_<8>` |
| `commands[0].command_type` | ✅ | enum |
| `commands[0].ticket_id` | ⚠️ | `null` для `CreateTicket`, обязателен для остальных |
| `commands[0].offline_uuid` | ⚠️ | обязателен для `CreateTicket` |
| `commands[0].payload` | ✅ | object |
| `commands[0].force_create` | ❌ | только уровень команды, только `CreateTicket` |

⚠️ `force_create` из входящего payload требуется явно удалять перед проставлением значения из уровня команды — иначе обход проверки дублей без подтверждения.

### 3.3. Валидация

| Условие | `code` | `reason` |
|---|---|---|
| `batch_id` пустой или > 64 | `invalid_input` | `invalid_batch_id` |
| `commands` пуст | `invalid_input` | `commands_empty` |
| `commands` > 20 | `invalid_input` | `commands_too_many` |

Проверка дублей `command_uuid` внутри пачки становится тривиальной при длине 1.

При ошибке верхнего уровня команда не выполнена, остаётся `pending`.

## 4. Типы команд

### 4.1. `CreateTicket`

#### Обязательные поля payload

| Поле | Тип |
|---|---|
| `offline_author_id` | int |
| `offline_author_name` | string |
| `opened_at` | int |
| `city_id`, `street_id`, `home_id`, `object_id` | int \| string |
| `fullAddress` | string |
| `group_id`, `request_id`, `department_id` | string |
| `details` | string, ≥ 6 символов |

#### Опциональные

| Поле | Примечание |
|---|---|
| `staff_id` | 0 / отсутствует = не назначен |
| `comments` | единый текст, §9.2 |
| `solution`, `closed_at`, `closed_by_name` | если закрыта офлайн |
| `closed_by_id` | ⚠️ принимается, не сохраняется |
| `call_phone`, `call_first_name`, `call_last_name` | данные заявителя |

#### 4.1.1. `repair_time` — игнорируется 🔄

Клиент офлайн срок не задаёт. Поле может отсутствовать или быть передано — **игнорируется в обоих случаях**.

Сервер ставит `expected_repair_time = time()` на момент синхронизации и пишет в `lift_history`: «Срок ремонта назначен сервером: офлайн-клиент срок не задаёт».

Валидация `repair_time_in_past` для офлайна не применяется.

**Следствия для UI:**

| Состояние | Отображение |
|---|---|
| До синхронизации | «будет назначен при синхронизации» |
| После | `repair_time` в прошлом → подсветка `cell-alert-danger` = сигнал «срок не назначен» |

#### 4.1.2. Валидация

| Условие | Результат | Статус |
|---|---|---|
| `opened_at` отсутствует | `invalid_input`, `opened_at_required` | ✅ |
| `details` < 6 | `archived`, `validation_error` | ✅ |
| Адрес не разрешается | `archived`, `validation_error` (`object_not_found`) | ✅ |
| `solution` < 6 | `archived`, `validation_error` | ✅ |
| `staff_id` не существует | `archived`, `validation_error` | 🆕 |
| `group_id` вне доступа | `archived`, `group_not_allowed` | 🆕 |
| `object.vis = 0` | **создаётся**, пометка в истории | ✅ |
| Активный дубликат без `force_create` | `duplicate_detected` | ✅ |

#### 4.1.3. Автокоррекции ✅

| Условие | Действие |
|---|---|
| `opened_at > now + 1 день` | `call_date = now` |
| `solution` есть, `closed_at` нет | `closed_at = now` |
| `closed_at < opened_at` | `closed_at = opened_at` |

Все три логируются в `lift_history` с `source = 'offline_sync'`.

⚠️ Пометка должна идти в `comments`, при пустом — в `call_details`. Сейчас всегда в `call_details`.

#### 4.1.4. Дубликаты ✅

Дубликат — активная заявка на том же `address_lift` **и** `call_department`. Список снимается до INSERT.

| `force_create` | Поведение |
|---|---|
| нет | `duplicate_detected` + `existing_tickets[]` |
| `true` | создаётся, номера дубликатов в `lift_history` |

#### 4.1.5. Создание сразу закрытой ⚠️

При `solution` + `closed_at`: `call_status = 1`, `call_solution`, `call_date2`, `call_last_name`.

**Дефект:** `comments` попадает в `lift_notes`, но `call_full_note_history` не заполняется. Карточка закрытой заявки читает слепок → комментарии не видны. Требуется сериализация и удаление заметок, как в `callClose`.

## 6. Статусы

### 6.1. Серверные

| Статус | Смысл | Действие клиента |
|---|---|---|
| `success` | выполнена | удалить, ✅ тост, сброс счётчиков |
| `archived` | отброшена, в архиве сервера | → `rejected`, ⚠️ уведомление |
| `ignored` | идемпотентность | удалить, без уведомления |
| `failed` | системная ошибка | `retry_count++`, backoff |
| `duplicate_detected` | нужно решение | → `needs_confirmation` |

### 6.2. Клиентские статусы outbox 🔄

| Статус | Идёт в отправку | Блокирует заявку | Видна в очереди | Кнопка «Удалить» |
|---|---|---|---|---|
| `pending` | ✅ | — | ✅ | ✅ |
| `needs_confirmation` | ❌ | ❌ | ✅ | ✅ |
| `failed` (retry исчерпан) | ❌ | **✅** | ✅ | ✅ |
| `rejected` | ❌ | ❌ | ✅ | ✅ |

`rejected` и `needs_confirmation` — внутренние, серверу не отправляются.

**`archived` больше не удаляется молча.** Переходит в `rejected`, остаётся видимой с причиной. Повтор невозможен: сервер уже отбросил команду, тот же `command_uuid` вернёт `ignored`. Единственный путь — удалить и создать заново через онлайн-форму.

### 6.3. Обработка `no_rights`

Текст по типу команды, тост persistent (`timeout: 0`), номер заявки — в историю:

| Тип | Текст |
|---|---|
| `CloseTicket` | Недостаточно прав для этого действия. Заявка не закрыта. |
| `CreateTicket` | Недостаточно прав для этого действия. Заявка не создана. |
| `EditTicket` | Недостаточно прав для этого действия. Изменения не применены. |
| `AddComment` | Недостаточно прав для этого действия. Комментарий не добавлен. |

Дополнительно клиент перечитывает `config` — права в UI обновляются сразу.

## 7. Порядок и блокировки 🔄

### 7.1. Строгий FIFO

Отбор — курсором по составному индексу **`[status, created_at]`**, первая eligible запись.

Сейчас порядок «случайно правильный»: курсор идёт по индексу `status`, а `command_uuid` начинается с timestamp. Индекс делает гарантию явной и дешёвой. Миграция данных не требуется.

При равных `created_at` (секундная точность) порядок разрешается `command_uuid`, содержащим миллисекунды.

### 7.2. Зачем строгий порядок

В пачечной модели команда в backoff **пропускалась**, следующие уходили. Это ломало хронологию одной заявки:

| Момент | Событие |
|---|---|
| t=0 | комментарий A → `failed`, retry через 30 с |
| t=5 | комментарий B → `success` |
| t=10 | закрытие → `success` |
| t=30 | комментарий A → заявка закрыта → `archived` |

Первый по времени комментарий потерян. Строгий FIFO с блокировкой по заявке это исключает.

### 7.3. Блокировка по заявке

Ключ блокировки: `ticket_id ?? offline_uuid`.

Множество заблокированных ключей = ключи команд со статусом `failed` (retry исчерпан). Вычисляется один раз за запуск, обновляется по ходу.

Алгоритм отбора: идти по `pending` в порядке FIFO, пропускать записи с заблокированным ключом, брать первую незаблокированную.

| Ситуация | Поведение |
|---|---|
| `failed` для заявки 35732 | команды 35732 ждут, заявки 35733+ идут |
| `rejected` для заявки 35732 | **не блокирует** — сервер отбросил, следующие могут пройти |
| `needs_confirmation` | не блокирует других; для офлайн-заявки зависимых команд нет (Вариант А) |

### 7.4. Прерывание при обрыве сети

Первая сетевая ошибка (`network_error`, `offline: true`, таймаут, `rate_limited`) → **выход из цикла немедленно**. Иначе 50 команд × 15 с = 12 минут бесполезных таймаутов.

Команда остаётся `pending`, `retry_count` **не инкрементируется** — её вины нет.

## 8. Режимы запуска 🔄

### 8.1. Триггеры

| Триггер | Задержка | Примечание |
|---|---|---|
| Событие `online` | **5 с** | debounce, предыдущий таймер отменяется |
| Открытие SPA | **3 с** | было 1 с |
| Возврат вкладки (`visibilitychange`) | 2 с | |
| Периодический опрос | 60 с | только при видимой вкладке и непустой очереди |
| Кнопка «Синхронизировать» | нет | сбрасывает ручной режим |
| После успешной команды | нет | продолжение того же запуска |

**Зачем задержка.** `navigator.onLine` становится `true` раньше, чем связь реально работает: DHCP, DNS, captive portal, сервер ещё недоступен. Немедленный старт сжигает одну из трёх попыток впустую.

### 8.2. Два счётчика отказов

| Счётчик | Что считает | Порог | Действие при достижении |
|---|---|---|---|
| `failedRuns` | запуски без единого терминального статуса | **3** | ручной режим |
| `retry_count` команды | серверные ответы `failed` | **3** | статус `failed`, блокировка заявки |

Сетевые ошибки инкрементируют только `failedRuns`. Любой `success` / `ignored` / `archived` сбрасывает `failedRuns`.

Backoff команды: **30 → 60 → 120 с**. После третьей неудачи — `failed`, `last_error`, автоповтор прекращается.

### 8.3. Ручной режим

Флаг персистентный (в `config`-сторе IndexedDB), переживает перезагрузку.

| Поведение | |
|---|---|
| Автотриггеры | игнорируются |
| Кнопка «Синхронизировать» | доступна, сбрасывает флаг и `failedRuns` |
| Индикатор в шапке | отдельное состояние «Приостановлено» |
| Уведомление | однократно: «Синхронизация приостановлена. Нажмите «Синхронизировать»» |
| Очередь | сохраняется полностью, ничего не удаляется |

### 8.4. Локи

`withSyncLock` (Web Locks, между вкладками) берётся **на команду**, не на весь запуск. Короткое удержание, порядок между вкладками сохраняется — каждая берёт старейшую eligible.

`withIdbWriteLock` — на время записи результата команды.

Модалка дубликата **не удерживает локи** (§13.2).

|---|---|
| Доп. описание | append в `payload.details` |
| Ответственный | `payload.staff_id` |
| Статус уведомления | `payload.notify_status` |
| Комментарий | append строки в `payload.comments` |
| Закрытие | `payload.solution`, `closed_at`, `closed_by_name`, `closed_by_id` |
| **Срок ремонта** | **не меняется** |

⚠️ Слияние — в одной `readwrite`-транзакции IndexedDB. Сейчас чтение в `readonly`, запись отдельной транзакцией: два быстрых комментария могут перезаписать друг друга.

### 9.2. Формат `comments` ✅

```
⏳ [Офлайн-комментарии]
[Иванов И., 02.11.2026 14:30]: Выехал на объект
[Петров П., 02.11.2026 14:45]: На месте, работаю
```

Сервер сохраняет всю строку как **одну заметку** с `is_offline = 1`, `note_post_date = opened_at`.

### 9.3. Закрытие ✅

`closed_by_*` и `offline_author_*` независимы: создать мог один диспетчер, закрыть другой.

### 9.4. Intra-batch mapping — удалён 🔄

При поштучной отправке зависимость решается последовательностью: `CreateTicket` ушёл → пришёл `ticket_id` → следующие команды используют его. Словарь внутри пачки не нужен ни десктопу, ни мобильному клиенту.

Для десктопа зависимых команд не существует вовсе (Вариант А).

### 9.5. `vis = 0` ✅

Проверка в офлайн-пути не выполняется. Заявка создаётся, в `lift_history` пометка «объект выведен из обслуживания на момент синхронизации».

### 9.6. Закрытая заявка — финальна ✅

Не переоткрывается. Единственный путь — «Закрыть и создать новую для этого объекта»: новая сущность, связь только через адрес и `from_ticket_id` в UI-состоянии.

Офлайн-закрытая в UI идентична онлайн-закрытой, отличие информационное: «⏳ ЗАКРЫТА ЛОКАЛЬНО».

## 10. Ошибки

### 10.1. Форма ⚠️

```json
{ "status": "error", "code": "invalid_input", "reason": "commands_empty", "message": "..." }
```

Обёртки `error` / `details` нет. `retry_after` для `rate_limited` — плоско на верхнем уровне.

### 10.2. Уровни

| Уровень | Поведение клиента |
|---|---|
| `status: "error"` | команда не выполнена, остаётся `pending`; при сетевом классе — прерывание запуска |
| `status: "ok"` + `results[0]` | обработка по §6 |

Коды `tenant_not_resolved`, `tenant_suspended`, `token_revoked`, `unauthorized`, `invalid_action` не существуют. Полный набор — `API_PROTOCOL.md` §16.2.

## 11. Идемпотентность

### 11.1. Основной уровень — `command_uuid` ✅

| Статус в `offline_command_log` | Поведение |
|---|---|
| `success`, `archived`, `ignored` | `ignored`, `already_processed` |
| **`failed`** | лог удаляется, команда выполняется заново |
| **`duplicate_detected`** | лог удаляется, команда выполняется заново |
| записи нет / истёк TTL | выполняется |

🔄 `duplicate_detected` исключён из терминальных: он означает «ожидает решения», заявка не создана. Иначе повтор с `force_create` и тем же `command_uuid` возвращал `ignored` — заявка не создавалась, хотя клиент показывал успех.

### 11.2. Уровень `batch_id` — deprecated ⚠️

Сохраняется для совместимости на переходный период. Клиент переиспользует `batch_id` при повторе той же команды (состав всегда один, отслеживание не нужно).

После подтверждения стабильности: убрать `batch_id` из запроса, прекратить запись в `offline_sync_log`, удалить таблицу. Это снимает основной потребитель диска — JSON-ответы до 3.5 МБ × 30 дней.

### 11.3. Транзакция = одна команда 🔄

Запись логов идемпотентности внутри той же транзакции теперь безопасна: откат означает, что команда не применена, повтор применит её один раз.

В пачечной модели откат из-за сбоя записи `offline_sync_log` уничтожал логи **всех** команд, и повтор применял `AddComment` второй раз. Риск снят.

### 11.4. TTL 🔄

| Таблица | TTL | Проверка при чтении |
|---|---|---|
| `offline_command_log` | 7 дней | **обязательна** |
| `offline_sync_log` | 30 дней | обязательна, пока используется |
| `offline_actions_archive` | 30 дней | — |
| `lift_access_tokens` | по `expires_at` | ✅ в SQL |
| `lift_refresh_tokens` | по `expires_at` | ✅ в SQL |

**Фильтр по TTL в SELECT, а не только чистка.** Без него истёкшая, но не удалённая строка даёт ложный `ignored` — команда, пролежавшая офлайн 8 дней, выбрасывается вместо выполнения.

### 11.5. Чистка — cron 🔄

`event_scheduler` на хостинге отключён, MySQL EVENT не работает. Существующий `cleanup_offline_tables` удалить или пометить неактивным.

Cron в панели хостинга доступен. Скрипт вызывается раз в сутки, обязан:

1. Получить список тенантов из master-реестра.
2. Для каждого — своё соединение (`DB::forTenant`), пакетные удаления с `LIMIT`.
3. Логировать объёмы по таблицам и тенантам.
4. Продолжать при ошибке одного тенанта.

Защита вызова — секретный токен, не авторизация пользователя.

`lift_access_tokens` и `lift_refresh_tokens` сейчас не чистятся вовсе: каждое открытие страницы создаёт запись.

### 11.6. Форматы идентификаторов ✅

`batch_<ts_ms>_<8 hex>`, `cmd_<ts_ms>_<8 hex>`, `offline_<ts_ms>_<8 hex>`. Не UUID v4. Валидация `/^(batch|cmd|offline)_\d+_[a-z0-9]{8}$/`, длина ≤ 64.

### 11.7. `created_tickets` при `ignored` ⚠️

| Путь | `created_tickets` |
|---|---|
| лог с терминальным статусом → `ignored` | **не заполняется** |
| `callnew` находит `offline_uuid` → `success` | заполняется ✅ |

Первый путь — пробел: после обрыва связи клиент не свяжет локальную заявку с серверным ID. Требуется брать `ticket_id` из лога, при отсутствии — искать по `offline_uuid`.

## 12. Rate-limiting 🆕

| Параметр | Лимит |
|---|---|
| Команд синхронизации на пользователя | **120 / мин** |
| Прочих запросов на пользователя | 60 / мин |
| Размер запроса | 10 МБ |

Отдельный лимит для синхронизации: при поштучной отправке 50 команд не должны съедать квоту поллинга и чтения карточек.

Реализация отсутствует. Клиент готов: `rate_limited` → прерывание запуска, `failedRuns++`, cooldown по `retry_after`.

## 13. Экран очереди

### 13.1. Состав 🔄

Четыре группы в порядке FIFO:

| Группа | Статус | Что показано | Действия |
|---|---|---|---|
| Ожидает | `pending` | тип, автор, объект, превью, дата | «Удалить» |
| Требует подтверждения | `needs_confirmation` | + список существующих заявок | «Создать дубликат», «Отменить», «Удалить» |
| Ошибка | `failed` | + `last_error`, `retry_count` | «Повторить», «Удалить» |
| Отклонено | `rejected` | + `reason`, `message` | «Создать заново онлайн», «Удалить» |

Кнопка «Удалить» — **на каждой записи любого статуса**, с подтверждением.

Сводка: «Всего: N · Ожидает: N · Подтвердить: N · Ошибок: N · Отклонено: N».

Кнопка «Синхронизировать» — сбрасывает ручной режим.

**В бэклог:** «Удалить всю очередь» с подтверждением. В текущий объём не входит.

### 13.2. Дубликат в фоне 🔄

Синхронизация фоновая, поэтому модалка не всплывает сама:

1. Команда → `needs_confirmation`.
2. Уведомление: «Требуется подтверждение дубликата» со ссылкой на очередь.
3. Запуск продолжается с другими командами.
4. Модалка открывается по клику из очереди.

Локи не удерживаются, другие вкладки и поллер не блокируются.

### 13.3. Индикатор в шапке

| Состояние | Условие |
|---|---|
| 🟢 idle | очередь пуста |
| 🟡 pending | есть `pending` |
| 🔴 error | есть `failed` |
| 🟠 attention | есть `needs_confirmation` или `rejected` |
| ⏸ paused | ручной режим |

`getOutboxCount()` считает только `pending` — отклонённые и ожидающие подтверждения не должны держать вечный жёлтый бейдж.

### 13.4. Прогресс

При поштучной отправке прогресс естественный: «Синхронизация: 7 из 23». Обновляется по каждой команде.

### 13.5. Чистка отклонённых

`rejected` старше 7 дней удаляются автоматически — расширить существующий `cleanupFailed(7)` на новый статус.
