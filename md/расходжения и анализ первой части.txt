# 📊 Комплексный анализ фронтенд-файлов

Проанализировал все присланные файлы в контексте согласованных протоколов (`OFFLINE_PROTOCOL.md` v3.0, `API_syncCommands.md` v4.2). Ниже — структурированный отчёт.

---

## 1. Инвентаризация файлов и их роли

| Файл | Роль | Зависимости |
|------|------|-------------|
| `offline-db.js` | Обёртка над IndexedDB, schema v2 | `idb` (vendor) |
| `outbox-queue.js` | **Фасад** постановки команд (единственная точка записи) | `offline-db`, `auth-store`, `uuid` |
| `batch-builder.js` | Сборка пачки: вес, порядок, маркер автора | `backoff` |
| `sync-manager.js` | Оркестратор: цикл, ответы, идемпотентность | `batch-builder`, `backoff`, `sync-lock`, `uuid` |
| `sync-lock.js` | Мультитаб-мьютекс (Web Locks API) | — |
| `online-status.js` | Трекер сети (`navigator.onLine`) | — |
| `uuid.js` | Генераторы `batch_id` / `command_uuid` / `offline_uuid` | — |
| `backoff.js` | Экспоненциальные задержки retry | — |
| `tickets-controller.js` | Таблица заявок + бейджи офлайн-состояний | `offline-db` |
| `main.js` | Точка входа, роутинг, инициализация | всё выше |

**Слоистость чистая:** `main` → `sync-manager` → `batch-builder`/`backoff` → `outbox-queue` → `offline-db`. Прямых записей в `offline-db.addOutboxCommand` из контроллеров нет — всё через фасад. Это правильное решение.

## 2. Ключевые архитектурные решения фронтенда, которые бэкенд ОБЯЗАН учитывать

### 2.1. Глобальный outbox на устройство (не на пользователя)
Команды синхронизируются **любым** залогиненным пользователем, не только автором. Для бэкенда это означает:
- `user_id` в `offline_sync_log` / `offline_command_log` = **кто синхронизировал** (текущий токен)
- Авторство = `offline_author_id` / `offline_author_name` в payload
- Сервер НЕ должен проверять «этот пользователь создал эту команду»

### 2.2. Маркер чужого авторства
Если синхронизирует не автор, `batch-builder.applyAuthorMarker` добавляет префикс `[Синхронизировано: <кто>. Автор: <автор>]` в текст (`details` / `solution` / `text`). Бэкенд получит **уже готовый** текст с маркером — самому ничего добавлять не нужно. Исключение: `CreateTicket` (автор уже в полях `offline_author_*`).

### 2.3. Идемпотентность через сохранённый `batch_id`
`sync-manager` хранит `pendingBatchId` + состав пачки в `IndexedDB.config`. При сетевом сбое retry идёт **с тем же `batch_id`**. 

**Критично для бэкенда:** ответ по `batch_id` должен кэшироваться в `offline_sync_log.cached_response` и возвращаться при повторе. Если кэша нет, но `batch_id` уже встречался — это нештатная ситуация.

### 2.4. Перегенерация `batch_id` при изменении состава
Если состав команд изменился (что-то ушло, что-то добавилось) — генерируется **новый** `batch_id`. Значит, одна и та же команда может в разных попытках уйти в разных пачках. Защита от дублей — только через `command_uuid`.

### 2.5. `duplicate_detected` → отдельный повтор
`_handleDuplicate` отправляет команду с `force_create: true` в **новой пачке из одного элемента** с новым `batch_id`, но **с тем же `command_uuid`**.

**Критично для бэкенда:** при статусе `duplicate_detected` команда **НЕ должна** записываться в `offline_command_log` как обработанная. Иначе повтор вернёт `already_processed` вместо создания. В лог попадают только финальные статусы: `success`, `ignored`, `archived`. Статусы `failed` и `duplicate_detected` — не фиксируются как «обработанные».

### 2.6. Временные метки из прошлого
Фронтенд шлёт `closed_at` и `created_at` — реальное время действия (офлайн могло быть часы/дни назад). Бэкенд должен использовать **их**, а не `time()`, для `call_date2` и `note_post_date`.

## 4. 🔴 Критические несоответствия

### 4.1. Имя поля описания: `details` против `description_delta`

Это **самое серьёзное** расхождение:

| Источник | Имя поля в `EditTicket` |
|----------|------------------------|
| `OFFLINE_PROTOCOL.md` раздел 4.2 | `description_delta` |
| `API_syncCommands.md` раздел 4.3 | `description_delta` |
| `outbox-queue.js` `enqueueEdit` | **`details`** |
| `batch-builder.js` `applyAuthorMarker` | **`patched.details`** |

**Фронтенд будет слать `details`, а сервер по протоколу ждёт `description_delta`.** Валидация сервера сочтёт payload пустым (`edit_payload_empty`) и заархивирует команду.

Нужно выбрать одно имя. Два варианта:
- **Вариант А:** переименовать во фронтенде на `description_delta` (соответствует протоколу, подчёркивает семантику «только дельта»)
- **Вариант Б:** принять на сервере оба имени (`description_delta` как основное, `details` как алиас)

Рекомендую Вариант А — меньше двусмысленности.

### 4.2. Отсутствует `enqueueAccept` в `outbox-queue.js`

Протокол описывает 5 типов команд, включая `AcceptTicket`. В фасаде реализованы только 4:
- `enqueueCreate` ✅
- `enqueueEdit` ✅
- `enqueueClose` ✅
- `enqueueComment` ✅
- `enqueueAccept` ❌ **отсутствует**

Также `getTicketFlags` не проверяет флаг `hasAccept`.

Это, вероятно, запланировано для мобильной версии (механики принимают в работу). Для бэкенда: обработчик `handleAcceptTicket` всё равно нужен, просто на десктопе пока не вызывается.

### 4.3. Фото в офлайн-комментариях — только онлайн

`enqueueComment` явно **не сохраняет** `photo_base64` в outbox (комментарий: «Фото — ТОЛЬКО ОНЛАЙН»). При этом:
- `API_syncCommands.md` описывает сжатие фото до 500 КБ и лимит 2 шт.
- Мобильная версия для механиков может потребовать фото офлайн (основной сценарий — фото неисправности на месте)

**Противоречие между десктопом и протоколом.** Нужно зафиксировать:
- Десктоп: фото офлайн не поддерживается (текущая реализация)
- Мобилка: фото поддерживается со сжатием (будущая реализация)
- Бэкенд должен быть готов к обоим случаям (валидировать, если пришло)

## 5. 🟡 Замечания, требующие решения

### 5.1. Семантика дельты описания не закреплена однозначно

В текущем онлайн-коде `calledit` (из репозитория) логика `str_contains` пытается угадать: фронт прислал полное описание или дельту. Для офлайн-команд в протоколе заявлено: **всегда только дельта, всегда конкатенация**. Нужно подтвердить, что фронтенд в `enqueueEdit` действительно кладёт только новый текст, а не полное поле редактирования.

### 5.2. Поведение при ошибках валидации пачки

В `sync-manager._syncLoop`: если `response.status === 'error'` и код ≠ `rate_limited`, вызывается `_markBatchFailed` — **все** команды помечаются `failed`. 

Протокол же говорит: при ошибке верхнего уровня пачка остаётся в outbox для retry. Статус `failed` исключает автоматический повтор (команда выпадает из `getPendingBatch`, т.к. фильтр по `status = 'pending'`).

Получается: ошибки валидации пачки → ручное вмешательство. Для `duplicate_command_uuid` или `commands_too_many` это, пожалуй, правильно (это баг клиента). Но стоит убедиться, что такие ситуации вообще не возникают в штатной работе.

### 5.3. Валидация `repair_time_in_past`

Протокол требует ошибку, если `repair_time < текущего времени`. Но для офлайн-заявки, созданной 2 дня назад, срок ремонта мог легитимно «протухнуть», пока пользователь был без сети. 

Рекомендация для бэкенда: **не валидировать** `repair_time` на «в прошлом» для офлайн-команд. Либо валидировать мягко (принять как есть). Жёсткая валидация приведёт к архивации легитимных команд.

### 5.4. `_applyCreatedTickets` и зависимость от `offline_uuid`

После успеха `CreateTicket` сервер возвращает `created_tickets: {offline_uuid: ticket_id}`. Фронтенд проставляет `ticket_id` зависимым командам, у которых `ticket_id === null`. 

Это работает, **только если** зависимые команды ещё в outbox. Если они ушли в той же пачке (intra-batch) — сервер сам их связал. Всё корректно, но бэкенд должен обязательно возвращать `created_tickets` даже если в пачке была одна команда (для обновления локального кэша).

### 5.5. Навигация к офлайн-заявкам

В `tickets-controller` офлайн-заявки получают `id = o.uuid` (строка `cmd_...`). Клик ведёт на `#/ticket/cmd_...`. Значит `details-controller` должен различать:
- числовой `call_id` → серверная заявка
- строковый `offline_uuid` → локальная офлайн-заявка

После синхронизации локальная запись должна быть заменена на серверную (фронтенд обновляет кэш). Бэкенд здесь не участвует, но это влияет на то, какие поля обязательно возвращать в `created_tickets`.

### 5.6. `getPendingBatch(50)` против лимита 20

`sync-manager` запрашивает 50 команд, `buildBatch` берёт максимум 20. Избыточное чтение, но безвредно. Если в outbox много команд с активным backoff — они читаются и пропускаются. Это нормально.

## 6. 🟢 Сильные стороны реализации

1. **Фасад `outbox-queue`** — единая точка записи, контроллеры не лезут в БД напрямую.
2. **`markRetry` читает актуальный `retry_count` из хранилища** перед инкрементом — защита от гонок.
3. **Чистые функции** в `batch-builder` и `backoff` — легко тестировать, параметр `nowSec` для инъекции времени.
4. **`sync-lock` с graceful fallback** — если Web Locks недоступен, работаем без него (идемпотентность сервера спасает).
5. **`online-status` сознательно без ping** — разделение «нет сети» и «сервер упал».
6. **Защита от повторной подписки** в `tickets-controller` (`_isSubscribedToAddresses`).
7. **Корректная конвертация миллисекунд в секунды** для офлайн-заявок (`createdAt > 9999999999`).
8. **XSS-защита** в `_renderCityDropdown` (создание элементов вместо `innerHTML`).
9. **AUTH_LOST корректно прерывает синхронизацию** через `abortTag('sync')`, команды остаются pending.
10. **Outbox НЕ очищается при logout** — синхронизируется при следующем входе (правильно для глобального outbox).

## 7. Вопросы для уточнения перед реализацией бэкенда

1. **Поле описания в `EditTicket`:** фиксируем `description_delta` и правим фронтенд? Или сервер принимает оба имени?

2. **`AcceptTicket` на десктопе:** нужен ли сейчас, или это только мобилка? (влияет на то, добавлять ли `enqueueAccept` сейчас)

3. **Валидация `repair_time` в прошлом:** отключаем для офлайн-команд?

4. **Фото на десктопе в офлайн:** оставляем «только онлайн»? Если да — протокол нужно скорректировать пометкой «для десктопа; мобилка — отдельно».

5. **Формат `call_staff_status` для `AcceptTicket`:** фронтенд не реализован, но сервер будет ставить `2` (WEB). Подтверждаем, что «принять в работу» = `notify_status 2` для десктопа? (ранее обсуждали, что механик в мобилке тоже может принимать)

6. **Что возвращать в `message` для `duplicate_detected`:** фронтенд пока использует заглушку-тост вместо модалки (см. `main.js` — `onDuplicateDetected` возвращает `false`). Временное поведение: дубликат НЕ создаётся, команда удаляется. Это устраивает до Фазы 4?

7. **Формат ответа сервера для заявок:** `open`/`close` возвращают массив с полем `id` или `call_id`? Фронтенд в `tickets-controller` ожидает `item.id` для навигации, но в `_applyPendingRowDecorations` читает `td[data-col-id="id"]`. Нужно убедиться, что маппинг единообразен.
