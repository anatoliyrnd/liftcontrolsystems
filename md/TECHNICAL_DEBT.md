## 1. Назначение

Документ фиксирует **накопленный технический долг** проекта Lift-Calls: что было сделано «быстро и временно», что отложено, что нужно переделать. В отличие от roadmap (планируемые фичи), техдолг — это **обязательства**, которые нужно закрыть, чтобы система оставалась управляемой.

**Принцип:** техдолг не «стыдно», но он должен быть **явным**. Каждый пункт имеет приоритет, оценку и план закрытия.

### 4.1. Архитектура

#### TD-ARCH-01. Урезанный PHP-бэкенд (Трек А) — временное решение

| Параметр      | Значение      |
| ------------- | ------------- |
| **Приоритет** | P1            |
| **Категория** | Архитектурный |
| **Статус**    | Активен       |
| **Создан**    | 01.11.2026    |
| **Дедлайн**   | T+6–8 месяцев |

**Описание:** для быстрого запуска тенанта l3 используется урезанный PHP-код на `l3.liftcs.ru` с отдельной БД MariaDB. Это временное решение, пока новый API (Трек Б) не готов.

**Что «болит»:**

- Двойная поддержка кода (PHP + Node.js).
- Два стека в голове у соло-разработчика.
- Новые фичи в Треке А не добавляются (только багфиксы).

**План закрытия:**

1. Довести новый API до готовности (Фазы 1–12).
2. Мигрировать l3 на новый API (Фаза 13).
3. Переключить прокси-роутер: `'l3' => ['*' => 'new_api']`.
4. Оставить урезанный PHP только как архив закрытых заявок (TD-ARCH-02).

**Риск «застревания» на Треке А:**

- Жёсткий дедлайн: 6–8 месяцев.
- Регулярные checkpoints (каждый месяц) — прогресс Трека Б.
- Демонстрация нового API заказчику до полного переключения.

#### TD-ARCH-02. Архив закрытых заявок на MariaDB

| Параметр      | Значение      |
| ------------- | ------------- |
| **Приоритет** | P2            |
| **Категория** | Архитектурный |
| **Статус**    | Активен       |
| **Создан**    | 01.11.2026    |

**Описание:** после миграции l3 на новый API закрытые заявки остаются в MariaDB. Доступ к ним — только через отдельный прокси или админку, которая пока не реализована.

**Что «болит»:**

- Диспетчеры не могут посмотреть закрытые заявки до миграции (после переключения).
- Нужен отдельный экран/прокси для архива.

**Варианты решения:**

| Вариант                                               | Плюсы                     | Минусы                                  |
| ----------------------------------------------------- | ------------------------- | --------------------------------------- |
| A. Отдельный прокси `archive.l3.liftcs.ru`            | Просто, изолировано       | Дополнительный домен, сертификат        |
| B. Раздел «Архив» в PHP-админке `/settings/archive/`  | В одном месте             | Смешивает данные (MariaDB + PostgreSQL) |
| C. Миграция закрытых заявок тоже (не только открытых) | Полная картина            | Противоречит стратегии «чистого старта» |
| D. Экспорт закрытых заявок в CSV/PDF перед миграцией  | Просто, не требует прокси | Не интерактивно                         |

**Рекомендация:** вариант B (раздел «Архив» в `/settings/archive/`). PHP-админка обращается к MariaDB напрямую (только чтение) для закрытых заявок l3. Реализуется после Фазы 13.

**План:**

1. После миграции l3 → создать `/settings/archive/`.
2. PHP-код: `SELECT` из MariaDB (read-only), форматирование в UI.
3. Добавить в меню «Архив» (только для тенантов, у которых есть MariaDB-архив).

#### TD-ARCH-03. PgBouncer при росте тенантов

| Параметр      | Значение                         |
| ------------- | -------------------------------- |
| **Приоритет** | P3                               |
| **Категория** | Производительность / Архитектура |
| **Статус**    | Отложен                          |
| **Создан**    | 01.11.2026                       |
| **Триггер**   | 50+ тенантов                     |

**Описание:** при использовании schema-per-tenant один пул соединений на всех тенантов. Это хорошо до 50 тенантов. При росте до 50+ — соединений может не хватить, и понадобится PgBouncer.

**Что «болит»:** при 50+ тенантах `max_connections` PostgreSQL (по умолчанию 100) может стать узким местом.

**План закрытия:**

1. Мониторинг `pg_stat_activity` (количество активных соединений).
2. При приближении к 80% `max_connections` — развернуть PgBouncer.
3. Конфиг: `pool_mode = transaction`, `max_client_conn = 500`, `default_pool_size = 20`.

**Триггер:** при стабильном количестве активных соединений > 80 или при 50+ тенантах.

### 4.3. Производительность

#### TD-PERF-01. Асинхронный экспорт отчётов

| Параметр      | Значение           |
| ------------- | ------------------ |
| **Приоритет** | P2                 |
| **Категория** | Производительность |
| **Статус**    | Активен            |
| **Создан**    | 01.11.2026         |

**Описание:** `GET /reports/calls/export/pdf` и `/excel` синхронные. При >10 000 строк — таймаут.

**Что «болит»:** диспетчер ждёт 30+ секунд, браузер может отвалиться по таймауту.

**План закрытия:**

1. Лимит 10 000 строк (уже есть).
2. Если > 10 000 — вернуть `202 Accepted` с `job_id`.
3. Очередь (`bullmq` + Redis).
4. `GET /reports/export/:job_id/status` — статус.
5. `GET /reports/export/:job_id/download` — скачать готовый файл.

#### TD-SYNC-01. Дублирование `calledit`/`callnote` при `network_error`

| Параметр      | Значение             |
| ------------- | -------------------- |
| **Приоритет** | P1                   |
| **Категория** | Архитектурный / Sync |
| **Статус**    | Частично закрыт      |
| **Создан**    | 04.11.2026           |

**Описание:** при таймауте онлайн-запроса `calledit` / `callnote` сервер
мог уже применить мутацию, но клиент ответа не получил. Автоматический
fallback в outbox продублировал бы дельту описания / комментарий.

**Текущее состояние:** fallback в outbox при `network_error` отключён
для `calledit`/`callnote` (см. `details-controller._onSave` / `_onAddNote`).
Работает **только** для `callClose` — он идемпотентен на сервере (повторное
закрытие → `ticket_already_closed` → архив, данные не портятся).

**Целевое решение:** унифицировать `calledit`/`callnote` с `syncCommands` —
клиент генерирует `command_uuid`, сервер пишет в `offline_command_log`,
при повторе возвращает `ignored`. Один механизм идемпотентности на оба пути.

**Связано:** `API_PROTOCOL.md` v4.3 (syncCommands), `OFFLINE_PROTOCOL.md` v3.0.
**Конец `TECHNICAL_DEBT.md` v3.0.**
