````md
### 0.2. Соединение

| Параметр        | Значение                                                   |
| --------------- | ---------------------------------------------------------- |
| Метод           | `POST`                                                     |
| Content-Type    | `application/json; charset=utf-8`                          |
| Accept          | `application/json`                                         |
| HTTP-статус     | **всегда 200**, ошибки в теле                              |
| Таймаут клиента | 15 с (`AbortController`); для `syncCommands` — 30 с        |
| Авторизация     | `Authorization: Bearer <access_token>`                     |
| Cookie          | `lift_refresh` — HttpOnly, Secure, SameSite=Strict, path=/ |

### 0.3. Форма ответа ✅

`Response::ok($payload)` выполняет `['status' => 'ok'] + $payload` — **плоское слияние ключей**. Обёртка `data` появляется только там, где она передана явно.

| Тип                | Форма                                      | Пример                                        |
| ------------------ | ------------------------------------------ | --------------------------------------------- |
| Списки             | голый массив, без `status`                 | `[ {...}, {...} ]`                            |
| Одиночная сущность | `{status, data}`                           | `ticket`, `get_tenant_info`                   |
| Команды            | `{status, ...поля}`                        | `{status:"ok", call_id:35733, message:"..."}` |
| Конфигурация       | `{status, ...поля}`                        | `config`, `loadAddress`, `notifications`      |
| Пачка команд       | `{status, data:{...}}`                     | `syncCommands` ⚠️ сейчас плоско               |
| Отчёты             | `{status, data:{...}}`                     | `reports_*` 🆕                                |
| Ошибка             | `{status:"error", code, message, reason?}` | без обёртки `error`                           |

**Правило:** обёртка `data` — для одиночной сущности, результата пачки и отчётов. Остальное плоско.

### 0.4. Публичные экшены

Без авторизации: `get_tenant_info`. Все остальные требуют валидный Bearer.

## 1. Форматы данных

### 1.1. Даты и время

Все даты — **Unix timestamp, целое число секунд**.

| Тип поля      | Формат             | Пример                         |
| ------------- | ------------------ | ------------------------------ |
| Дата + время  | Unix timestamp (с) | `1761214500`                   |
| Числовые ID   | Integer            | `35732`                        |
| `alert_level` | Integer 1–3        | `3`                            |
| Флаг заметок  | String             | `"Есть заметки (3)"` или `"—"` |

### 1.2. Правило часового пояса

**Unix-метка абсолютна и не имеет часового пояса.** Локальность учитывается клиентом в момент построения метки:

1. Пользователь выбирает стенное время «17:00» в своей зоне.
2. Клиент строит `new Date(y, m-1, d, hh, mm)` — конструктор трактует значения как локальные.
3. `Math.floor(date.getTime() / 1000)` даёт абсолютную метку (для MSK это 14:00 UTC).
4. Сервер сохраняет метку **как есть, без сдвигов**.
5. Любой клиент, рендеря метку в локальной зоне, получает исходные стенные 17:00.

**Запрещено:** прибавлять/вычитать смещение зоны к метке на любой стороне.

Серверное форматирование в строку (`lift_history`, `full_history`, пометки автокоррекции) выполняется в единой бизнес-зоне: `bootstrap.php` задаёт `date_default_timezone_set('Europe/Moscow')` ✅ (B3.9).

Сравнения выполняются в абсолютных величинах. Для DATETIME-колонок запись идёт через `FROM_UNIXTIME()` ✅ (B3.6) — конвертация и сравнение в одной зоне MySQL.

⚠️ Осталось: `@@session.time_zone = SYSTEM`, то есть зона MySQL берётся из ОС хостера. PHP зафиксирован явно, MySQL — нет. Смена TZ сервера разъедет `NOW()` с `FROM_UNIXTIME` и вернёт скос на 3 часа. Сделать явным в точке подключения: `PDO::MYSQL_ATTR_INIT_COMMAND => "SET time_zone = '+03:00'"`. Europe/Moscow = UTC+3 без DST с 2014, смещение эквивалентно именованной зоне и не требует таблиц зон MySQL.
````

### 2.2. `can_add_ticket` и `user_add_call` — решение принято ✅

Флаг `lift_users.user_add_call` уважается в обоих путях: online (`callnew`) и offline (`syncCommands → CreateTicket`). Инженер с флагом создаёт заявку офлайн — команда выполняется, а не уходит в `archived: no_rights` с потерей работы.

| Роль            | `user_add_call = 0` | `user_add_call = 1` |
| --------------- | ------------------- | ------------------- |
| `administrator` | ✅                  | ✅                  |
| `dispatcher`    | ✅                  | ✅                  |
| `engineer`      | ❌                  | ✅                  |
| прочая роль     | ❌                  | ✅                  |
| `guest`         | ❌                  | ❌                  |

Единый источник истины — `App\Support\CallPolicy::canCreate()`. Его используют: `ConfigService` (выдача `can_add_ticket`), `ApiController` (sync-путь), `CallService` (online-путь). Дублирующих проверок роли быть не должно.

Флаг прокидывается в `$user` через `AuthService::formatUser()` — иначе он недоступен в sync-пути, где `$user` приходит из `validate()`.

### 2.3. Роли

| Роль            | Описание                                                |
| --------------- | ------------------------------------------------------- |
| `administrator` | полные права                                            |
| `dispatcher`    | создаёт и редактирует заявки, закрывает, комментирует   |
| `engineer`      | механик; видит свои заявки, закрывает и комментирует их |

| `reserved`      | резерв, права гостя                                     |

**Допустимы только эти пять значений.** Клиент нормализует всё неизвестное в `guest`.

Нормализация на сервере реализована ✅ (B1.4): `mechanic → engineer`, `foreman → dispatcher` при чтении. Данные не меняются. `staff_list` продолжает отбирать по сырым значениям БД.

### 5.1. Идентификатор ⚠️

**Обязательны все три поля: `id` (int), `call_id` (int), `call_number` (string)** — с одинаковым значением.

Сейчас карточка отдаёт только `call_id` + `call_number`, а списки — только `id`. Клиент читает `id`, поэтому карточка, открытая по прямой ссылке, не показывает номер и не может сохранить изменения.

### 5.2. Заметки

`note` — **массив**, не объект с числовыми ключами. Для открытых читается из `lift_notes`, для закрытых — из `call_full_note_history`.

Элемент: `{ id, user, body, date, type, is_offline }`. `is_offline: 1` — заметка создана офлайн, клиент рисует маркер ⏳.

### 5.3. История

`full_history` — **plain text**, строки вида `[dd.mm.yyyy hh:mm] [Офлайн] текст`, разделённые `\n`. Источник `offline_sync` помечается префиксом `[Офлайн]`.

### 5.4. Права ⚠️

| Поле             | Правило (целевое)                                                      |
| ---------------- | ---------------------------------------------------------------------- |
| `can_edit`       | `type = open` И (`admin` ИЛИ `dispatcher`)                             |
| `can_close`      | `type = open` И (`admin` ИЛИ `dispatcher` ИЛИ (`engineer` И назначен)) |
| `can_comment`    | `type = open` И (`admin` ИЛИ `dispatcher` ИЛИ (`engineer` И назначен)) |
| `closureallowed` | определить судьбу: отдавать осмысленно или удалить                     |

Сейчас `can_close` разрешает любому `engineer` без назначенности, `can_edit` — назначенному `engineer`. Both расходятся с матрицей `API_syncCommands.md` §2.2. `closureallowed` захардкожен в 0.

**Права вычисляются той же логикой, что и серверная проверка при выполнении действия** — один источник истины.

### 7.3. Дубликаты ✅

| ----------------- | ------------------------------------------------------- |

## 9. `callClose` — закрытие

**Request:** `{ "action": "callClose", "call_id": 35732, "solution": "...", "user_id": 3 }`

`solution` — минимум 6 символов. `user_id` — для логирования.

### 9.1. Поведение ✅

1. Все заметки из `lift_notes` сериализуются в `call_full_note_history` (JSON).
2. Заметки удаляются из `lift_notes`.
3. Устанавливаются `call_status = 1`, `call_date2 = closed_at`, `call_solution`, `call_last_name`.
4. Запись в `lift_history`, инкремент версии заявок, событие `ticket_closed`.

**Колонки БД:** дата закрытия — `call_date2`, имя закрывшего — `call_last_name`. Имена `call_close_date` / `call_close_name` из прежних документов ошибочны.

Закрытая заявка **не переоткрывается**. Единственный путь продолжить работу по объекту — «Закрыть и создать новую для этого объекта»: создаётся отдельная заявка с новым ID, связанная с предыдущей только адресом.

**Response:** `{ "status": "ok", "message": "Заявка №35732 успешно закрыта." }`

**Ошибки:** `closed` (reason `ticket_already_closed`), `not_found`, `invalid_input` (reason `solution_too_short`), `forbidden` ⚠️.

## 11. `notifications` — события и версии

**Request:**

```json
{
  "data": "notifications",
  "since_id": 142857,
  "versions": {
    "staff": 15,
    "dicts": 8,
    "addresses": 3,
    "open_tickets": 42,

```

**Response:**

```json
{
  "status": "ok",
  "notifications": [
    {
      "id": 142859,
      "event_type": "emergency",
      "ticket_id": 35732,
      "actor_id": 5,
      "text": "Аварийная заявка №35732",
      "sound": true,
      "timeout": 15000,
      "created_at": 1761215710
    }
  ],
  "last_id": 142859,
  "versions": {
    "staff": 15,

    "addresses": 3,
    "open_tickets": 42,

  },

```

### 11.1. Поля события

| Поле         | Тип         | Статус                                            |
| ------------ | ----------- | ------------------------------------------------- |
| `id`         | int         | ✅                                                |
| `event_type` | string      | ⚠️ см. 11.2                                       |
| `ticket_id`  | int \| null | ✅                                                |
| `actor_id`   | int         | ⚠️ **не отдаётся** — колонка `user_id` не выбрана |
| `text`       | string      | ✅                                                |
| `sound`      | bool        | ✅                                                |
| `timeout`    | int \| null | ✅                                                |
| `created_at` | int         | ⚠️ не отдаётся                                    |

**`actor_id` критичен:** клиент фильтрует собственные действия по нему. Без поля фильтрация не работает, и пользователь получает тосты о своих же операциях, включая звуковые.

### 11.2. Типы событий

| Генерируется     | Ожидается клиентом | Статус                |
| ---------------- | ------------------ | --------------------- |
| `ticket_created` | `ticket_created`   | ✅                    |
| `ticket_closed`  | `ticket_closed`    | ✅                    |
| `ticket_edited`  | `ticket_edited`    | ✅ добавлен в словарь |
| `ticket_note`    | `note_added`       | ✅ алиас на клиенте   |
| `spult_error`    | `spult_error`      | ✅ error              |

Типы `ticket_reassigned`, `staff_accepted`, `ticket_overdue`, `emergency`, `staff_unassigned` описаны, но не генерируются.

#### 11.2.1. `spult_error`

Один тип на все расхождения СПульта, различие — в `kind` внутри текста.

| kind                    | Заявка                       | ticket_id |
| ----------------------- | ---------------------------- | --------- |
| `guid_mismatch`         | создана                      | int       |
| `guid_conflict`         | создана                      | int       |
| `spult_id_conflict`     | создана                      | int       |
| `duplicate_note_failed` | существует, заметка не легла | int       |
| `address_unresolved`    | нет                          | null      |
| `org_mismatch`          | нет                          | null      |
| `pult_guid_mismatch`    | нет                          | null      |
| `bad_xml`               | нет                          | null      |
| `fatal`                 | нет                          | null      |

Правила:

- `timeout: 0` — сервер шлёт явно, тост persistent. Дефолт типа (8 с) не применяется.
- `sound`: `ticket_id === null` → `1` (сигнал потерян, требует внимания); `ticket_id !== null` → `0` (заявка создана, расхождение — вопрос к админу, письмо ушло).
- Ссылка «Открыть →» рисуется **по наличию `ticket_id`**, не по типу события. Для карантина ссылки нет: заявки нет, просмотр спула в админ-панели не реализован.
- Текст обязан содержать **адрес и причину** — диспетчер передаёт их голосом. Формирует `sp.php`. Клиент не обрезает текст события (лимит 500 символов, полный текст доступен по наведению).

### 11.3. Версии слоёв ⚠️

Сервер отдаёт числовые версии слоёв данных. Клиент передаёт свои; сервер возвращает `outdated` — список слоёв, где серверная версия больше клиентской.

| Ключ             | Инкремент при                                             |
| ---------------- | --------------------------------------------------------- |
| `staff`          | изменении справочника сотрудников                         |
| `dicts`          | изменении отделов / типов / групп                         |
| `addresses`      | изменении адресного справочника                           |
| `open_tickets`   | `callnew` (открытая), `calledit`, `callnote`, `callClose` |
| `closed_tickets` | `callnew` (сразу закрытая), `callClose`                   |

**Сейчас существует единственный ключ `tickets`**, а клиент отправляет `open_tickets`. Сравнение всегда идёт с нулём → `outdated` непустой на каждом ответе → полный список открытых перезапрашивается каждые 120 секунд независимо от изменений.

Требуется завести оба ключа и расставить инкременты по таблице. Инкремент — строго после успешного коммита.

**Правило клиента:** в запрос отправляются версии **применённых** данных, а не полученных. Отметка «применено» ставится после успешной записи, что делает потерянное обновление самовосстанавливающимся на следующем тике.

### 11.4. Прочее

Окно свежести событий — 30 минут, чистка вероятностная при создании события. Лимит выборки по умолчанию 50 ⚠️ (протокол предполагал 10–20; при массовых операциях клиент получает лавину тостов).

### 11.4.1. Три канала доставки — не заменяют друг друга

| Канал                 | Живёт                | Кому                                     |
| --------------------- | -------------------- | ---------------------------------------- |
| `spult_events`        | 30 дней              | админ-панель, разбор постфактум          |
| Лента `notifications` | 30 минут             | открытая вкладка, best-effort            |
| Email админу          | до удаления из ящика | закрытая вкладка — единственный надёжный |

`timeout: 0` означает «не закрывать по таймеру в UI», а не «долговременное хранение». `cleanup()` удаляет события старше 30 минут: если вкладка была закрыта дольше, событие в ленту не попадёт. **Лента — не журнал**, клиент на неё как на журнал не рассчитывает.

Лимит выборки 50 (§11.4) при массовой операции даёт лавину тостов. Клиентский throttle звука — 1 beep / 10 с, но persistent-тосты копятся в очереди и закрываются вручную. Агрегация массовых расхождений (одно событие на смену адреса, а не на лифт) — задача бэкенда.

### 13.2. `save_user_settings`

**Request:**

```json

  "action": "save_user_settings",
  "profile": { "surname": "Иванов", "name": "Иван", "patronymic": "Иванович" },
```

### 13.3. Разрез по scope

`scope` ∈ `open` | `close` | `report`. На сервере хранятся **только `order` и `hidden`**.

Локально на клиенте (ключ обязательно содержит `user_id`): ширины колонок, колонка и направление сортировки, период закрытых, фильтры городов. Эти настройки устройство-специфичны и на сервер не уходят.

**Обратная совместимость:** плоский `{order, hidden}` трактуется как `open`; при следующем сохранении пишется структура с разрезом. Отдельная миграция не требуется.

### 13.4. Раздельное ФИО ⚠️

`AuthService::formatUser` возвращает `surname: null` и `patronymic: null` hardcoded. Сохранённое раздельное ФИО не восстанавливается после перезагрузки.

Требуется: добавить колонки `user_surname`, `user_patronymic` в `lift_users`, писать их в `save_user_settings`, возвращать в `formatUser` и `get_user_settings`. Поле `user_name` остаётся отображаемым именем.

## 15.1. Общие фильтры

Единый объект для `reports_stats`, `reports_list`, `reports_export`. Отличия: `page`/`limit` только в `list`, `format` только в `export`.

### Валидация дат (порядок проверок фиксирован)

| Условие                                                | Ответ                                          |
| ------------------------------------------------------ | ---------------------------------------------- |
| `date_from <= 0`                                       | `{status:"ok", data:null}`                     |
| `date_from > date_to`                                  | `{status:"ok", data:null}`                     |
| `date_to > strtotime('today 23:59:59')` (PHP TZ = МСК) | `{status:"ok", data:null}`                     |
| `date_to - date_from > 90*86400`                       | `invalid_input`, `reason: date_range_too_long` |

90 дней = **90 календарных включительно** (`D … D+89`, дельта `90*86400 − 1`). Клиент считает дни, сервер — секунды.

## 15.4. `reports_list`

**Request:** общие фильтры + `sort`, `page`, `limit`.

| Поле    | Правило                                                                                   |
| ------- | ----------------------------------------------------------------------------------------- |
| `sort`  | `"date"` \| `"address"` \| `"department"`, дефолт `"date"`                                |
| `page`  | `max(1, page)`, дефолт 1. Выход за диапазон → пустой `items`, `current_page` как запрошен |
| `limit` | `min(200, max(10, limit))`, дефолт 50                                                     |

**Сортировка (только серверная):**

| `sort`       | ORDER BY                                                       |
| ------------ | -------------------------------------------------------------- |
| `date`       | `call_date DESC`, при `date_type="closed"` — `call_date2 DESC` |
| `address`    | ключ из **чистых имён** (см. ниже), пустой ключ — в конец      |
| `department` | `call_department ASC`                                          |

Хвост всегда `c.call_id DESC`.

**Ключ адреса** — паритет `Address::sortKey`, собирается только при `sort="address"`:

```
LEFT JOIN lift_city   ci ON ci.id = c.address_city
LEFT JOIN lift_street st ON st.id = c.address_street
LEFT JOIN lift_home   h  ON h.id  = c.address_home
LEFT JOIN lift_object o  ON o.id  = c.address_lift

LOWER(CONCAT_WS(' ', NULLIF(ci.city_name,''), NULLIF(st.street_name,''),
                     NULLIF(h.home_name,''),  NULLIF(o.object_name,''))) AS address_sort_key

ORDER BY (address_sort_key = '') ASC, address_sort_key ASC, c.call_id DESC
```

JOIN справочников — **без фильтра `vis`**: скрытые позже улица/дом/лифт обязаны остаться в истории. Это осознанно расходится с `loadAddress`.

## 15.5. `reports_export`

**Request:** общие фильтры + `format: "csv"` (единственный поддерживаемый), без `page`/`limit`.

```json
{
  "status": "ok",
  "data": {
    "file_base64": "…",
    "filename": "report_2026-11-19.csv",
    "mime_type": "text/csv",
    "rows_count": 150
  }
}
```

Пустая выборка → `{"status":"ok","data":null,"message":"По вашему запросу ничего не найдено"}`.

**Лимит:** выборка `LIMIT 2001`. Ровно 2000 — валидно; 2001-я строка → `invalid_input`, `reason: export_too_many_rows`. `LIMIT 2000` не позволяет отличить «ровно 2000» от «больше» — поэтому 2001.

**Rate limit:** 1 экспорт на пользователя тенанта в 30 с. Файловый флаг **вне webroot**, ключ tenant+user, `flock`, TTL 30 с. Отказ → `rate_limited`, `reason: rate_limited`, **`retry_after` плоско на верхнем уровне** (остаток окна, минимум 1).

**CSV:** UTF-8 с BOM, разделитель `;`, кавычки `"`, escape-параметр `fputcsv` пустой. Переносы внутри ячеек `\n`. Защита от формул: значение, начинающееся с `=`, `+`, `-`, `@`, получает префикс `'`. Даты — `date('d.m.Y H:i', ts)`, зона МСК из `bootstrap.php`. Имя файла — дата генерации в МСК.

| №   | Заголовок      | Содержимое                                                                                      |
| --- | -------------- | ----------------------------------------------------------------------------------------------- |
| 1   | ID             | `call_id`                                                                                       |
| 2   | Адрес          | `fullAddress` `\n` дата создания `·` `call_first_name`                                          |
| 3   | Описание       | `call_details`                                                                                  |
| 4   | Закрытие       | дата закрытия `\n` кто закрыл; открыта → `—`                                                    |
| 5–7 | Отв. 1 / 2 / 3 | имя `\n` `Статус: <суффикс> · <дата>`; слот пуст → `—`; статус 0/null → `Не уведомлен` без даты |

**Суффиксы — §1.3, без эмодзи:** `по телефону`, `онлайн`, `в телеграм`, `в макс`, `в вк`, `по смс`, `по email`. Тот же набор, что рисует `body-render` в таблице ⇒ UI и CSV не расходятся. `getStatusWord()` из карточки **не используется** — он даёт «web онлайн», третью формулировку.

**Форматирование не заявляется:** «wrap text включён», «автофильтр активен» из приёмки убраны — CSV метаданных форматирования не хранит. Переносится в волну 3 (XLSX).

## 15.6. Права — проверяются на сервере

**Отход от §20 для этого модуля:** online-путь отчётов права проверяет с первого дня. Иначе инженер и гость получили бы выгрузку всего тенанта.

| Роль                          | Видимость                                                     | Фильтр `staff_id` в UI |
| ----------------------------- | ------------------------------------------------------------- | ---------------------- |
| `administrator`, `dispatcher` | все заявки                                                    | ✅                     |
| `engineer`                    | только свои: OR по `call_staff`, `call_staff2`, `call_staff3` | ❌                     |
| `guest`, `reserved`           | **`forbidden`, `reason: no_rights`** на все четыре экшена     | ❌                     |

Источник истины — `CallScope::readAll()` / `isAssigned()`. **Обхода по `user_position` нет:** прораб уже нормализован в `dispatcher` (§19.5), а частный случай в отчётах сломал бы инвариант «видимость в списке = видимость карточки». Кому нужен широкий доступ — выдаётся `user_read_all_calls`.

`staff_id` у инженера не игнорируется молча: условие пересекается с его областью через AND.

Меню строится сервером по `can_view_reports` (`admin ∥ dispatcher`). Инженер с `position=foreman` и ролью `engineer` пункта не увидит, но доступ по прямой ссылке получит — известное расхождение, волной 1 не расширяем.

## 15.7. Офлайн

Отчёты работают только онлайн. `navigator.onLine === false` → превентивная заглушка «Отчёты доступны только при наличии интернета», кнопки заблокированы. Обращений к `outbox` нет; кэш справочников (`address_flat`) использовать разрешено.

Отказ канала определяется **по `resp.offline === true`**, не по кодам:

| Ответ                                                      | Поведение                                                               |
| ---------------------------------------------------------- | ----------------------------------------------------------------------- |
| `offline === true`                                         | заглушка «нет сети», **последние успешные данные не очищаются** (§16.5) |
| `code:"aborted"` без `offline` (ручная отмена при unmount) | молча, не ошибка                                                        |
| `http_*` (без `offline`)                                   | тост ошибки, не офлайн-заглушка                                         |
| `_authLost`                                                | выход без своего тоста — уводит `main.js`                               |

## 15.8. Связь с офлайн-синхронизацией

`SyncManager` не используется. Все запросы напрямую в `api.php`, тег `"reports"`, `abortTag("reports")` в `unmount`. Префиксы `offline_` в отчёты не попадают.

## 15.9. Ограничения реализации (SQL / PHP)

1. **`PDO::ATTR_EMULATE_PREPARES = false`** ⇒ повтор одного именованного плейсхолдера запрещён (`HY093`). Фильтр по ответственному и область чтения используют **уникальные имена** `:s1/:s2/:s3`, значения дублируются в массиве params.
2. `LIMIT` / `OFFSET` подставляются числами после `(int)` — валидированы, инъекции нет;绑定 строкой в нативном режиме ломается.
3. Все JOIN — **LEFT**, без `vis`. Внешних ключей в БД нет, осиротевшие ссылки штатны.
4. `set_error_handler` превращает warning/notice в исключение ⇒ доступ к массивам только через `??`, приведения явные (`declare(strict_types=1)`).
5. Отчёты сравнивают int-колонки, `NOW()`/`FROM_UNIXTIME` не используют ⇒ долг `@@session.time_zone = SYSTEM` (§1.2) их не задевает. Форматирование в строку — `date()`, зона МСК задана в `bootstrap.php`.
6. Единый `ReportsQueryBuilder` для трёх экшенов: агрегаты, список и экспорт обязаны работать на идентичной выборке.

## 18. Мультитенантность

### 18.1. Определение тенанта ✅

**Единственный способ — заголовок `Host`.** Ни `X-Tenant`, ни JWT `tenant_id`, ни `org_key` в резолве не участвуют.

Алгоритм:

1. `HTTP_HOST`, отбросить порт, привести к нижнему регистру.
2. Разделить по `.`, требуется не менее трёх частей.
3. Поддомен = первая часть.
4. Не входит в зарезервированные: `www`, `api`, `admin`, `mail`, `test`, `dev`, `staging`, `docs`, `cp`, `ftp`, `mysql`, `ns1`, `ns2`, `org`.
5. Соответствует `/^[a-z0-9][a-z0-9-]{0,30}$/`.
6. Поиск в master-реестре по поддомену.

Каждый тенант — **отдельная БД**. Соединение устанавливается через `DB::forTenant`.

## 19. Аутентификация

Точка входа `/auth.php`, экшен в query: `?action=login|refresh|logout|validate`. Полная модель сессий — `AUTH_PROTOCOL.md` §0 (Трек А).

### 19.1. `login` ✅

Request: `POST /auth.php?action=login`

```json
{
  "name": "dispatcher",
  "pname": "123456",
  "webGL": "<fingerprint>",
  "user_id": 3,
  "autoLogin": true
}
```

`user_id` опционален: при передаче поиск по ID, иначе по `name`. Если `name` содержит `@` — поиск по `user_email`, иначе по `user_login`. Пароль обязателен. `autoLogin` принимается, на срок жизни токенов не влияет.

Response:

```json
{
  "status": "ok",
  "access_token": "<64 hex>",
  "expires_at": 1761221700,
  "user": {
    "id": 3,
    "name": "Иван",
    "surname": "Иванов",
    "patronymic": "Иванович",
    "display_name": "Иванов Иван Иванович",
    "role": "dispatcher",
    "user_add_call": 0,
    "user_read_all_calls": 0,
    "user_position": "foreman"
  }
}
```

#### Объект `user` — единый для `login`, `refresh`, `validate`

| Поле                  | Тип            | Источник                            |
| --------------------- | -------------- | ----------------------------------- |
| `id`                  | int            | `user_id`                           |
| `name`                | string         | `user_firstname ?: user_name`       |
| `surname`             | string \| null | `user_surname`, пустое → null       |
| `patronymic`          | string \| null | `user_patronymic`, пустое → null    |
| `display_name`        | string         | `user_name` целиком                 |
| `role`                | string         | `user_role` с нормализацией (§19.5) |
| `user_add_call`       | int 0 \| 1     | флаг создания заявок                |
| `user_read_all_calls` | int 0 \| 1     | флаг чтения всех заявок             |
| `user_position`       | string \| null | должность, **не нормализуется**     |

⚠️ **Изменение контракта `name`.** До B1.6 поле всегда содержало полное ФИО. Теперь при заполненном `user_firstname` там только имя. Клиент, показывающий `user.name` как ФИО в шапке, обязан перейти на `display_name`. Для незаполненных записей поведение прежнее (fallback на `user_name`), поэтому дефект проявится только после наполнения ФИО через B4.

Флаги — `int 0|1`, не `bool`: колонки `tinyint(1)`, приведение к `bool` живёт внутри `CallPolicy`.

#### Побочные эффекты

- `family_id` (32 hex) — уникален **на логин**, не на пользователя;
- одна запись в `lift_access_tokens` (единственная генерация access);
- одна запись в `lift_refresh_tokens`;
- cookie `lift_refresh`: `Secure`, `HttpOnly`, `SameSite=Strict`, `path=/`, `Max-Age=2592000`, без `Domain` (host-only);
- автомиграция устаревшего хэша пароля на bcrypt.

Legacy-колонки `api_token` / `api_token_expires` / `webgl_info_spa` не читаются и не пишутся.

Ошибки: `invalid_input` (пустой пароль), `invalid_credentials`, `user_blocked`.
⚠️ Ограничение попыток входа отсутствует — перебор не блокируется.

### 19.2. `refresh` ✅

Request: `POST /auth.php?action=refresh`, тело `{}`, cookie `lift_refresh`.
Response: идентичен `login`, **cookie обновляется всегда**.

Ротация обязательна: предъявленный токен гасится, преемник выпускается в той же семье.

| Исход                                  | Код             | `reason`        | Клиент                                   |
| -------------------------------------- | --------------- | --------------- | ---------------------------------------- |
| Успех, в т.ч. повтор внутри grace 30 с | `ok`            | —               | новый access + новая cookie              |
| Cookie нет                             | `missing_token` | —               | `auth:lost` → логин                      |
| Токен не найден или истёк              | `token_expired` | —               | `auth:lost` → логин                      |
| Повтор ротированного вне grace         | `token_invalid` | `refresh_reuse` | `auth:lost` → логин                      |
| Гонка не разрешилась за 2 попытки      | `rate_limited`  | `refresh_busy`  | транспорт, повтор через `retry_after: 1` |
| Пользователь заблокирован              | `user_blocked`  | —               | `auth:lost` → логин                      |

`retry_after` передаётся плоско на верхнем уровне (§16.1).

**Отзыв при краже.** Исход `refresh_reuse` удаляет всю семью **и все access-токены пользователя**. Ранее выданный access перестаёт работать немедленно. На других устройствах семья цела: их access умрёт, клиент получит 401 и обновится без разлогина.

`refresh_busy` — не потеря сессии. Клиент обязан трактовать его как транспорт, а не как отказ авторизации.

### 19.3. Срок жизни access — исправлено ✅

Дефект v4.3 («через 2 часа после логина любой refresh падает») устранён: `AuthService::validate` больше не сравнивает `lift_users.api_token_expires` с `time()`. Срок проверяется только в SQL — `findByAccessToken` фильтрует `a.expires_at > NOW()`.

Подтверждено данными продакшн-цепочки: преемник выпущен через 2 ч 00 м 31 с после предка, ротация прошла успешно.

### 19.4. Defects v4.3 — статус

| Дефект v4.3                        | Статус                                               |
| ---------------------------------- | ---------------------------------------------------- |
| Refresh не ротируется              | ✅ исправлено: семьи + grace + CAS                   |
| Logout не отзывает access          | ✅ исправлено: предъявленный + вся семья refresh     |
| Двойная генерация access           | ✅ исправлено: единственная генерация в контроллере  |

Осталось: ограничение попыток входа (§19.1), `device_mismatch` (§16.4).

### 19.5. Вычисление роли ✅

Источник — `user_role`. Нормализация при чтении: `mechanic → engineer`, `foreman → dispatcher`. Данные не меняются.

Fallback только при пустом или `guest`, и только по явным флагам:

| Условие                       | Роль          |
| ----------------------------- | ------------- |
| `user_localadmin` истинно     | administrator |
| `user_disppermission` истинно | dispatcher    |
| иначе                         | guest         |

Fallback по `user_level` удалён полностью: необнулённый уровень 0 давал администратора.

`user_position` — бизнес-тип, не роль доступа, не нормализуется. Пустая строка и NULL отдаются как `null`.

### 19.6. `logout` ✅

Request: `POST /auth.php?action=logout`, тело `{}`, cookie `lift_refresh`, опционально `Authorization: Bearer`.
Response: `{ "status": "ok", "message": "Вы вышли из системы" }`

Порядок: удалить предъявленный access → найти семью по cookie (без фильтра по срокам) → удалить всю семью → снять cookie теми же параметрами.

Отсутствие cookie не мешает удалить access и снять cookie. Остальные access дотекают 2 часа — принятое решение, не дефект.

### 19.7. `validate` ✅

Request: `POST /auth.php?action=validate`, заголовок `Authorization: Bearer <access>`.
Response: `{ "status": "ok", "user": {…} }` — объект из §19.1.

Пользователь читается из БД на каждом запросе, роль и флаги пересобираются. Смена роли и `user_block` действуют со следующего запроса.

### 19.8. Сроки жизни

| Сущность   | TTL     | Константа                              | Хранение                                               |
| ---------- | ------- | -------------------------------------- | ------------------------------------------------------ |
| access     | 7200 с  | `AuthService::ACCESS_TTL`              | `lift_access_tokens`; на клиенте только память вкладки |
| refresh    | 30 дней | `AuthService::REFRESH_TTL`             | `lift_refresh_tokens` + HttpOnly cookie                |
| grace-окно | 30 с    | `AuthService::REFRESH_REUSE_GRACE_SEC` | —                                                      |

Срок преемника считается от момента ротации, не наследуется. Cookie и строка в БД считаются от одной константы.

````
# 📡 API Protocol v6.1: Модуль отчетов

## 0. Обзор

Модуль отчетов добавляет четыре новых action'а к существующему `api.php`:
- `reports_filters_data` — справочники для UI
- `reports_stats` — агрегаты для графиков
- `reports_list` — таблица с пагинацией
- `reports_export` — выгрузка в CSV

**Все отчеты работают строго в онлайн-режиме.** Офлайн-синхронизация не поддерживается.

## 1. Общие правила

### 1.1. Авторизация
Все запросы требуют `Authorization: Bearer <token>`. Публичных endpoint'ов нет.

### 1.2. Формат ответа
Все ответы оборачиваются в `{"status": "ok", "data": {...}}` согласно §0.3 основного протокола.

### 1.3. Единый объект фильтров
Все три endpoint'а (`reports_stats`, `reports_list`, `reports_export`) принимают **идентичный объект фильтров**. Отличается только наличие `page`/`limit` в `reports_list` и `format` в `reports_export`.

## 2. Контракты endpoint'ов

### 2.1. `reports_filters_data`

**Назначение:** Справочники для UI (отделы, сотрудники, города).

**Запрос:**
```json
POST /api.php
{
  "action": "reports_filters_data"
}
````

**Ответ:**

```json
{
  "status": "ok",
  "data": {
    "departments": [{ "id": "22", "name": "Электромеханики" }],
    "staff": [{ "id": 1, "name": "Иванов", "position": "dispatcher" }],
```

**Назначение:** Выгрузка в CSV.

**Запрос:**

```json
  "action": "reports_export",
  "format": "csv",
  "date_from": 1699000000,
  "date_to": 1699500000,
```

**Ответ (успех):**

```json
{
  "status": "ok",
  "data": {
    "file_base64": "SWQ70JHRg9C6...",
    "filename": "report_2026-11-10.csv",
    "mime_type": "text/csv",
    "rows_count": 150
  }
```

**Ответ (пустая выборка):**

```json
{
  "status": "ok",
  "data": null,
  "message": "По вашему запросу ничего не найдено"
}
```

**Ограничения:**

- **Жесткий лимит: 2000 строк** на уровне SQL
- При превышении → ошибка `export_too_many_rows` с подсказкой "Сузьте период поиска"
- **Rate limit:** 1 экспорт на пользователя в 30 секунд

**Формат CSV:**

- Кодировка: UTF-8 с BOM
- Разделитель: `;` (русская локаль Excel)
- Переносы строк внутри ячеек: `\n`
- Wrap text: включен

**Структура колонок:**
| № | Заголовок | Содержимое |
|---|---|---|
| 1 | ID | call_id |
| 2 | Адрес | Полный адрес\nДата создания · Создатель |
| 3 | Описание | call_details |
| 4 | Закрытие | Дата закрытия\nКто закрыл или — если открыта |
| 5 | Отв. 1 | Имя\nСтатус: · Дата |
| 6 | Отв. 2 | (если есть) |
| 7 | Отв. 3 | (если есть) |

## 3. Валидация и ошибки

### 3.1. Невалидные даты

Если `date_from > date_to` или `date_to > end_of_today` → `{"status": "ok", "data": null}` (не исключение).

### 3.2. Период > 90 дней

```json
{
  "status": "error",
  "code": "invalid_input",
  "reason": "date_range_too_long",
  "message": "Период не может превышать 90 дней"
}
```

### 3.3. Экспорт > 2000 строк

```json
{
  "status": "error",
  "code": "invalid_input",
  "reason": "export_too_many_rows",
  "message": "Слишком много результатов. Сузьте период поиска."
}
```

### 3.4. Rate limit на экспорт

```json
{
  "status": "error",
  "code": "rate_limited",
  "reason": "rate_limited",
  "message": "Слишком много запросов. Повторите позже.",
  "details": { "retry_after": 30 }
}
```

### 3.5. Полнотекстовый поиск без адреса

Если `details_text` или `solution_text` заданы без `home_id`/`object_id` → сервер **игнорирует** фильтры (не ошибка).

## 4. Семантика фильтров

### 4.1. `department_ids` (включающий)

Массив ID отделов. Если пустой → сервер использует все видимые отделы.

### 4.2. `city_only`

Если `true` → игнорируем `street_id`, `home_id`, `object_id`.

### 4.3. `is_emergency`

Если `true` → только заявки с `type_report = 0`.

### 4.4. `staff_id`

Фильтр по ответственному: `(call_staff = :id OR call_staff2 = :id OR call_staff3 = :id)`.

### 4.5. Часовой пояс

Клиент строит `date_from`/`date_to` как Unix-секунды **по Москве** (00:00:00 и 23:59:59). Сервер не прибавляет 86399.

## 5. Ролевая модель

- **Полный доступ к сводке** (`reports_stats`): все роли (кроме `guest`)
- **Доступ к списку** (`reports_list`): все роли с фильтрацией по своим заявкам для `mechanic`
- **Фильтр `staff_id` в UI:** виден только ролям `dispatcher`, `admin`, `foreman`
- **Экспорт** (`reports_export`): те же права, что и `reports_list`

## 6. Связь с существующими компонентами

Отчеты **не используют** офлайн-синхронизацию. Все запросы идут напрямую в `api.php`, минуя `SyncManager`.
