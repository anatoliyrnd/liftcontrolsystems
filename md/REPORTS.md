С чего начать в первую очередь (Приоритизация):

Быстрые победы: Индексы БД и кэширование справочников (сильно ускорит систему, почти не требует изменения UI).

UX-улучшения: Drill-down из графиков (свяжет Сводку и Результаты в единый сценарий).

Долгосрочные: Асинхронный экспорт больших данных и материализованные агрегаты (подготовка к росту базы).

# Drill-down (Проваливание) из графиков Сводки:

Проблема: Графики на вкладке «Сводка» статичны. Если диспетчер видит, что в отделе «Электромеханики» 50 открытых заявок, он не может быстро понять, что это за заявки.

Алгоритм: Сделать SVG-сегменты (донат) и строки баров кликабельными. При клике на «Электромеханики» формируется payload: { department*ids: [id*отдела], status: 'open', date_type: 'created', period: 'all_time' }. Этот payload через существующий механизм localStorage и publishResultRequest отправляется в окно результатов. Пользователь сразу видит детальный список.

# Асинхронный экспорт больших выборок (Background Jobs):

Проблема: Ограничение в 2000 строк — вынужденная мера, чтобы не вешать PHP-процесс на генерации гигантского XLSX.

Алгоритм: Если выборка > 2000 строк, сервер не генерирует файл сразу. Он создает задачу в очереди (например, в таблице БД export_tasks), возвращает клиенту status: "processing" и task_id. Фоновый воркер (Cron/демон) генерирует файл, кладет его в защищенную папку и обновляет статус задачи на done. Фронтенд периодически опрашивает статус или получает уведомление через WebSocket, после чего скачивает файл.

# Материализованные агрегаты для исторических данных:

Проблема: Построение сводки (reports_summary) за прошлый год будет требовать тяжелых запросов с GROUP BY по миллионам строк.

Алгоритм: Создать таблицу daily_stats (дата, отдел, город, кол-во созданных, кол-во закрытых, суммарное время закрытия). Раз в сутки (ночью) скрипт агрегирует данные за прошедший день и пишет в эту таблицу. При запросе статистики за периоды старше 1 месяца сервер читает данные из этой быстрой таблицы, а не из основной таблицы заявок.

Индексы БД:

Согласно вашему документу, нет индексов на address_home, address_street, call_staff2/3. Это критично для расширенного поиска. Создание композитных индексов на эти поля — самое быстрое алгоритмическое улучшение производительности фильтрации.

3. Аналитика и бизнес-ценность (Логика метрик)
   Сравнение периодов (Period-over-Period):

Алгоритм: На вкладке «Сводка» рядом с текущими цифрами показывать дельту (например, «Закрыто: 45 (▲ +10% к прошлой неделе)»). На бэкенде в метод getSummary добавить флаг compare: true. Если он передан, сервер вычисляет метрики не только за текущий пресет, но и за предыдущий аналогичный период, и возвращает разницу.

Тепловая карта нагрузки (Heatmap):

Алгоритм: Добавить новый тип графика (на основе CSS Grid, без тяжелых библиотек). По осям: дни недели (Пн-Вс) и часы (00:00 - 23:00). Интенсивность ячейки = количество созданных заявок. Это позволит диспетчерам видеть пиковые часы нагрузки и правильно распределять смены.

Анализ «Застреваний» по ответственным:

Алгоритм: Сейчас метрика slow_entrapment показывает общую цифру. Добавить логику группировки этих заявок по staff_id (кто был назначен). Это позволит выявить сотрудников, у которых заявки систематически висят дольше 50 минут, для проведения с ними работы.

Умный Retry для экспорта:

Алгоритм: Если сервер вернул rate_limited с retryAfterSec, текущая логика просто показывает ошибку. Можно улучшить UX: если пользователь пытается нажать кнопку повторно во время кулдауна, показывать не просто тост, а визуально менять текст на кнопке на «Повторить через 12 с», с обратным отсчетом.

## 17. Уровни доступа к отчётам

**Область:** только пять экшенов `reports_*`. Уровень — свойство **тенанта**,
не пользователя; выдаётся супер-админом SaaS, администратор организации
изменить его не может.

### 17.1. Шкала и хранение

| Уровень    | Ранг | Подпись     |
| :--------- | :--- | :---------- |
| `light`    | 1    | Лёгкий      |
| `standard` | 2    | Стандарт    |
| `extended` | 3    | Расширенный |

Проверка — сравнение рангов, не три независимых флага: новый уровень
добавляется строкой в `RANKS` и картами `ReportsAccess`, вызывающие места
не меняются.

Центральная БД, таблица `organizations`:

| Колонка              | Тип                                   | Дефолт       | Назначение                        |
| :------------------- | :------------------------------------ | :----------- | :-------------------------------- |
| `reports_level`      | `ENUM('light','standard','extended')` | `'standard'` | текстовый уровень                 |
| `reports_access_rev` | `INT UNSIGNED`                        | `1`          | монотонная ревизия для пропагации |

`Registry::findBySubdomain()` — `SELECT *`, колонки доезжают без правки SQL.
Нормализация одна — в `Tenant::fromRequest()` через `ReportsAccess::normalizeLevel()`.

**Fail-closed:** неизвестное значение или `NULL` → `light` + `Logger::warning`.
`NULL` возможен только при выкатке кода раньше ALTER — порядок в 17.14 обязателен.
Неизвестный ключ фичи/группы в коде → `\InvalidArgumentException`: гейт добавили,
ключ в карту забыли — способность не должна молча утечь в `standard`.

### 17.2. Способности (булевы)

| Ключ           | light    | standard | extended |
| :------------- | :------- | :------- | :------- |
| `summary`      | 🔒 тизер | ✅       | ✅       |
| `export_csv`   | 🔒       | ✅       | ✅       |
| `export_print` | 🔒       | ✅       | ✅       |
| `export_xlsx`  | 🔒       | 🔒       | ✅       |

Комментарии в XLSX отдельным ключом **не выделены** — часть формата (§9.2),

он получается через «Сохранить как PDF» в диалоге печати (§4), серверного пути нет.

Поиск по ID способностью **не является** — см. инвариант 2 в 17.10.

### 17.3. Группы фильтров

| Группа          | Ключи payload                                  | light | standard | extended |
| :-------------- | :--------------------------------------------- | :---- | :------- | :------- |
| `date`          | `date_from`, `date_to`, `date_type`            | ✅    | ✅       | ✅       |
| `address`       | `city_id`, `street_id`, `home_id`, `object_id` | ✅    | ✅       | ✅       |
| `sort`          | `sort`                                         | ✅    | ✅       | ✅       |
| `address_multi` | `city_ids`, `city_only`                        | ❌    | ✅       | ✅       |
| `department`    | `department_ids`                               | ❌    | ✅       | ✅       |
| `status`        | `status`                                       | ❌    | ✅       | ✅       |
| `staff`         | `staff_id`                                     | ❌    | ✅       | ✅       |
| `text`          | `details_text`, `solution_text`                | ❌    | ❌       | ✅       |

**Отказ только явный.** Дефолты (`status='all'`, `staff_id=0`, пустые тексты,
`city_only=false`, пустые списки) проходят молча: клиент заблокированной группы
их просто не рендерит. Молчаливое игнорирование непустого значения запрещено —
оно вернуло бы выборку шире запрошенной.

Заблокированная группа на клиенте приводится к дефолту **и в UI**: иначе radio
«Открытые» показывал бы условие, которого в payload нет. `department_ids` у light
уезжает `[]` («условия по отделу нет», §4), а не список всех галочек.

### 17.4. Лимиты уровня

| Параметр          | light         | standard | extended |
| :---------------- | :------------ | :------- | :------- |
| `max_period_days` | 31            | 90       | 90       |
| `max_rows`        | 100           | 2000     | 2000     |
| `address_scope`   | `object_only` | `any`    | `any`    |

`max_rows` — потолок **экспорта** для standard/extended и потолок **списка** для light.
Список standard/extended остаётся пагинированным без потолка (поведение v6.5):
ввести 2000 на список значило бы даунгрейд существующего поведения.

`object_only`: обязателен `object_id > 0`. Дом и город как фильтр запрещены;
`city_only=true` отсекается группой `address_multi` раньше.

### 17.5. Порядок проверок и ошибки

Порядок фиксирован, дешёвое раньше дорогого:

```
роль → булева способность → группы фильтров → адрес-скоуп → даты → строки → лимитер
```

Отказ по уровню не сжигает окно бакета (§9.1) и не зависит от мусорных дат.

| Ситуация                                    | code            | reason                  | Детали                       |
| :------------------------------------------ | :-------------- | :---------------------- | :--------------------------- |
| Способность недоступна                      | `forbidden`     | `feature_not_available` | `feature` плоско             |
| Заблокированная группа с непустым значением | `forbidden`     | `feature_not_available` | `feature` = имя группы       |
| light без конкретного лифта                 | `invalid_input` | `object_required`       | —                            |
| Период выше потолка уровня                  | `invalid_input` | `date_range_too_long`   | текст динамический: «N дней» |
| Строк больше потолка                        | `invalid_input` | `export_too_many_rows`  | переиспользован, приёмка №40 |

`feature` кладётся через `details` и уезжает на верхний уровень
(API_PROTOCOL §16.1, прецедент `retry_after`). Новых `ErrorCode` не заведено.


Матрица уровней живёт **только** в `App/Support/ReportsAccess.php`. В `config.js`
(`REPORTS.ACCESS`) — имена ключей, подписи уровней и тексты замков; состава уровней
там нет. Старые клиенты поля игнорируют, контракт не ломается.

### 17.7. Пропагация изменения

| Слой       | Механизм                                                                                                                                                                                                |
| :--------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| БД         | смена уровня = один `UPDATE`, бампающий обе колонки                                                                                                                                                     |
| Сервер     | `getNotifications`: `versions.reports_access = tenant.reportsAccessRev`. Tenant уже в памяти после `create()` — ноль дополнительных запросов                                                            |
| `outdated` | **не мерджится**: клиент его не читает, драйвер — `versions` против `applied`                                                                                                                           |
| Поллер     | `LAYERS` += `reports_access`, `LAYER_EVENT` → `sync:fetch_reports_access`. `emptyVersions()`, персистентность `syncAppliedVersions`, cooldown слоя и сброс при смене пользователя построены от `LAYERS` |
| `main.js`  | шестой хендлер — копия staff-хендлера: `menuManager.initialize()` + `sync:applied`                                                                                                                      |
| Применение | `menu-manager.initialize()` — единственная точка распаковки config; `userStore.setReportsAccess(...)` рядом с `setRole`                                                                                 |
| Событие    | `reports:access` диспатчится **только при изменении** набора                                                                                                                                            |

**Ревизия, а не ранг уровня:** ранг (1…3) пропустил бы понижение по правилу
`seen <= applied`. Rev монотонен в обе стороны.

Событие только при изменении обязательно: `initialize()` вызывается и по bump
`staff`/`dicts`, а безусловная пересборка `filtersView` теряла бы введённые фильтры.

Поллер стартует по `isAuth` без standalone-guard, поэтому уровень доезжает и в
служебное окно результатов — без F5.

### 17.8. Поведение клиента

| Элемент                     | Поведение                                                                                                                                |
| :-------------------------- | :--------------------------------------------------------------------------------------------------------------------------------------- |
| Сводка у light              | статичный тизер: плитки «—», подписи из `REPORTS.ACCESS.TEASER_TILES`, баннер. **Запрос не уходит.** Прямой вызов экшена отсекает сервер |
| Замки                       | класс `.locked` + `disabled` + `title`; видимый 🔒 — основной носитель смысла                                                            |
| Кнопки выгрузки             | замок вплетён в `disabled` внутри `_syncExport()`; `finally` XLSX зовёт его же, а не `btn.disabled = false`                              |
| Гейты в обработчиках        | дублируются в начале `_onExport`/`_onPrint`/`_onXlsx`; в печати — **до** `window.open`                                                   |
| Адрес у light               | пикер `mode: "elevator"`; обязательность лифта продублирована в `validate()` — snapshot может восстановить дом                           |
| Потолок периода             | из `access.maxRangeDays`; `REPORTS.MAX_RANGE_DAYS` — фолбэк                                                                              |
| Смена уровня на лету        | `reports-controller` пересобирает `filtersView` (лимиты зашиты при создании) с сохранением snapshot; сводка при понижении уничтожается   |
| Дефолт при отсутствии полей | замков нет: сервер без §17 не гейтит ничего, UI обязан совпадать с его поведением                                                        |

**R1.** `city_only` сворачивает поле поиска адреса (`picker.setSearchCollapsed`)
и сбрасывает выбор ниже города, **сохраняя `city_id`** — иначе `city_only=true`
уехал бы без города и фильтр расширился до всего тенанта. Разворачивание список
не раскрывает (`autoOpen:false`).

**R2.** Фокус поля поиска открывает список при выборе дома (`object_id == null`).
Ранний выход `select()` оставлен только для выбора лифта: клик по полю с полным
адресом по-прежнему выделяет текст.

### 17.10. Инварианты

1. **Уровень ⊥ область чтения.** Тариф не меняет видимость заявок ни в одну
   сторону. `CallScope` об уровнях не знает.
2. **Поиск по ID вне гейта.** Вкладка byId ведёт на `#/ticket/:id`, экшен `ticket`
   обслуживает `CallScope::canView`. Ключа `search_by_id` в реестре нет — мёртвых
   ключей не плодим. Вкладка не блокируется никогда.
3. **Область действия гейта** — только `reports_*`. `ticket`, `open`, `close`,
   `loadAddress` не гейтятся: иначе апгрейд тарифа ломал бы журнал.
4. **Отказ только явный**, дефолты молча.
5. **Fail-closed на сервере, отсутствие гейта на клиенте** при отсутствии полей —
   разные слои, не расхождение.
6. **Матрица одна** — серверная; клиент рендерит присланное.
7. `reports_filters_data` открыт всем уровням: словари и так в `config.staff_list`.
8. Демо-тенант получает уровень колонкой, исключений в `DemoGuard` нет.
9. **No-downgrade:** потолок списка только у light, поведение v6.5 сохранено.
10. Тизер не является защитой — защиту даёт серверный 403.

### 17.11. Контракт админпанели тенантов

| Правило        | Формулировка                                                                                           |
| :------------- | :----------------------------------------------------------------------------------------------------- |
| Ввод уровня    | select по allowlist трёх значений, свободный ввод запрещён                                             |
| Ревизия        | read-only бейдж, руками не редактируется                                                               |
| Смена          | один `UPDATE`, бампающий обе колонки; раздельные statements запрещены                                  |
| Холостая смена | `UPDATE` только при фактическом изменении значения                                                     |
| Даунгрейд      | механизмом поддержан, политика тестового сервера запрещает; UI не блокирует                            |
| Аудит          | `(tenant_id, old_level, new_level, old_rev, new_rev, admin_id, ts)`; rev — ключ идемпотентности записи |

```sql
UPDATE organizations
   SET reports_level = :level,
       reports_access_rev = reports_access_rev + 1
 WHERE id = :tenant_id;
```

Подсказка под селектом: «Уровень применяется ко всем пользователям организации.
Изменение вступает в силу в открытых вкладках автоматически в течение одного
цикла опроса уведомлений; перелогин не требуется».

### 17.13. Долг и ограничения

| Пункт                                                        | Следствие                                                          |
| :----------------------------------------------------------- | :----------------------------------------------------------------- |
| `title` на disabled-кнопке показывается не во всех браузерах | смысл несёт видимый 🔒; при жалобах — перенос подсказки на обёртку |

### 17.14. Выкатка

| Шаг | Действие                                                                                |
| :-- | :-------------------------------------------------------------------------------------- |
| 1   | ALTER + UPDATE в центральной БД (**до** кода)                                           |
| 2   | Бэкенд одним заходом                                                                    |
| 3   | `npm run build` из `frontend/`, выкладка `ui/`                                          |
| 4   | Жёсткая перезагрузка: прод-бандл с хэшем закэширован `sw.js`                            |
| 5   | Проверка: `config` отдаёт три поля; `versions.reports_access` растёт после смены уровня |

Код раньше ALTER → `normalizeLevel(null)` → `light` + warning, отчёты закрыты.
Это осознанный fail-closed, а не баг: порядок шагов обязателен.
