С чего начать в первую очередь (Приоритизация):

Быстрые победы: Индексы БД и кэширование справочников (сильно ускорит систему, почти не требует изменения UI).

UX-улучшения: Drill-down из графиков (свяжет Сводку и Результаты в единый сценарий).

Долгосрочные: Асинхронный экспорт больших данных и материализованные агрегаты (подготовка к росту базы).

# Drill-down (Проваливание) из графиков Сводки:

Проблема: Графики на вкладке «Сводка» статичны. Если диспетчер видит, что в отделе «Электромеханики» 50 открытых заявок, он не может быстро понять, что это за заявки.

Алгоритм: Сделать SVG-сегменты (донат) и строки баров кликабельными. При клике на «Электромеханики» формируется payload: { department*ids: [id*отдела], status: 'open', date_type: 'created', period: 'all_time' }. Этот payload через существующий механизм localStorage и publishResultRequest отправляется в окно результатов. Пользователь сразу видит детальный список.

# Асинхронный экспорт больших выборок (Background Jobs):

Проблема: Ограничение в 2000 строк — вынужденная мера, чтобы не вешать PHP-процесс на генерации гигантского XLSX.

Алгоритм: Если выборка > 2000 строк, сервер не генерирует файл сразу. Он создает задачу в очереди (например, в таблице БД export_tasks), возвращает клиенту status: "processing" и task_id. Фоновый воркер (Cron/демон) генерирует файл, кладет его в защищенную папку и обновляет статус задачи на done. Фронтенд периодически опрашивает статус или получает уведомление через WebSocket, после чего скачивает файл.

# Материализованные агрегаты для исторических данных:

Проблема: Построение сводки (reports_summary) за прошлый год будет требовать тяжелых запросов с GROUP BY по миллионам строк.

Алгоритм: Создать таблицу daily_stats (дата, отдел, город, кол-во созданных, кол-во закрытых, суммарное время закрытия). Раз в сутки (ночью) скрипт агрегирует данные за прошедший день и пишет в эту таблицу. При запросе статистики за периоды старше 1 месяца сервер читает данные из этой быстрой таблицы, а не из основной таблицы заявок.

Индексы БД:

Согласно вашему документу, нет индексов на address_home, address_street, call_staff2/3. Это критично для расширенного поиска. Создание композитных индексов на эти поля — самое быстрое алгоритмическое улучшение производительности фильтрации.

3. Аналитика и бизнес-ценность (Логика метрик)
   Сравнение периодов (Period-over-Period):

Алгоритм: На вкладке «Сводка» рядом с текущими цифрами показывать дельту (например, «Закрыто: 45 (▲ +10% к прошлой неделе)»). На бэкенде в метод getSummary добавить флаг compare: true. Если он передан, сервер вычисляет метрики не только за текущий пресет, но и за предыдущий аналогичный период, и возвращает разницу.

Тепловая карта нагрузки (Heatmap):

Алгоритм: Добавить новый тип графика (на основе CSS Grid, без тяжелых библиотек). По осям: дни недели (Пн-Вс) и часы (00:00 - 23:00). Интенсивность ячейки = количество созданных заявок. Это позволит диспетчерам видеть пиковые часы нагрузки и правильно распределять смены.

Анализ «Застреваний» по ответственным:

Алгоритм: Сейчас метрика slow_entrapment показывает общую цифру. Добавить логику группировки этих заявок по staff_id (кто был назначен). Это позволит выявить сотрудников, у которых заявки систематически висят дольше 50 минут, для проведения с ними работы.

Умный Retry для экспорта:

Алгоритм: Если сервер вернул rate_limited с retryAfterSec, текущая логика просто показывает ошибку. Можно улучшить UX: если пользователь пытается нажать кнопку повторно во время кулдауна, показывать не просто тост, а визуально менять текст на кнопке на «Повторить через 12 с», с обратным отсчетом.

## 16. Уровни доступа к отчётам (v6.6)

Уровень — свойство **тенанта**, не пользователя. Хранится в центральной БД
(`organizations`), читается один раз в `Tenant::fromRequest()`. Матрица уровней
живёт только в `App/Support/ReportsAccess.php`; клиент рендерит присланное.

### 16.1 Шкала

`light`(1) < `standard`(2) < `extended`(3). Проверка — сравнение рангов.
Новый уровень добавляется строкой в `RANKS` и картами, вызывающие места не меняются.

Fail-closed: неизвестный/NULL уровень → `light` + `Logger::warning`. Неизвестный
ключ фичи или группы в коде → `InvalidArgumentException` (дефект разработки:
гейт добавили, ключ в карту забыли — способность не должна утечь в standard).

### 16.2 Способности (булевы)

| Ключ           | light    | standard | extended |
| -------------- | -------- | -------- | -------- |
| `summary`      | 🔒 тизер | ✅       | ✅       |
| `export_csv`   | 🔒       | ✅       | ✅       |
| `export_print` | 🔒       | ✅       | ✅       |
| `export_xlsx`  | 🔒       | 🔒       | ✅       |

`search_by_id` в реестре **нет**: вкладка byId ведёт на `#/ticket/{id}`, её
обслуживает экшен `ticket` вне гейта отчётов. Мёртвых ключей не заводим.

### 16.3 Группы фильтров payload

| Группа          | Ключи                                  | light | standard | extended |
| --------------- | -------------------------------------- | ----- | -------- | -------- |
| `date`          | date_from, date_to, date_type          | ✅    | ✅       | ✅       |
| `address`       | city_id, street_id, home_id, object_id | ✅    | ✅       | ✅       |
| `sort`          | sort                                   | ✅    | ✅       | ✅       |
| `address_multi` | city_ids, city_only                    | ❌    | ✅       | ✅       |
| `department`    | department_ids                         | ❌    | ✅       | ✅       |
| `status`        | status                                 | ❌    | ✅       | ✅       |
| `staff`         | staff_id                               | ❌    | ✅       | ✅       |
| `text`          | details_text, solution_text            | ❌    | ❌       | ✅       |

Отказ **только явный**: значение, отличное от дефолта, вне разрешённой группы.
Дефолты (`status=all`, `staff_id=0`, пустые тексты/списки, `city_only=false`)
проходят молча. Молчаливое игнорирование запрещено — вернуло бы выборку шире
запрошенной.

### 16.4 Лимиты

| Параметр             | light         | standard | extended |
| -------------------- | ------------- | -------- | -------- |
| `max_period_days`    | 31            | 90       | 90       |
| `max_rows` (экспорт) | —             | 2000     | 2000     |
| потолок списка       | 100           | нет      | нет      |
| `address_scope`      | `object_only` | any      | any      |

**No-downgrade:** потолок 2000 относится к экспорту, как в v6.5. Список у
standard/extended остаётся пагинированным без потолка — ввести 2000 на список
значило бы понизить существующее поведение. У light список режется на 100
проверкой `countTotal` **до** выборки.

`object_only`: обязателен `object_id > 0`. Адресная цепочка (город→улица→дом)
остаётся навигацией, дом/город как фильтр запрещены.

### 16.5 Порядок проверок и reason'ы

роль → булева способность → группы/адрес-скоуп → даты → строки → лимитер.

| reason                  | Код           | Когда                                   | Поля                          |
| ----------------------- | ------------- | --------------------------------------- | ----------------------------- |
| `feature_not_available` | forbidden     | способность или группа недоступна       | `feature` (плоско)            |
| `object_required`       | invalid_input | light без конкретного лифта             | —                             |
| `date_range_too_long`   | invalid_input | период выше потолка уровня              | текст динамический («N дней») |
| `export_too_many_rows`  | invalid_input | экспорт > 2000 **и** список light > 100 | —                             |

`export_too_many_rows` переиспользован для списка: сообщение «Сузьте период
поиска» уже принято приёмкой №40, новый reason ломал бы клиент.

Гейт способности стоит **раньше лимитера**: отказ по уровню не сжигает окно
бакета. Лимитер по-прежнему стоит до запроса строк (защита от перебора).

### 16.6 Инварианты

1. Уровень ⊥ `CallScope`: тариф не меняет видимость заявок ни в одну сторону.
   `extended` у engineer не расширяет область чтения.
2. `reports_level` гейтит только пять `reports_*`. `ticket`, `open`, `close`,
   `loadAddress`, `notifications` не трогает — иначе апгрейд ломал бы журнал.
3. `reports_filters_data` открыт всем уровням: словари и так в `config.staff_list`.
4. Реестр — один файл; клиент матрицу не хранит (`config.js` — имена и тексты).
5. Демо-тенант получает уровень колонкой, исключений в `DemoGuard` нет.
6. Клиент при отсутствии полей `reports_*` → без замков (сервер без §16 всё
   разрешает). Серверный fail-closed — другой слой, расхождения нет.

| Поллер       | `LAYERS`/`LAYER_EVENT` += `reports_access`; `emptyVersions`, applied-персистентность, cooldown и сброс при смене пользователя подхватывают ключ сами |
| main.js      | хендлер `sync:fetch_reports_access` → `menuManager.initialize()` → `sync:applied`                                                                    |
| menu-manager | `userStore.setReportsAccess(...)` рядом с `setRole`; событие `reports:access` **только при изменении**                                               |
| Потребители  | reports-controller (тизер/пересборка фильтров), reports-results-controller (`_syncExport`)                                                           |

**Rev, а не ранг уровня:** ранг (light=1…extended=3) пропустил бы понижение по
правилу `seen <= applied`. Rev монотонен в обе стороны.

`outdated` не мерджим: клиент его не читает (только комментарии в коде),
драйвер — `versions` vs `applied`. `AddressCacheService` не изменён.

Поллер стартует по `isAuth` без standalone-guard, поэтому окно результатов
получает обновление уровня так же, как основное окно.

Событие только при изменении обязательно: `initialize()` вызывается и по bump
staff/dicts, безусловная пересборка `filtersView` теряла бы введённые фильтры.

### 16.9 Поведение UI

| Элемент                     | light                                                               | standard         | extended    |
| --------------------------- | ------------------------------------------------------------------- | ---------------- | ----------- |
| Вкладка «Сводка»            | тизер: плитки «—», замок, баннер; **запрос не уходит**              | сводка           | сводка      |
| Вкладка «Расширенный поиск» | адрес до лифта + даты + сортировка; остальные контролы задизейблены | всё кроме текста | всё         |
| Вкладка «Поиск по ID»       | работает                                                            | работает         | работает    |
| Кнопки выгрузки             | все с замком                                                        | XLSX с замком    | все активны |

Тизер — не защита: прямой вызов экшена отсекает серверный гейт. Запрос не
делаем, чтобы не плодить 403 в истории действий.

Замки вплетены в выражение `disabled` внутри `_syncExport` и в `finally`
`_onXlsx`: навешенный один раз замок снимала бы первая же выгрузка.

**R1.** «Только город» сворачивает поле поиска адреса (`setSearchCollapsed`) и
сбрасывает выбор ниже города, **сохраняя `city_id`** — иначе `city_only=true`
уехал бы без города и фильтр расширился до всего тенанта. Флаг живёт в пикере:
видимость `searchWrap` меняют четыре внутренних места.

**R2.** `onfocus` открывает список при выборе дома (`object_id == null`).
Ранний выход `select()` оставлен только для выбора лифта. Дом-выборка из
snapshot в режиме `elevator` получает то же поведение.

Locked-группы приводятся к дефолту **в UI** при создании и в `setValues`:
иначе radio «Открытые» врал бы при payload `status=all`. Payload заблокированной
группы — дефолт сервера (`department_ids: []`).

### 16.10 Контракт админпанели тенантов

| Поле                 | Тип                                   | Дефолт     | Смысл                                       |
| -------------------- | ------------------------------------- | ---------- | ------------------------------------------- |
| `reports_level`      | `ENUM('light','standard','extended')` | `standard` | текстовый уровень, один на тенант           |
| `reports_access_rev` | `INT UNSIGNED`                        | `1`        | цифровая ревизия пропагации, read-only в UI |

Правила интерфейса:

1. Select строго по allowlist трёх значений, свободный ввод запрещён.
2. `rev` — бейдж только для чтения, руками не редактируется.
3. Смена уровня = **один UPDATE**, бампающий обе колонки:
   ```sql
   UPDATE organizations
      SET reports_level = :level,
          reports_access_rev = reports_access_rev + 1
    WHERE id = :tenant_id;
   ```
   Раздельные statements запрещены: уровень без бампа = открытые окна живут
   со старыми замками до F5.
4. UPDATE выполнять только при фактическом изменении значения.
5. Даунгрейд механизмом поддержан; политика тестового сервера его запрещает
   (трём тенантам проставлен `extended`).
6. Аудит: `(tenant_id, old_level, new_level, old_rev, new_rev, admin_id, ts)`.

Подписи: `light` — «Лёгкий», `standard` — «Стандарт», `extended` — «Расширенный».

### 16.13 Не входит в реестр

Индексы БД, кэш справочников, `daily_stats` как механизм, умный retry экспорта —
инфраструктура и UX, тарифом не гейтятся. Drill-down из графиков — UI-only
(шлёт уже доступные базовые экшены), серверного гейта не требует. PDF через
«Сохранить как PDF» — браузерная функция, гейтить нечего.

Ключи будущих фич (`period_comparison`, `heatmap`, `staff_stuck_analysis`,
`drilldown`, лимиты асинхронного экспорта) фиксируются здесь по мере реализации;
в карту вносятся вместе с гейтом, не заранее.
