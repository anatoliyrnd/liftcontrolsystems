# РАЗДЕЛ 1. РЕЗЮМЕ ПРОЕКТА

## 1.1. Цель

Модернизировать существующую систему диспетчеризации лифтов по **двухтрековой стратегии**.

### Трек А (урезанный PHP, временный)

- Доделать существующий PHP-код на `liftcs.ru` с минимальным функционалом для быстрого запуска нового тенанта (l3).
- **Срок жизни:** 6–8 месяцев (до готовности нового бэкенда).
- **Цель:** дать диспетчерам привыкнуть к новому интерфейсу, не дожидаясь полной реализации.
- **Что входит:** авторизация (админ, диспетчер, механик), создание/просмотр/закрытие заявок, комментарии, поиск по номеру, фильтры (лифт, дом, механик, период, исключение Аварийной службы), экспорт PDF/Excel, адресный справочник, справочники типов и приоритетов.
- **Что НЕ входит** (техдолг): группы лифтов, права по группам, контрагенты, офлайн-синхронизация, фото, закрепление механиков как отдельная сущность, массовый перенос лифтов, тонкая настройка прав.

### Трек Б (новый Node.js API, основной)

- Новый API на Node.js + PostgreSQL с **schema-per-tenant** (каждый тенант — отдельная схема PostgreSQL).
- Тенанты на урезанном коде переносятся на новый бэкенд с миграцией **только открытых заявок**. Закрытые заявки остаются в архиве MariaDB.
- Все будущие тенанты создаются сразу на новом бэкенде.

### Общие цели (оба трека)

Внедрить:

1. Систему ролей и прав с четырьмя уровнями контекста (Тенант → Группа → Лифт → Заявка).
2. Разделение «роли доступа» и «должностного типа».
3. Группы лифтов как основную единицу организационного доступа.
4. Закрепление механиков за лифтами (федеральное требование).
5. Адресный контракт (`AddressProvider`) с заделом на общий адресный сервис.
6. Каталог данных лифта с разделением на категории.
7. Контрагентов и управление статусом договора.
8. Логирование и аудит всех действий.
9. Офлайн-синхронизацию.
10. Прокси-роутер для legacy-тенантов.
11. Тенантскую админ-панель на PHP как тонкий клиент к API.

## 1.2. Что НЕ реализуется в текущем этапе

- **Полная миграция legacy-тенантов в первом этапе** — они остаются на `sh.e-rcs.ru`, доступ через прокси на `sh.liftcs.ru`.
- **Параллельная запись** — стратегия «чистого старта» для новых тенантов.
- **Мастер-адресация (общее адресное пространство)** — закладывается архитектурно через интерфейс `AddressProvider`, но `MasterApiAddressProvider` не реализуется.
- **Роль «Связист» как отдельная сущность с полноценной фильтрацией по типу заявки 24** — закладывается через должностной тип `dispatch_equipment_mechanic`, но логика заявок по диспетчерскому оборудованию откладывается.
- **Иерархия групп** — группы плоские, без подгрупп.
- **S3 для фото** — техдолг, локальный диск на старте.

## 1.3. Ключевые принципы

- Жёсткое ядро прав роли + дополнительные права от Админа (гибридная модель).
- Разделение технической роли (`user_role`) и бизнес-типа (`user_position`).
- Policy-слой как единая точка проверки прав.
- Все действия, кроме просмотра, логируются.
- Секретные данные диспетчеризации хранятся отдельно и маскируются.
- Пользователи не удаляются, только блокируются.
- Адресная абстракция для будущей замены на общий сервис.
- **Schema-per-tenant в PostgreSQL** — каждый тенант = отдельная схема (`tenant_sh`, `tenant_l3` и т.д.), подключение переключается по поддомену.
- **Двухтрековая разработка** — Трек А (урезанный PHP для быстрого запуска) и Трек Б (новый API для основной функциональности).
- **Урезанный код как временный мост** — не вкладываем в него лишнего, только то, что нужно для работы l3-тенанта.
- **Архитектура с учётом будущего переезда** — даже в урезанном PHP учитываем, что через 6–8 месяцев перейдём на новый стек.
- **Прокси-роутер только для legacy** — `sh.liftcs.ru` проксирует на `sh.e-rcs.ru`, новые тенанты работают напрямую.
- **Своя БД на тенант** — принцип сохраняется и в новом стеке (через schemas).
- **Бизнес-логика — только в API.** PHP-админка и прокси — тонкие.
- **PostgreSQL — единственный источник истины** для нового API.

# РАЗДЕЛ 3. ЦЕЛЕВАЯ АРХИТЕКТУРА

## 3.1. Система прав: четыре уровня контекста

Каждый запрос к системе проходит проверку прав на одном из четырёх уровней:

```
TENANT (вся организация, определяется поддоменом)
  └── GROUP (группа лифтов: ЖК, дом, территория)
        └── ELEVATOR (конкретный лифт)
              └── CALL (конкретная заявка)
```

### Принцип проверки

При любом действии система проверяет доступ **сверху вниз**, от широкого контекста к узкому:

1. Пользователь — Админ тенанта? → Разрешить.
2. Пользователь имеет доступ к группе заявки/лифта? → Проверить права в группе.
3. Пользователь закреплён за лифтом? → Проверить права по закреплению.
4. Пользователь назначен ответственным на заявку? → Проверить права по заявке.
5. Ни одно условие не выполнено → Отказать.

## 3.2. Роли и должностные типы

### 3.2.1. Разделение концепций

| Концепция               | Поле в БД                      | Назначение                                                                                                               |
| ----------------------- | ------------------------------ | ------------------------------------------------------------------------------------------------------------------------ |
| **Роль доступа**        | `user_role`                    | Техническая роль для API-прав: `administrator`, `dispatcher`, `engineer`, `guest`                                        |
| **Должностной тип**     | `user_position`                | Бизнес-тип: `dispatcher`, `foreman`, `mechanic`, `dispatch_equipment_mechanic`, `electronics_engineer`, `admin`, `guest` |
| **Флаг быстрого входа** | `allow_dispatcher_quick_login` | Разрешён ли показ в списке быстрого входа диспетчера                                                                     |

### 3.2.2. Почему это разделение критично

Прораб функционально является диспетчером с расширенными правами. Если определять его только по роли `dispatcher`, он попадёт в список быстрого входа диспетчера, что недопустимо.

Должностной тип решает эту проблему:

| Пользователь        | `user_role`     | `user_position`               | Попадает в быстрый вход диспетчера? |
| ------------------- | --------------- | ----------------------------- | ----------------------------------- |
| Обычный диспетчер   | `dispatcher`    | `dispatcher`                  | ✅ Да                               |
| Старший диспетчер   | `dispatcher`    | `dispatcher` + доп. права     | ✅ Да (но с расширенными правами)   |
| Прораб              | `dispatcher`    | `foreman`                     | ❌ Нет                              |
| Механик             | `engineer`      | `mechanic`                    | ❌ Нет                              |
| Связист             | `engineer`      | `dispatch_equipment_mechanic` | ❌ Нет                              |
| Инженер-электронщик | `engineer`      | `electronics_engineer`        | ❌ Нет                              |
| Админ               | `administrator` | `admin`                       | ❌ Нет                              |
| Гость               | `guest`         | `guest`                       | ❌ Нет                              |

### 3.2.3. Базовые роли (4 штуки, без изменений)

| Роль            | Описание                                        |
| --------------- | ----------------------------------------------- |
| `administrator` | Полные права на всё в тенанте                   |
| `dispatcher`    | Создаёт и редактирует заявки в своих группах    |
| `engineer`      | Механик. Видит закреплённые лифты и свои заявки |
| `guest`         | Только чтение                                   |

### 3.2.4. Должностные типы (специализации)

| Тип                           | Описание                                                                                                                     | Базовая роль    |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------- | --------------- |
| `dispatcher`                  | Обычный диспетчер                                                                                                            | `dispatcher`    |
| `foreman`                     | Прораб. Начальник над механиками, менеджер по клиентам                                                                       | `dispatcher`    |
| `mechanic`                    | Обычный механик                                                                                                              | `engineer`      |
| `dispatch_equipment_mechanic` | Связист / электромеханик дисп. оборудования (заявки типа 24)                                                                 | `engineer`      |
| `electronics_engineer`        | **Инженер-электронщик.** Механик без закреплённых лифтов. Работает с электроникой / диспетчерским оборудованием (уточняется) | `engineer`      |
| `admin`                       | Администратор организации                                                                                                    | `administrator` |
| `guest`                       | Гость (представитель УК, аудитор)                                                                                            | `guest`         |

**Примечание по `electronics_engineer`:** по сути это механик без закреплённых лифтов, работающий с электроникой/диспетчерским оборудованием. В отличие от `dispatch_equipment_mechanic` (связист), который привязан к заявкам типа 24, инженер-электронщик может привлекаться к более широкому кругу заявок по электронике. Конкретная логика фильтрации заявок для этой должности уточняется в процессе реализации.

### 3.2.5. Специализации через дополнительные права

**Старший диспетчер** = Обычный диспетчер (`user_position = 'dispatcher'`) + дополнительные права, которые выдаёт Админ:

- `can_create_dispatchers` — создавать диспетчеров.
- `can_edit_dispatchers` — изменять диспетчеров.
- `can_block_dispatchers` — блокировать диспетчеров.

Эти права хранятся в `user_group_access.extra_permissions` (JSON) или в отдельных полях `user_group_access` (см. раздел 4.1.2). Старший диспетчер **не является отдельной должностью** — это обычный диспетчер с расширенными правами. Он попадает в быстрый вход диспетчера (по `user_position = 'dispatcher'`), но имеет больше возможностей в админке.

**Прораб** = Диспетчер + дополнительные права:

- Доступ к нескольким группам.
- Закрепление механиков за лифтами.
- Создание пользователей с ролью `engineer` (с доп. правом от Админа).
- Переназначение ответственных в заявках.

**Бригадир** = Механик + дополнительные права на группу:

- Просмотр всех лифтов группы.
- Возможно, закрытие заявок в группе (на усмотрение Админа).

**Связист** = Механик без закреплённых лифтов:

- Работает только с заявками типа «Неисправность дисп. об.» (`type_id=24`).
- Только те заявки, где он назначен ответственным.
- Отдельное закрепление за диспетчерским оборудованием (не за лифтами).

**Инженер-электронщик** = Механик без закреплённых лифтов:

- Работает с электроникой / диспетчерским оборудованием.
- Закрепляется за оборудованием (не за лифтами) через `user_elevator_assignment` с `assignment_type = 'electronics_specialist'` (или `dispatch_specialist` — уточняется).
- Может привлекаться к заявкам по электронике (тип 24 и смежные — уточняется).

## 3.3. Группы лифтов

### 3.3.1. Основные правила

- Каждый лифт **обязан** принадлежать группе.
- Если лифт не назначен в группу — он попадает в системную группу «Без группы» (создаётся автоматически при создании тенанта).
- Группы **плоские**, без иерархии и подгрупп.
- Лимит групп на тенант: **32 по умолчанию** (soft-limit, настраивается в мастер-БД).

### 3.3.2. Кто управляет группами

- Создание/редактирование/удаление групп — только Админ.
- Привязка лифтов к группам — Админ.
- Назначение прав пользователям на группы — Админ.

## 3.4. Закрепление механиков и специалистов за лифтами

### 3.4.1. Федеральное требование

За каждым лифтом должен быть закреплён механик. Это не опционально, а обязательное требование.

### 3.4.2. Правила

- Механик может быть закреплён за лифтами из разных групп.
- Механик может быть закреплён за несколькими лифтами.
- Один лифт может иметь несколько механиков (основной + резервные).
- При блокировке механика система предупреждает о лифтах без активного механика.
- Работа с заявками НЕ блокируется при отсутствии закреплённого механика — диспетчер может назначить любого ответственного.

### 3.4.3. Единая таблица закреплений

Закрепления механиков и специалистов хранятся в **одной таблице** `user_elevator_assignment` с полем `assignment_type`:

- `mechanic` — механик (закреплён за лифтом).
- `dispatch_specialist` — связист (закреплён за диспетчерским оборудованием).
- `electronics_specialist` — инженер-электронщик (закреплён за оборудованием).

**Источник истины — `user_elevator_assignment`.** Поля-кэши в `lift_object_core` и `lift_object_dispatch` (`core_assigned_mechanic_id`, `ds_assigned_specialist_id`) обновляются в той же транзакции и служат для быстрого отображения.

### 3.4.4. Связист — механик без лифтов

Связист (электромеханик диспетчерского оборудования) — это механик **без закреплённых лифтов**. Он работает только с заявками по диспетчерскому оборудованию, где назначен ответственным.

### 3.4.5. Инженер-электронщик — механик без лифтов

Инженер-электронщик — это механик **без закреплённых лифтов**, работающий с электроникой / диспетчерским оборудованием. В отличие от связиста, он может привлекаться к более широкому кругу заявок по электронике (уточняется).

### 3.6.5. Особые поля

**`abbreviated_name` (SPult ID):**

- Жёсткая привязка к внешней системе ЛКДС СПульт.
- Изменяется только Админом или пользователем с правом `can_edit_spult_id`.
- Запрещено массовое обновление.
- Каждое изменение логируется (старое → новое).

**`vis` (статус договора):**

- `1` — лифт активен, договор действует.
- `0` — лифт скрыт, договор расторгнут.
- Изменяется Админом или пользователем с правом `can_manage_contract_status`.
- Может меняться массово по дому, группе или контрагенту.
- Указывается дата расторжения/приостановки договора.
- При возобновлении договора в поля даты и причины скрытия записывается пустое значение.

## 3.7. Контрагенты и статус договора

### 3.7.1. Таблица контрагентов

Создаётся таблица `contractors` для хранения владельцев лифтов.

### 3.7.2. Поле `contractor_id` в `lift_object`

Каждый лифт ссылается на контрагента. Это позволяет:

- Фильтровать лифты по контрагенту.
- Массово менять `vis` по контрагенту.
- Видеть в карточке лифта, кому он принадлежит.

### 3.7.3. Жизненный цикл договора

```
Договор действует → Прораб/Админ расторгает → Лифты скрываются (vis=0)
 - указывается дата расторжения/приостановки договора.
 - при возобновлении договора в поля дата и причина скрытия записывается пустое значение.
                                                    ↓
Договор возобновлён ← Прораб/Админ возвращает ← Лифты видны (vis=1)
```

### 3.7.4. Поиск скрытых лифтов

Диспетчер может запросить поиск адреса с флагом «Искать в удалённых». В этом случае:

- Сервер возвращает все лифты, включая `vis=0`.
- Для скрытых лифтов добавляется поле `is_hidden` и причина скрытия.
- Пользователь получит информацию о том, почему не обслуживаем и с какого числа.
- **Создавать заявки по выключенным адресам может только Админ или Прораб, если ему даны отдельные права.**
- Диспетчер при попытке создать заявку на скрытый лифт получает отказ.

## 3.9. Переходная стратегия

### Этап 1 (сейчас)

- Legacy-тенант (sh) работает на `sh.e-rcs.ru`.
- Настраивается прокси `sh.liftcs.ru` → `sh.e-rcs.ru`.
- Новый тенант (l3) запускается на урезанном PHP-бэкенде (Трек А).
- Новый API (Трек Б) разрабатывается параллельно.

### Этап 2 (через 6–8 месяцев)

- Новый API готов.
- l3-тенант переносится на новый API (PostgreSQL, схема `tenant_l3`).
- Миграция: пользователи, лифты, **открытые** заявки, комментарии. Закрытые заявки — архив в MariaDB.
- sh-тенант продолжает работать через прокси (или переезжает позже, когда будет готов).

### Этап 3 (дальнейшее развитие)

- Все новые тенанты создаются сразу на новом API.
- sh-тенант переносится на новый API по готовности.
- Урезанный PHP-бэкенд остаётся только как архив (если нужен).

## 3.10. Schema-per-tenant в новом API

Принцип: каждый тенант = отдельная схема PostgreSQL.

**Подключение:**

1. Прокси-роутер определяет тенант по поддомену.
2. Запрос к API с заголовком `X-Tenant: l3`.
3. API переключает `search_path`: `SET search_path TO tenant_l3, public`.
4. Все последующие запросы — в рамках этой схемы.

**Плюсы:**

- Изоляция данных между тенантами.
- Простой бэкап: `pg_dump -n tenant_l3`.
- Простая миграция: применить миграции на каждую схему отдельно.
- Совместимость с принципом «своя БД на тенант».
- **Единое адресное пространство** — общие адреса в `public.lift_city/street/home`, доступны всем тенантам.

**Системные таблицы** (справочники, конфигурация, адреса) — в схеме `public`.

# РАЗДЕЛ 6. БИЗНЕС-ПРОЦЕССЫ

## 6.1. Быстрый вход диспетчера

### Сценарий

1. На диспетчерском компьютере сохранён ключ организации в `localStorage`.
2. При запуске фронтенд передаёт ключ на бэкенд через `check_org_key`.
3. Если ключ действителен — фронтенд вызывает `get_org_users` с этим ключом.
4. Бэкенд возвращает список **только обычных диспетчеров**.
5. Фронтенд показывает список на странице входа. Диспетчер выбирает себя и вводит пароль.

### Фильтр в `get_org_users`

В список попадают только пользователи, у которых:

| Условие               | Значение                           |
| --------------------- | ---------------------------------- |
| Организация           | соответствует `org_key`            |
| Статус                | не заблокирован (`user_block = 0`) |
| Базовая роль          | `dispatcher`                       |
| Должностной тип       | `dispatcher`                       |
| Разрешён быстрый вход | `allow_dispatcher_quick_login = 1` |
| Не скрыт              | `user_hiden = 0`                   |

**Прораб, админ, механик, связист, инженер-электронщик, гость — НЕ попадают в список.**  
**Старший диспетчер (диспетчер с доп. правами) — попадает, так как `user_position = 'dispatcher'`.**

### Ответ сервера

Минимальный набор данных:

| Поле      | Назначение       |
| --------- | ---------------- |
| `user_id` | ID для выбора    |
| `name`    | Отображаемое имя |

Не передаются: телефон, роль, права, служебные поля.

## 6.2. Создание заявки (`callnew` / `POST /calls/create`)

### Порядок действий

1. Фронтенд отправляет запрос с ключом `"action"` (или в URL для нового API).
2. Бэкенд проверяет авторизацию (Bearer-токен).
3. **Проверка прав:** `CallPolicy::canCreate($user, $groupId)`.
4. Валидация входных данных (минимальная длина описания — 6 символов, из `lift_options.min_length_text`).
5. **Адресный слой:** `AddressProvider::resolveAddress()` для валидации адреса.
6. Определение `alert_level` на основе правил.
7. INSERT в `lift_calls`.
8. Запись в `lift_history`.
9. Запись в `audit_log`.
10. Возврат `generated_id` фронтенду.

### Проверки прав при создании

- Админ: всегда.
- Диспетчер / Старший диспетчер: если группа заявки входит в его доступные группы.
- Прораб: если группа входит в его доступные группы.
- Механик, Гость, Связист, Инженер-электронщик: отказ.
- **При попытке создать заявку на скрытый лифт (`vis=0`):** Админ — разрешено; Прораб — только с правом `can_manage_contract_status`; остальные — отказ с сообщением «Договор по этому лифту расторгнут».

## 6.3. Редактирование заявки (`calledit` / `POST /calls/edit`)

### Порядок действий

1. Валидация `call_id`.
2. **Проверка прав:** `CallPolicy::canEdit($user, $call)`.
3. Проверка, что заявка не закрыта (`call_status != 1`).
4. Проверка ограничения: за один запрос — одно назначение или снятие ответственного.
5. Обновление только переданных полей.
6. Если передан `details` — дополнение описания (append-only).
7. Запись в `lift_history`.
8. Запись в `audit_log`.

### Ограничения

- Адрес менять нельзя.
- Закрытие через `calledit` запрещено.
- Механик не может редактировать заявку.

## 6.4. Закрытие заявки (`callClose` / `POST /calls/close`)

### Порядок действий

1. Валидация `call_id`, `solution` (мин. 6 символов), `user_id`.
2. **Проверка прав:** `CallPolicy::canClose($user, $call)`.
3. Проверка, что заявка не закрыта (защита от двойного закрытия).
4. **Оптимистичная блокировка:** если между проверкой и записью заявка закрыта другим пользователем — вернуть ошибку с именем закрывшего.
5. Сборка `call_fullhistory`: описание + все комментарии из `lift_notes` + лог из `lift_history`.
6. Сериализация `call_full_note_history` в JSON.
7. UPDATE `lift_calls`: `call_status=1`, `call_solution`, `call_date2`, `call_last_name`, `call_fullhistory`, `call_full_note_history`.
8. Удаление записей из `lift_notes` для этой заявки.
9. Запись в `audit_log`.

### Защита от гонок

Если два пользователя одновременно закрывают одну заявку:

- Первый успешный запрос закрывает заявку.
- Второй получает ошибку: «Заявка уже закрыта [имя] в [дата/время]».

## 6.5. Комментарии и фото (`callnote` / `POST /calls/note`)

### Порядок действий

1. Валидация `call_id`, `note` (мин. 6 символов), `photo_base64` (если есть).
2. **Проверка прав:** `CallPolicy::canComment($user, $call)`.
3. Проверка: механик НЕ может дополнять описание.
4. Обработка фото (если есть):
   - Проверка лимита: максимум **2 фото на всю заявку**.
   - Сохранение файла в `/uploads/calls/{call_id}/` (локально, техдолг).
   - Сжатие до 1280px, качество 0.7.
5. INSERT в `lift_notes` с `img_name`.
6. Запись в `lift_history`.
7. Запись в `audit_log`.

### Лимит фото

- Фронтенд ограничивает **1 фото на 1 комментарий**.
- Бэкенд ограничивает **2 фото на всю заявку** (суммарно по всем комментариям).
- Проверка: `SELECT COUNT(*) FROM lift_notes WHERE note_relation = ? AND img_name != ''`.

### Удаление фото по cron

- Cron-задача раз в день.
- Находит закрытые заявки старше 1 года.
- Парсит `call_full_note_history`, извлекает пути к фото.
- Переносит файлы в архивную папку.
- Через 3 месяца удаляет из архива.
- В `call_full_note_history` заменяет путь на заглушку.

## 6.6. Офлайн-синхронизация (`callNewOffline` / `POST /calls/offline`)

### Порядок действий

1. Фронтенд отправляет пачку (максимум 10 заявок).
2. Бэкенд начинает транзакцию.
3. Для каждого тикета:
   - Проверка идемпотентности: `SELECT call_id FROM lift_calls WHERE offline_uuid = ?`.
   - Если найдена — пропустить.
   - Если не найдена — вызвать `callnew()` с данными тикета.
4. Если ошибка в любом тикете — rollback всей пачки.
5. Запись в `offline_sync_log`.
6. Возврат результата.

### Обработка адресов

Если адрес не проходит валидацию через `AddressProvider`:

- Сохранить как есть.
- Установить `address_not_verified = 1`.
- Фронтенд покажет плашку «Адрес не проверен».

## 6.7. Смена прав и принудительный выход

### Порядок действий при изменении прав

1. Админ (или старший диспетчер — для диспетчеров) меняет права пользователя.
2. Бэкенд обновляет `user_group_access`.
3. Бэкенд добавляет хэш текущего токена пользователя в `revoked_tokens`.
4. Бэкенд устанавливает `lift_users.force_reload = 1`.
5. Запись в `audit_log`.

### Поведение фронтенда

1. При следующем запросе пользователь получает ошибку `TokenRevoked`.
2. Фронтенд показывает модальное окно: «Ваши права были изменены администратором. Сеанс будет завершён через 10 секунд».
3. Через 10 секунд фронтенд делает `logout` и редиректит на страницу входа.

### Очистка `revoked_tokens`

- Периодическая очистка записей старше 30 дней.
- Выполняется по cron или при логине.

## 6.8. Управление контрагентами и расторжение договора

### Расторжение договора

1. Прораб/Админ выбирает дом, группу или контрагента.
2. Нажимает «Расторгнуть договор».
3. Фронтенд отправляет `objectSetVisibilityBulk` с `vis=0`, причиной и датой расторжения.
4. Бэкенд проверяет право `can_manage_contract_status`.
5. UPDATE `lift_object SET vis=0, contract_suspended_at=now(), contract_suspend_reason=...` для всех затронутых лифтов.
6. Запись в `object_visibility_history`.
7. Запись в `audit_log`.

### Возобновление договора

1. Прораб/Админ заходит в список скрытых лифтов.
2. Выбирает лифты (или весь дом/контрагента).
3. Нажимает «Вернуть в работу».
4. Фронтенд отправляет `objectSetVisibilityBulk` с `vis=1` и причиной «Договор возобновлён».
5. UPDATE `lift_object SET vis=1, contract_suspended_at=NULL, contract_suspend_reason=NULL`.
6. Лифты снова видны в основном списке.

### Поиск скрытых лифтов

- В `loadAddress` добавляется параметр `include_hidden`.
- По умолчанию `false` — скрытые лифты не показываются.
- Если `true` — возвращаются все лифты, включая `vis=0`.
- Для скрытых лифтов добавляется `is_hidden: true`, `hidden_reason`, `suspended_at`.
- **Создавать заявки на скрытые лифты может только Админ или Прораб с правом `can_manage_contract_status`.**

## 6.9. Управление диспетчерами (старший диспетчер)

1. Админ выдаёт обычному диспетчеру права `can_create_dispatchers`, `can_edit_dispatchers`, `can_block_dispatchers` через `user_group_access`.
2. Диспетчер с этими правами (старший диспетчер) может:
   - Создавать новых диспетчеров (`POST /users` с `role='dispatcher'`, `position='dispatcher'`).
   - Изменять диспетчеров (`POST /users/:id`).
   - Блокировать диспетчеров (`POST /users/:id/block`).
3. Все действия логируются в `audit_log`.
4. При изменении прав диспетчера — принудительный выход (как в 6.7).

## 6.10. Работа инженера-электронщика

1. Инженер-электронщик (`user_position = 'electronics_engineer'`) — механик без закреплённых лифтов.
2. Закрепляется за оборудованием через `user_elevator_assignment` с `assignment_type = 'electronics_specialist'`.
3. Может привлекаться к заявкам по электронике (тип 24 и смежные — уточняется).
4. Просматривает свои заявки, добавляет комментарии, закрывает свои открытые заявки.
5. Не может редактировать заявки (как механик).

## 6.11. Поиск и отчёты по заявкам (Трек А и новый API)

### Сценарий

1. Диспетчер/Админ открывает экран «Отчёты».
2. Вводит номер заявки в поле поиска (быстрый поиск).
3. Или выбирает фильтры:
   - Лифт (выпадающий список по доступным группам).
   - Дом (выпадающий список).
   - Механик (выпадающий список закреплённых).
   - Период (от–до).
   - Статус (открытые / закрытые / все).
   - Исключить Аварийную службу (чекбокс, по умолчанию выключен).
4. Нажимает «Показать».
5. Система возвращает список заявок с пагинацией.
6. Может экспортировать результат в PDF или Excel.

### Правила поиска

- Поиск по номеру — частичное совпадение (`LIKE %номер%`).
- Фильтры комбинируются (`AND`).
- Если выбран «Исключить Аварийную службу» — в результат не попадают заявки с `is_emergency = true`.
- Механик видит только свои заявки (где `call_staff = user_id`).
- Диспетчер видит заявки своих групп.
- Лимит выборки — 10 000 строк. При превышении — пагинация или асинхронный экспорт (техдолг).

### Аудит

- Экспорт отчёта логируется в `audit_log` с параметрами фильтров.

## 6.12. Перенос тенанта с урезанного на новый API

### Сценарий (через 6–8 месяцев, когда новый API готов)

**1. Подготовка (T-7 дней):**

- Создать схему PostgreSQL для тенанта.
- Применить миграции на схему.
- Создать системную группу «Без группы».

**2. Миграция данных (T-0, ночью):**

- Скопировать пользователей (с хэшами паролей как есть).
- Скопировать лифты + основные/доп/диспетчер данные.
- Скопировать адреса (города, улицы, дома).
- Скопировать **открытые** заявки + комментарии + история.
- Скопировать справочники (уже будут в новом API).
- **Закрытые заявки — не переносить** (остаются в архиве MariaDB).
- **Фото — не переносить** (их не будет в урезанном).

**3. Валидация:**

- Скрипт сравнения: количество пользователей, лифтов, открытых заявок.
- Проверка целостности внешних ключей.

**4. Переключение:**

- Изменить DNS или прокси-роутер: `l3.liftcs.ru` → новый API.
- Проверка: логин, создание заявки, просмотр списка.

**5. Мониторинг (T+1 — T+7 дней):**

- Отслеживать ошибки.
- При критических проблемах — откат на урезанный PHP.

**6. Архив:**

- Закрытые заявки доступны через отдельный прокси или админку (реализуется позже).

# РАЗДЕЛ 7. ЛОГИРОВАНИЕ И АУДИТ

## 7.1. Два потока логирования

### Поток 1: Лог заявки (операционный)

- Живёт вместе с заявкой.
- Каждое действие (создание, дополнение описания, комментарий, смена статуса, назначение ответственного, закрытие) записывается в `lift_history`.
- При закрытии заявки весь лог сериализуется в `call_fullhistory`.
- Комментарии сериализуются в `call_full_note_history`.

### Поток 2: Общий аудит (`audit_log`)

Сюда пишутся все действия, не связанные с заявками:

- Вход/выход пользователя.
- Изменение прав доступа.
- Создание/редактирование лифта.
- Закрепление механика за лифтом.
- Создание/блокировка пользователя.
- Изменение группы.
- Изменение контрагента.
- Изменение `vis` (статус договора).
- Изменение `abbreviated_name` (SPult ID).
- **Создание/изменение/блокировка диспетчера старшим диспетчером.**
- **Экспорт отчёта** (с параметрами фильтров).

## 7.2. Правила логирования секретных полей

Для полей диспетчеризации (`ds_password_encrypted`, `ds_secret_key_encrypted`):

- **НЕ логировать** старое и новое значение.
- Логировать только факт изменения: «Пользователь [имя] изменил поле [имя поля] лифта №[id]».
- Логировать кто, когда, IP.

## 7.3. Просмотр секретов

Если пользователь запрашивает просмотр секретного поля (действие `objectDispatchReveal`):

- Проверка права `object_dispatch_view`.
- Запись в `audit_log`: «Пользователь [имя] просмотрел секретное поле [имя] лифта №[id]».

## 7.4. Append-only

Таблица `audit_log` только для записи. Никто, даже Админ, не может удалять или редактировать записи через интерфейс.
